## 한줄 요약
최근 라운드들에서 인덱스/보관주기/동시성 이슈가 이미 상당히 잘 정리되었고, storage.py 설계 자체는 현재 안정적입니다. 다만 `model_training_history()`를 쓰는 대시보드 쪽에 `prediction_accuracy_by_coin()`에서 이미 해결했던 것과 동일한 패턴의 N+1 조회 + 하드코딩 코인 목록 문제가 남아 있어, 그 부분만 새로 짚습니다.

## 발견한 점 (우선순위 순)

1. **`model_training_history()`에 코인별 배치 조회가 빠져 있음** — `storage.py:397-413`의 `model_training_history(conn, coin=None)`은 coin 하나만 받거나, coin 생략 시 전체를 하나의 timestamp 순으로만 섞어 반환합니다. 그런데 `dashboard.py:894-897`은 "코인별 최근 10개"가 필요해서 `for coin in ["BTC","ETH","XRP","SOL","DOGE","ADA"]:` 루프를 돌며 코인마다 별도 쿼리를 날립니다. 이는 과거 `prediction_accuracy_by_coin()`(storage.py:553-593)이 이미 고친 "코인마다 쿼리 1+N회" 패턴과 정확히 같은 모양인데, model_trainings 쪽은 그 리팩터링이 적용되지 않은 채 남아 있습니다. 지금은 코인이 6개로 고정돼 있어 성능상 급한 문제는 아니지만, 더 근본적인 문제는 **코인 목록이 dashboard.py에 리터럴로 박혀 있다는 점**입니다. 거래 유니버스에 코인이 추가되면 이 목록을 수동으로 안 고치는 한 그 코인의 학습 기록은 조용히 대시보드에서 빠집니다(에러 없이 누락).

2. **predictions 테이블의 복합 인덱스 3개는 현재는 괜찮지만 쓰기 비용이 쌓이는 지점** — `idx_predictions_coin_resolved_time`, `idx_predictions_resolved_time`, `idx_predictions_resolved_coin_time`(storage.py:188,189,198) 모두 각자 다른 조회 패턴을 위해 필요해서 과설계는 아니지만, `resolve_predictions()`(storage.py:427-451)의 매 사이클 UPDATE(resolved 0→1)가 이 3개 인덱스 모두에서 키 위치 변경을 유발합니다. 지금 보관주기(90일)와 코인 수 기준 정상 범위지만, 코인 수가 크게 늘거나 사이클 주기가 짧아지면 다시 볼 만한 지점입니다 — 지금 당장 조치는 불필요.

## 구체적 제안
- `storage.py`에 `prediction_accuracy_by_coin()`(570-584행)과 동일한 `ROW_NUMBER() OVER (PARTITION BY coin ORDER BY timestamp DESC)` 패턴으로 `model_training_history_by_coin(conn, coins: list[str] | None = None, limit_per_coin: int = 10) -> list[dict]`를 추가하세요. coins가 None이면 `SELECT DISTINCT coin FROM model_trainings`로 가져오면 하드코딩이 사라집니다.
- `dashboard.py:894-897`의 for 루프를 이 새 함수 호출 한 번으로 교체하세요. 반환된 리스트를 코인별로 그룹핑해 `reversed()`로 오래된 것 먼저 정렬하는 기존 로직만 유지하면 됩니다.

## 리스크/트레이드오프
- 새 배치 함수는 SQLite 3.25+ 윈도우 함수가 필요하지만, 이미 `prediction_accuracy_by_coin()`이 같은 요구사항을 쓰고 있어 추가 리스크는 없습니다.
- coins를 `SELECT DISTINCT coin`으로 자동 산출하면 과거에 한 번이라도 학습 기록이 있던 코인은 전부 나오므로, 지금처럼 "현재 거래 유니버스 6개만" 보여주던 암묵적 필터링이 사라집니다 — 유니버스에서 빠진 과거 코인까지 보이는 게 맞는지 확인 후, 필요하면 호출부에서 현재 유니버스 리스트를 명시적으로 넘기는 방식을 쓰는 게 안전합니다.
- (2)는 지금 당장 변경이 필요 없는 관찰 사항이라 코드 변경 자체의 리스크는 없습니다.
