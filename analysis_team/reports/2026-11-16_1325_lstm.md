## 한줄 요약
파인튜닝 학습률 분리는 이미 코드에 반영되어 있고(`lstm_model.py:177-178`), 재학습 주기·학습기간도 처음 설명(하루 1회/30일)보다 이미 크게 개선(하루 10회/90일, `main_loop.py:43-47`)되어 구조적으로는 양호함 — 남은 개선 포인트는 라벨링의 코인별 변동성 미반영과 피처의 "자기 참조성"에 있음.

## 발견한 점 (우선순위 순)

1. **`NEUTRAL_BAND`(44번째 줄)가 모든 코인에 동일한 고정값(0.05%)** — BTC처럼 변동성이 작은 코인과 변동성이 큰 알트코인은 1분 수익률 분포가 다른데, 같은 임계값을 쓰면 저변동 코인은 라벨에서 거의 안 걸러지고(노이즈가 그대로 학습 신호로 들어감), 고변동 코인은 너무 많이 걸러져(학습 샘플 손실) 코인별로 "학습 과제의 난이도"가 들쭉날쭉해질 수 있음.

2. **피처가 전부 해당 코인 자신의 OHLCV에서만 파생**(`FEATURE_COLS`, 57번째 줄) — 암호화폐는 BTC 동행성이 강한데 이 신호가 전혀 들어가 있지 않음. 다만 브리핑에서 언급된 "호가 스프레드"는 `data_fetcher.py`를 확인한 결과 Upbit 캔들(OHLCV)만 받아오고 있어 현재 데이터 파이프라인으로는 애초에 구할 수 없는 피처임 — 이건 추가 데이터 수집(오더북 API 연동) 없이는 불가능하므로 우선순위 낮음.

3. **train/val 분할(162~165번째 줄)이 시간순이라 미래 누수는 없지만, 경계 부근 시퀀스가 겹침** — `build_dataset`이 슬라이딩 윈도우(겹치는 60분 구간)로 샘플을 만들기 때문에, split 바로 앞 train 샘플과 바로 뒤 val 샘플은 입력 윈도우의 대부분(최대 59분)이 겹침. 전체 샘플 수 대비 영향은 작지만, 보고되는 val_accuracy가 실제보다 살짝 낙관적일 수 있음.

## 구체적 제안

- **A. 코인별 동적 NEUTRAL_BAND**: `build_dataset`(84번째 줄)에 `neutral_band: float | None = None` 파라미터를 추가하고, None이면 `close.pct_change().abs().median()` 같은 해당 코인 자체 수익률의 분포 기반 값(예: median의 0.5배)을 계산해 쓰도록 변경. `train_model`에서 `df`로부터 계산해 넘기면 코인마다 난이도가 균일해짐.
- **B. BTC 동행성 피처 추가**: `build_features`(61번째 줄)에 선택적 `btc_close: pd.Series | None` 인자를 추가하고 `btc_ret = btc_close.pct_change()`를 피처로 추가(`FEATURE_COLS`에 `"btc_ret"` 포함, N_FEATURES=6). `train_all`/`train_model` 호출부(`main_loop.py` 366번째 줄 근처)에서 이미 `fetch_all_minute_history`로 전체 코인을 받아오므로 BTC df를 같이 넘기기만 하면 됨.
- **C. 검증 분할에 gap 추가**: `train_model`(162~165번째 줄)에서 `split` 뒤 `X_val`은 그대로 두고, train 쪽에서 `X_train = X[:split - seq_len]`처럼 seq_len만큼 여유를 둬서 겹침 샘플을 제거.

## 리스크/트레이드오프

- A는 입력 feature 차원이 아니라 라벨링 기준만 바꾸므로 기존 저장된 가중치로 파인튠 이어가기 가능하지만, 코인별로 임계값이 달라지면 "코인 간 신호 강도 비교"가 더 어려워질 수 있음(리더보드에서 코인별 거래빈도 차이 해석 시 주의 필요).
- B는 입력 차원이 바뀌므로(`N_FEATURES` 5→6) 기존 `.pt` 가중치와 구조가 맞지 않아 전 코인 전면 재학습(`finetune=False`)이 최소 1회 필요하고, BTC 자체 모델은 "BTC의 BTC수익률=자기 자신"이 되어 별도 처리(자기 자신일 때는 제외) 필요.
- C는 학습 샘플이 소폭(seq_len만큼) 줄어들지만 전체 샘플 수(수만 개) 대비 미미하며, val_accuracy 신뢰도가 올라가는 이득이 더 큼.

(거래 건수, 실제 적중률, 손익 괴리 등 운영 데이터 기반 판단은 trading.db 접근이 필요한 부분이라 여기서는 다루지 않음.)
