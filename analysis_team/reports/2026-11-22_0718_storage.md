## 한줄 요약
schema/인덱스/동시성(WAL+재시도)/append-only 테이블 보관주기(prune)는 이미 여러 차례 리뷰를 거쳐 실제 쿼리 패턴에 잘 맞게 다듬어진 상태이며, 치명적 문제는 보이지 않는다. 유일하게 남은 공백은 `trades` 테이블에만 보관주기 정책이 없다는 점이다.

## 발견한 점 (우선순위 순)
1. **`trades` 테이블만 보관주기(prune) 정책이 빠져 있음.** `predictions`(90일, 447번째 줄), `snapshots`(365일, 464번째 줄), `model_trainings`(365일+trained=0만, 484번째 줄)는 모두 prune 함수가 있고 `main_loop.py` 754~763번째 줄에서 호출되지만 `trades`는 없다. 다만 `trades`는 1분 사이클마다 쌓이는 `predictions`와 달리 실제 매매 신호가 발생할 때만 INSERT되므로(`add_trades`, 307번째 줄) 증가 속도가 훨씬 느리고, 실제 체결 이력이라 지우면 과거 수익률/손절 통계를 복원할 수 없는 데이터다. "일관성 공백"이지 지금 당장 용량 문제라고 보기는 어렵다 — 실제 증가 속도는 운영 DB를 봐야 판단 가능.
2. **`predictions`에 복합 인덱스 3개**(`idx_predictions_coin_resolved_time`, `idx_predictions_resolved_time`, `idx_predictions_resolved_coin_time`, 181/182/191번째 줄)가 걸려 있다. 이 테이블은 사이클×코인마다 INSERT되는 가장 핫한 쓰기 경로라 매 INSERT마다 인덱스 3개가 갱신된다. 세 인덱스는 각각 코인 필터 유무/파티션 정렬 유무가 다른 쿼리 모양을 커버하므로 단순 중복은 아니고, "대시보드 읽기 속도 vs 사이클 쓰기 비용"을 의도적으로 읽기 쪽에 기울인 트레이드오프로 보인다. 코인 수가 적다면(현재 설계상 수 개~수십 개) 비용은 미미해 지금 손댈 필요는 없다.
3. **`portfolios`의 `"<strategy>__reset"/"<strategy>__cumulative"` 합성키**는 `make_portfolio_key`/`parse_portfolio_key`(52~86번째 줄)로 조립·파싱이 한 곳에 모였고, variant 오타와 strategy 내 구분자 충돌까지 쓰기 시점에 검증한다. 별도 `variant` 컬럼 + `UNIQUE(strategy, variant)`가 스키마상 더 "정석"이긴 하지만, 기존 `trading.db` 데이터 마이그레이션 비용 대비 지금 얻는 이득이 크지 않다.
4. **동시성(WAL + busy_timeout + 애플리케이션 재시도 + synchronous=NORMAL, 244~286번째 줄)**은 main_loop(쓰기)와 dashboard(읽기)의 실제 접근 빈도에 맞춰 적절히 구성돼 있고, 사이클 단위 커넥션/트랜잭션 경계도 문서화된 이유가 있어 새로 지적할 충돌 소지는 없다.

## 구체적 제안
- `trades`에 대해 지금 당장 `prune_trades`를 추가하라고 권하지는 않음. 다만 향후 거래량이 커질 경우를 대비해, 지우는 대신 `storage.py`에 `archive_old_trades(conn, keep_days=...)` 같은 함수를 만들어 오래된 행을 별도 파일(예: CSV/별 테이블)로 내보낸 뒤 원본에서 삭제하는 방식을 고려할 것 — `learner.py` 등에서 과거 전체 거래 이력을 참조하는 로직이 있는지 먼저 확인 후 적용.
- 그 외 스키마/인덱스는 현재 상태 유지를 권장.

## 리스크/트레이드오프
- `trades`를 지우거나 아카이브하면 "전체 기간 손절/수익 통계"를 사후에 복원할 수 없음 — 실제로 필요한 조치인지는 실제 운영 데이터(거래 건수 증가 속도, DB 파일 크기)를 봐야 판단 가능.
- `portfolios` 스키마를 지금 `variant` 컬럼 방식으로 바꾸면 기존 데이터 마이그레이션이 필요해, 마이그레이션 버그가 실제 포트폴리오 데이터 손상으로 이어질 위험이 생김 — 검증된 helper 함수로 유지하는 쪽이 더 안전.
