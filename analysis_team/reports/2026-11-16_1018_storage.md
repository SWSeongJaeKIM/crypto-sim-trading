## 한줄 요약
WAL+재시도 기반 동시성 처리는 이미 견고하지만, "strategy__mode" 합성 키 인코딩과 predictions/snapshots의 무제한 적재는 장기적으로 손봐야 할 설계상 약점이다.

## 발견한 점 (2~4개, 우선순위 순)

1. **portfolios/trades/snapshots의 전략 식별자가 문자열 합성 키("<strategy>__reset"/"<strategy>__cumulative")로만 존재** — `main_loop.py`에서 `portfolio_key(strat_name, mode)`로 "ma_cross_rsi__cumulative" 같은 문자열을 만들어 `storage.set_portfolio`/`add_trades`/`add_snapshot`의 `strategy` 컬럼(PK)에 그대로 저장하고, `dashboard.py:547`의 `name.rpartition("__")`로만 다시 분해한다. mode(reset/cumulative)는 엄연히 별도 차원인데 스키마에 컬럼이 없어 DB 레벨에서 `WHERE mode='reset'` 같은 쿼리나 FK/CHECK 제약을 걸 수 없고, 전략명에 `__`가 들어가면(지금은 없지만) 파싱이 깨진다. `get_params`/`set_params`는 반대로 base 전략명(`strat_name`)만 키로 써서 모드별 합성 키와 혼용되고 있어 일관성도 떨어진다.

2. **predictions, snapshots가 append-only로 사실상 무제한 증가** — predictions는 6코인×1분 주기로 쌓여 연간 약 300만 행, snapshots는 5개 전략×2모드×1분 주기로 연간 약 500만 행 규모까지 커질 수 있다(main_loop.py `CYCLE_INTERVAL_SEC=60`). 코드 전체를 검색했지만 DELETE/VACUUM/retention 로직이 전혀 없다. 조회 쿼리들은 인덱스(`idx_predictions_coin`, `idx_snapshots_strategy`)와 `LIMIT`을 쓰고 있어 당장 쿼리 속도 저하는 크지 않지만, DB 파일 크기와 백업 용량은 계속 늘어난다.

3. **동시 쓰기(main_loop)/읽기(dashboard) 충돌은 이미 잘 처리됨** — `connect()`에서 WAL 모드 + `busy_timeout` + `_RetryingConnection`의 애플리케이션 레벨 재시도(최대 8회, 선형 백오프)를 3중으로 걸어뒀고, 스키마 초기화도 프로세스당 1회로 제한해 락 경합 기회를 줄였다(`_schema_initialized_paths`). 예외 시 명시적 rollback으로 락을 빨리 풀어주는 것까지 고려되어 있어, 이 관점에서는 추가로 손댈 필요가 보이지 않는다.

4. **`recent_trades(strategy=None)` 전체 스캔** — `storage.py:242` 경로는 `strategy` 조건 없이 `ORDER BY timestamp DESC LIMIT`만 쓰는데, 기존 인덱스는 `(strategy, timestamp DESC)` 복합 인덱스뿐이라 전략 미지정 조회 시 이 인덱스를 못 쓰고 테이블 전체 스캔+정렬이 될 수 있다. trades는 실제 체결 시에만 쓰여 적재 속도가 낮아 당장은 미미하지만, 데이터 분석가 조회(대시보드 "전체 최근 거래" 뷰)에서 누적될수록 느려질 패턴이다.

## 구체적 제안
- `storage.py` SCHEMA에 `mode TEXT`를 portfolios/trades/snapshots에 별도 컬럼으로 추가하고 PK를 `(strategy, mode)` 복합키로 바꾸는 쪽을 장기 과제로 검토. 당장 전체 마이그레이션이 부담되면 최소한 `dashboard.py:547`의 파싱 로직에 "mode가 reset/cumulative가 아니면 즉시 예외/로그"를 추가해 조용한 오분류를 막는다.
- `model_trainings`/`predictions`/`snapshots`에 대해 "N일 이전 데이터는 일 단위로 집계 후 원본 삭제" 같은 간단한 retention 함수를 storage.py에 추가하고, dashboard 시작 시 또는 별도 주기로 1회 실행.
- `storage.py:49` trades 테이블에 `CREATE INDEX idx_trades_timestamp ON trades(timestamp DESC)` 단일 컬럼 인덱스를 추가해 전략 미지정 조회 경로를 커버.

## 리스크/트레이드오프
- 합성 키를 분리 컬럼으로 바꾸는 마이그레이션은 기존 trading.db의 모든 테이블 데이터를 변환해야 하므로, 이미 존재하는 `migrate_dual_portfolio.py` 패턴처럼 1회성 마이그레이션 스크립트와 실제 운영 데이터 백업이 필요하다 — 운영 중 봇을 멈춰야 할 수도 있다.
- retention/삭제 로직은 "모델 성능 추이 전체 보존"이라는 model_trainings의 설계 의도와 충돌할 수 있으므로 model_trainings는 삭제 대상에서 제외하고 predictions/snapshots에만 적용해야 한다. 또한 삭제 타이밍이 main_loop의 쓰기와 겹치면 락 경합을 새로 만들 수 있어, 별도 유지보수 스크립트(한가한 시간대)로 분리하는 것이 안전하다.
- 실제로 지금 DB 파일 크기나 쿼리 지연이 문제가 되고 있는지는 운영 데이터(trading.db)를 봐야 판단 가능 — 코드만으로는 "증가 추세의 존재"만 확인했고 현재 심각도는 알 수 없다.
