## 한줄 요약
스키마/동시성/보관주기는 이전 analysis_team 리포트들을 거치며 대부분 잘 다듬어졌고, 남은 핵심 이슈는 portfolios 합성키의 근본적 설계 한계와 prune 함수들이 "정의만 되어 있고 실제 호출 주체는 이 파일 밖"이라는 점이다.

## 발견한 점 (우선순위 순)
1. **portfolios 합성키(`<strategy>__variant`) 구조적 한계** — `make_portfolio_key`/`parse_portfolio_key`(52~74행)가 쓰기 시점 검증과 읽기 시점 폴백을 보강했지만, 근본적으로 `strategy TEXT` 단일 PK(89~93행)에 variant 정보를 문자열로 인코딩하는 구조다. strategy 이름 자체에 `__`가 들어가면 파싱 모호성이 남고(rpartition 기준이라 거의 안전하지만 이론상 충돌 가능), variant 종류가 늘어날 때마다 두 함수를 같이 고쳐야 한다. "쓰기 시점 검증 추가"는 좋은 개선이지만 "장기적으로 유지보수하기 좋은 스키마"로 보기는 어렵다.
2. **prune 함수들의 호출 주체 불명** — `prune_predictions`/`prune_snapshots`/`prune_model_trainings`(420~475행)는 잘 설계돼 있으나, storage.py 안에는 이들을 주기적으로 호출하는 코드가 없다. 호출은 main_loop.py 쪽일 것으로 추정되나 이 파일만으로는 확인 불가 — main_loop.py를 봐야 판단 가능.
3. **trades 테이블은 prune 대상에서 빠져있음** — predictions/snapshots/model_trainings와 같은 append-only지만 보관주기가 없다. 다만 거래는 신호 발생 시에만 생성되므로(매 사이클이 아님) 증가 속도가 predictions 대비 훨씬 낮아 당장 급한 문제는 아니다.
4. **동시성/인덱스 설계는 이미 잘 되어 있음** — WAL + busy_timeout + 애플리케이션 레벨 재시도(216~259행), 그리고 실제 쿼리 패턴(전체 스캔 경로, resolved+시간 정렬, N+1 쿼리)에 맞춘 인덱스 보강(104~164행)은 반복적인 리뷰를 거쳐 타당하게 정리되어 있다. 억지로 더 손댈 필요는 없어 보인다.

## 구체적 제안
- **portfolios 스키마 변경**: `strategy TEXT, variant TEXT CHECK(variant IN ('reset','cumulative')), data_json TEXT, updated_at TEXT, PRIMARY KEY(strategy, variant)` 형태로 별도 마이그레이션 적용. 마이그레이션 시 이미 있는 `parse_portfolio_key`(67~74행)를 그대로 재사용해 기존 `"strategy__variant"` 키를 분해하고 새 테이블에 INSERT, 기존 테이블은 DROP 대신 `old_portfolios`로 rename해 데이터 손실 방지. `get_portfolio`/`set_portfolio`(262~277행) 시그니처에 `variant` 파라미터를 추가해야 하며, 이는 main_loop.py/dashboard.py 호출부도 함께 바꿔야 하는 다파일 작업이다.
- **prune 함수 3종(420~475행) 실제 호출 여부 확인**: main_loop.py의 사이클 루프에서 "N사이클마다 1회"(예: 1440사이클=1일) 호출되고 있는지 확인 필요. 없다면 main_loop.py에 하루 1회 호출을 추가해야 함(범위 밖이라 여기서는 코드 작성 안 함).
- **prune_trades(keep_days=365) 추가**: `prune_snapshots`(437~454행)와 동일 패턴으로 trades에도 보관주기 함수를 추가해 일관성 확보(우선순위 낮음).

## 리스크/트레이드오프
- portfolios 스키마 변경은 main_loop.py/dashboard.py를 동시에 맞춰 배포해야 해서, 순서를 잘못하면 과도기에 데이터 불일치가 생길 수 있다. 실제 운영 DB 백업 없이 적용하면 위험.
- prune 함수를 실제로 스케줄링하면 과거 predictions/snapshots 데이터는 복구 불가 — keep_days 값이 대시보드가 보여주려는 "장기 추이" 기간보다 짧으면 안 된다(이미 문서화돼 있어 위험은 낮음).
- trades에 prune을 추가하면 과거 전체 거래 기록이 필요해질 경우(예: 장기 성과 재분석) 지워진 데이터를 못 보게 될 수 있다. 모의투자라 실손실은 없지만 분석 가치 손실은 있을 수 있음.

(참고: 분석 대상은 /home/claude/crypto-sim-trading/local/storage.py 한 파일로 한정했으며, 실제 운영 DB의 거래내역/손익/학습 정확도 등 데이터 값 자체는 보지 않았다.)
