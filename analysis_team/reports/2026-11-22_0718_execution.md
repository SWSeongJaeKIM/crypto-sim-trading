## 한줄 요약
예외처리 격리, 로깅 쓰로틀링, 60초 사이클 드리프트 보정은 이미 여러 차례의 자체 분석을 거쳐 견고하게 구현돼 있어 이번 검토에서도 사이클을 죽이는 새로운 치명적 결함은 없었다. 다만 (1) 과거 리포트(2026-11-22_0618)가 지적했던 "재학습마다 90일 전체 재수집" 구조가 아직 미적용 상태로 남아 있고, (2) API 재시도/병렬호출 경로에서 작은 타이밍 비효율 2건을 새로 발견했다.

## 발견한 점 (우선순위 순)

1. **LSTM 재학습마다 90일치 1분봉을 캐시 없이 매번 전체 재수집** (`local/data_fetcher.py` 301~374행, `fetch_minute_history` 168~270행 / `local/main_loop.py` 523~617행 `retrain_lstm`). 캐시 CSV(343행)는 실패 시 폴백으로만 쓰이고 정상 경로에서는 항상 코인당 ~648페이지를 처음부터 다시 받는다. `retrain_lstm()`이 메인 루프와 동기 실행되므로 이 구간(수 분~수십 분, 로그로 소요시간은 확인 가능) 동안 60초 매매 사이클이 완전히 멈춘다. 하루 10회(`RETRAIN_TIMES_LOCAL`) 반복되면 누적 정지 시간이 상당할 수 있다. `analysis_team/reports/applied_log.json`에도 같은 제안이 "skipped"(통합 테스트 부재로 보류)로 남아 있어, 여전히 유효한 미해결 항목이다.

2. **(신규, 경미) `_http_get_json`이 마지막 재시도 실패 후에도 불필요하게 sleep한다** (`local/data_fetcher.py` 108~133행). `for attempt in range(retries)` 루프의 `except` 블록(132행)이 매 실패마다 `time.sleep(1.0*(attempt+1))`을 호출하는데, 이는 더 이상 재시도가 없는 마지막 attempt에서도 실행된다. `fetch_latest_minute_candles`(timeout=5, retries=2, 매 60초 사이클마다 호출되는 핫패스)의 경우 완전 실패까지 걸리는 시간이 11초가 아니라 13초가 되는 식으로, 불필요한 지연이 매번 들어간다.

3. **(신규, 경미) 실시간 캔들 수집(`fetch_all_latest_candles`)에는 공유 레이트리미터가 없다** (`local/data_fetcher.py` 273~298행). `fetch_all_minute_history`는 6코인 스레드가 전역 `_RateLimiter`를 공유해 Upbit 호출 속도를 명시적으로 제어하는데, 매 60초마다 실행되는 실시간 경로는 같은 보호 없이 6개 요청을 동시에 쏜다. 현재 코인 수(6)와 주기(60초)에서는 Upbit 한도에 걸릴 위험이 낮지만, 같은 파일 안에서 두 경로의 설계가 비대칭적이다.

(참고: Ctrl+C 종료 메시지가 재학습 중 부정확했던 과거 지적(0618 리포트)은 현재 `main_loop.py` 159~169행의 `_in_retrain` 분기 처리로 이미 반영되어 있어, 이번 리포트에서는 다시 거론하지 않았다.)

## 구체적 제안
- (1) `fetch_minute_history`에 `since`(캐시 CSV의 마지막 `open_time`) 파라미터를 추가해 재학습 간격(2시간24분)만큼인 코인당 ~15페이지만 증분 수집하고, PC가 오래 꺼져있다 켜진 경우를 대비해 캐시-현재 공백이 임계치 이상이면 전체 재수집으로 폴백하는 가드를 함께 넣는다. (기존 리포트와 동일 제안이며, 핵심 데이터 파이프라인 변경이라 통합 테스트 전까지는 신중히 접근할 것.)
- (2) `local/data_fetcher.py` 132행을 `if attempt < retries - 1: time.sleep(1.0 * (attempt + 1))`로 바꿔 마지막 시도 후의 무의미한 대기를 제거한다.
- (3) `fetch_all_latest_candles`의 `_fetch_one`(279~291행)에도 `fetch_all_minute_history`와 동일한 `_RateLimiter`(또는 더 짧은 간격의 별도 인스턴스)를 선택적으로 넘겨, 두 경로의 설계를 통일하고 향후 코인 수가 늘어날 때를 대비한다.

## 리스크/트레이드오프
- (1)은 상시 의존 핵심 파이프라인 변경(시그니처·캐시 병합·공백 감지)이라 Upbit 응답 경계값에 대한 실제 테스트 없이 적용하면 기존 동작을 깨뜨릴 위험이 있다 — 과거에도 같은 이유로 보류된 바 있다.
- (2)는 순수 효율 개선이라 부작용이 거의 없으나, 체감 효과는 코인당 1~3초 수준으로 작다.
- (3)은 현재 트래픽 수준에서는 이득이 작고, 리미터를 추가하면 코인 수가 늘었을 때 실시간 사이클 소요시간이 늘어날 수 있어 `CYCLE_ELAPSED_WARN_THRESHOLD_SEC`(30초) 경고 빈도에 영향을 줄 수 있다 — 간격 값을 충분히 짧게(예: 0.05초 이하) 잡아야 한다.

(참고: "지금 실제로 사이클이 60초에 근접해 지연되고 있는가", "재학습 정지 시간이 실제 매매 성과에 얼마나 영향을 주는가"는 실제 운영 데이터(run.log, DB)를 봐야 판단 가능하며 코드 구조만으로는 알 수 없다.)
