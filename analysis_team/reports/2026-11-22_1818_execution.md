## 한줄 요약
직전 회차에서 지적된 3건(on_progress 예외처리, 전체 캔들 실패 쓰로틀, COINS 중복)은 모두 코드에 반영되어 해결됨을 확인했고, 예외처리·API 재시도·사이클 타이밍 로직 전반은 견고하다. 다만 "최신 1분봉"의 데이터 신선도(staleness)를 검증하지 않는 새로운 진단 공백을 발견했다.

## 발견한 점 (우선순위 순)
1. **(신규) 최신 캔들의 신선도 검증 부재** — `local/data_fetcher.py`의 `fetch_latest_minute_candles`(195~229행)와 `local/main_loop.py`의 `run_one_cycle`(404행 근처)은 HTTP 200 + 정상 JSON이면 캔들의 `open_time`이 실제로 "지금"에 가까운지 전혀 확인하지 않는다. Upbit이 네트워크 에러 없이 지연/캐시된 응답(예: 서버·CDN 쪽 일시 지연)을 돌려주면, 사이클은 "정상 완료"로 기록되고 매매는 오래된 가격으로 계속 진행되지만 run.log에는 아무 흔적도 남지 않는다. 기존의 모든 쓰로틀 패턴(`_warned_missing_coin_data`, `_warned_all_candles_fail` 등)은 "실패"는 잡아내지만 "조용한 지연"은 구조적으로 잡아내지 못한다.
2. **(해결 확인)** `local/data_fetcher.py` 484~496행 `on_progress` 콜백 try/except 보호 — 반영됨(커밋 `370a47d`).
3. **(해결 확인)** `local/main_loop.py` 전체 캔들 수집 실패 로그 1시간 쓰로틀(`_warned_all_candles_fail`, 162~163/392~400행) — 반영됨(커밋 `0cd656e`).
4. **(해결 확인)** COINS 중복 정의 — `local/data_fetcher.py` 36행에서 `portfolio.COINS`를 import해 제거됨(커밋 `6d8f6d5`).
5. **(부차, 저우선)** `local/data_fetcher.py` 421~444행 `last_full_refresh.json` 마커 파일 쓰기가 비원자적(`write_text` 직접 호출). 다만 읽기 실패 시 "오늘 전체 재수집 안 함"으로 안전하게 폴백하므로 치명적이지 않음 — 참고용으로만 기록.

## 구체적 제안
- `fetch_latest_minute_candles()`가 반환하는 df의 마지막 행 `open_time`을 이용해, `local/main_loop.py` `run_one_cycle()`의 `prices_krw` 생성 직후(404행 근처)에서 "현재 시각 − 마지막 캔들 open_time"이 예컨대 3~5분을 넘으면 해당 코인에 경고 로그를 남긴다. 기존 `_warned_missing_coin_data`와 동일한 1시간 쓰로틀 딕셔너리 패턴(코인별)을 재사용해 로그 폭주를 막는다. 캔들을 버리거나 매매를 막을 필요는 없고, 진단용 로깅만 추가하면 된다(기존 매매 로직 무영향).
- `candle_date_time_kst`는 naive 로컬(KST) 시간이므로, 비교 기준도 `datetime.now()`(main_loop.py가 재학습 스케줄 계산에서 이미 쓰는 관례)와 동일하게 맞춰야 한다. UTC `datetime.now(timezone.utc)`와 섞어 비교하면 9시간 오프셋 오류가 날 수 있다.

## 리스크/트레이드오프
- 임계값을 너무 짧게 잡으면(예: 1분) Upbit 응답의 정상적인 지연에도 매 사이클 경고가 발생해 로그 폭주 위험이 있다 — 3~5분 여유 + 코인별 1시간 쓰로틀을 함께 둬야 한다.
- 신선도 체크는 "가격은 있지만 오래됨" 케이스만 대상으로 해야 하며, 이미 `missing_coins` 분기가 커버하는 "가격 자체가 없음" 케이스와 조건이 겹치지 않도록 구분해야 중복 경고를 피할 수 있다.
- 순수 로깅 추가라 실행/타이밍 구조에는 영향이 없지만, 코드 리뷰 지침상 트레이딩 로직 파일은 수정하지 않았으므로 위 제안은 적용 여부를 운영자가 판단해야 한다.
