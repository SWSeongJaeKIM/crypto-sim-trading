## 한줄 요약
피처·학습 로직 상당 부분은 이미 근거 있게 설계되어 있고(검증 셋 겹침 제거, 롤백 안전장치, val_acc 기반 임계값 조정 등), 가장 실질적인 개선 지점은 "영구 파인튠 체인에 자동 리셋 트리거가 없다"는 점과 "피처가 가격/거래량 파생 지표로만 한정되어 있다"는 점이다.

## 발견한 점 (2~4개, 우선순위 순)

1. **(중요) 파인튠 체인 길이를 추적만 하고 자동으로 쓰지 않음.** `get_finetune_chain_length()`(310~328줄)와 `finetune_chain_length` 메타 기록(236~279줄)이 이미 구현돼 있지만, `train_model()` 내부 어디에도 이 값을 읽어 "N회 이상 연속 파인튠되면 전체 재학습으로 전환"하는 로직은 없다(주석 238~266줄에서 코드 작성자 스스로 이 한계를 인지하고 있음). `finetune=True`가 기본값이고 호출부가 계속 같은 방식으로 부르면, 가중치가 몇 달간 한 번도 처음부터 다시 학습되지 않을 수 있어 과거 레짐에 서서히 고착(stale)될 위험이 있다. `VAL_ACC_ROLLBACK_THRESHOLD`(69줄)는 "한 번의 급격한 하락"만 잡아내지, "서서히 누적되는 드리프트"는 잡지 못한다.

2. **피처가 전부 가격·거래량 파생 지표(`FEATURE_COLS`, 71줄)뿐.** `ret`, `vol_chg`, `rsi14`, `macd_hist`, `bb_pctb` 5개 모두 해당 코인 자신의 close/volume에서만 계산된다. 호가 스프레드는 1분봉 OHLCV API 응답에 원래 없는 정보라 추가하려면 호가(orderbook) 수집 파이프라인을 새로 만들어야 하는 큰 변경이고, 이 파일 선에서 해결할 범위를 넘는다. 반면 다른 코인과의 상관관계(특히 BTC 선행성)는 시스템이 이미 6개 코인의 1분봉을 동시에 받아오는 구조(42줄 주석)라 상대적으로 적은 변경으로 추가 가능하다.

3. **SEQ_LEN(60)과 모델 크기(hidden=32, 1 layer)는 과적합보다 데이터 양 대비 적절한 편.** 코인당 샘플이 수만~십만 개 수준인데 파라미터는 약 5천개 수준이라 과적합 소지는 낮고, 코드가 이미 관찰한 54~62% val_accuracy(52~59줄)는 모델 용량 문제가 아니라 1분 방향성 자체의 낮은 신호 대 잡음비 문제로 보인다. 임계값을 0.55/0.45→0.60/0.40으로 올린 대응은 이미 합리적이라 추가로 구조를 바꿀 필요는 크지 않다.

4. 재학습 주기/데이터 기간 관련: 과제에서 전제한 "하루 1회+30일"은 이 파일의 문서화된 내용(하루 10회, `HISTORY_DAYS_FOR_TRAIN`=90일 — 18~20줄)과 다르다. 실제 설정값(`RETRAIN_TIMES_LOCAL`, `HISTORY_DAYS_FOR_TRAIN`)은 `main_loop.py`에 있어 이 파일만으로는 확인 불가.

## 구체적 제안
- `lstm_model.py` 141번째 줄 `train_model()` 시작부 근처에 `MAX_FINETUNE_CHAIN` 상수(예: 10, 즉 "하루치")를 추가하고, `prev_chain_length`를 모델 로드 전에 먼저 읽어(현재는 190줄에서 가중치 로드, 245~252줄에서야 chain_length 확인 — 순서를 바꿔야 함) `prev_chain_length >= MAX_FINETUNE_CHAIN`이면 `resumed_from_existing = False`로 강제해 전체 재학습을 트리거.
- `build_features()`(75~96줄)에 `ret.rolling(10).std().fillna(0)` 같은 변동성 피처를 추가하고 `FEATURE_COLS`(71줄)에 반영 — 가장 적은 변경으로 가능한 피처 보강.
- BTC 상관 피처는 `build_features`/`build_dataset`/`predict_proba`/`LSTMStrategy.signal` 네 함수 모두 시그니처 변경이 필요한 중간 규모 리팩터링이라 별도 작업으로 분리 권장.

## 리스크/트레이드오프
- 자동 전체 재학습 트리거를 넣으면 그 시점의 val_accuracy가 일시적으로 하락할 수 있고(파인튠 대비 수렴이 느림), `VAL_ACC_ROLLBACK_THRESHOLD`와 상호작용해 저장이 건너뛰어질 수 있어 두 로직을 함께 검토해야 한다.
- 변동성/상관 피처 추가는 입력 차원이 늘어 학습 시간이 다소 증가하고, 기존 저장 가중치(`N_FEATURES=5` 기준)와 shape가 맞지 않아 전체 재학습이 1회 강제된다.
- 실제 운영 환경에서 재학습 주기/데이터 기간이 과제가 설정한 "하루 1회/30일"인지 "코드 주석의 하루 10회/90일"인지는 `main_loop.py`를 봐야 확정 가능 — 실거래 수익성 여부와 함께, 이 부분은 실제 운영 데이터와 다른 파일을 봐야 판단 가능하다.
