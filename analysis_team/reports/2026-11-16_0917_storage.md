## 한줄 요약
스키마와 인덱스 자체는 실제 쿼리 패턴(strategy+timestamp, coin+predicted_at, resolved)에 맞게 짜여 있고 동시성(WAL+busy_timeout) 처리도 적절하지만, `predictions`/`trades`의 일부 전역(strategy/coin 미지정) 조회는 인덱스를 완전히 못 타고, append-only 테이블에 보관주기가 없어 장기적으로는 파일 크기·조회 속도가 서서히 나빠질 소지가 있다.

## 발견한 점 (우선순위 순)
1. **`prediction_accuracy(coin=None)` (storage.py 278-293행)**: `WHERE resolved=1 ORDER BY predicted_at DESC LIMIT 500` 질의인데, 기존 인덱스는 `idx_predictions_unresolved(resolved)` 단일 컬럼과 `idx_predictions_coin(coin, predicted_at DESC)` 복합뿐이라, coin 없이 전체 적중률을 구할 때는 resolved로 필터한 뒤 predicted_at을 따로 정렬해야 한다. predictions는 매 사이클 코인 수만큼 계속 쌓이는 append-only 테이블이라, 행이 수십만~수백만 단위로 늘어나면 이 전역 집계가 점점 느려진다.
2. **`recent_trades(strategy=None)` (storage.py 168-178행)**: strategy 미지정 시 `ORDER BY timestamp DESC LIMIT 20` 전역 조회를 하는데, 유일한 인덱스 `idx_trades_strategy(strategy, timestamp DESC)`는 선두 컬럼이 strategy라 전역 정렬엔 도움이 안 된다. trades는 실제 매매 발생시에만 쌓여 성장 속도는 느리지만, dashboard.py가 이 전역 호출(547행)을 쓰고 있어 장기적으로 행이 많아지면 매 대시보드 새로고침마다 비용이 커진다.
3. **보관주기 부재**: predictions, model_trainings 모두 삭제/정리 로직이 전혀 없다. 특히 predictions는 코인 수 × 1분마다 적재되므로(예: 코인 5개면 하루 약 7,200행, 1년에 약 260만행 추정) 지금 당장은 SQLite+인덱스로 버틸 수 있는 수준이지만, retention이 없으면 DB 파일이 계속 커지고 백업/복사 비용도 늘어난다.
4. **`portfolios`의 `"<strategy>__reset"/"<strategy>__cumulative"` 문자열 PK**: storage.py 자체는 `strategy TEXT PRIMARY KEY`(43-47행) 하나만 정의하고 mode 구분은 호출부 문자열 인코딩(main_loop.py `portfolio_key()`, dashboard.py에서 `rpartition("__")` 역파싱)에 의존한다. 과거 `migrate_dual_portfolio.py`가 별도로 필요했던 전례가 이 설계의 마이그레이션 비용을 이미 보여준다.
5. **동시성(main_loop 쓰기 vs dashboard 읽기)**: `connect()`(106-121행)에서 WAL 모드 + busy_timeout=5000을 설정한 것은 이 상황에 맞는 적절한 처리로, 추가 수정이 필요하지 않다.

## 구체적 제안
- storage.py 101-102행 인덱스 선언 옆에 `CREATE INDEX IF NOT EXISTS idx_predictions_resolved_time ON predictions(resolved, predicted_at DESC);` 추가 → `prediction_accuracy(coin=None)`이 이 복합 인덱스로 필터+정렬을 한 번에 처리.
- 58행 idx_trades_strategy 옆에 `CREATE INDEX IF NOT EXISTS idx_trades_timestamp ON trades(timestamp DESC);` 추가 → `recent_trades(strategy=None)` 전역 조회 속도 개선.
- `prune_old_predictions(conn, days=90)` 같은 헬퍼를 storage.py에 추가해 `DELETE FROM predictions WHERE resolved=1 AND predicted_at < datetime('now','-90 days')`를 main_loop.py 사이클에서 하루 1회 호출. model_trainings는 성장이 느리므로 당장은 보관주기가 급하지 않음.
- portfolios를 strategy/mode 분리 컬럼의 복합 PK로 바꾸는 편이 깨끗하나, 이는 storage.py 범위를 넘어 main_loop.py/dashboard.py까지 손봐야 하는 큰 변경임.

## 리스크/트레이드오프
- 인덱스 추가는 매 사이클 INSERT/UPDATE(특히 predictions)의 쓰기 비용과 디스크 사용량을 소폭 늘린다.
- 오래된 predictions를 삭제하면 "장기 적중률 추이" 같은 히스토리 분석 데이터가 사라진다 — 삭제 대신 일별 집계 테이블로 요약 보관하는 방식이 더 안전할 수 있다.
- portfolios 스키마를 복합 키로 바꾸면 기존 "__reset"/"__cumulative" 데이터를 다시 마이그레이션해야 하고 호출부 수정도 동반되어 변경 범위가 커진다.
- 실제 trading.db의 현재 행 수, 파일 크기, 쿼리 응답 시간은 운영 데이터를 봐야 확정 가능하며, 이 분석만으로 "지금 실제로 느려지고 있는지"는 판단할 수 없다.
