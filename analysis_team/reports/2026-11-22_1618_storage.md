## 한줄 요약
직전 회차의 `case_sensitive_like=ON` 수정(storage.py 277~284행)은 올바르게 적용됐고 부작용도 없음(프로젝트 전체에서 LIKE는 storage.py 2곳뿐, grep으로 확인) — 다만 `snapshots` 테이블에 대해 trades/model_trainings와 동일한 "보관주기 삭제용 timestamp 단독 인덱스"가 빠져 있어 매일 전체 스캔이 발생하는 문제가 새로 발견됨.

## 발견한 점 (2~4개, 우선순위 순)

**1) `prune_snapshots()`가 매일 `snapshots` 전체 스캔 — timestamp 단독 인덱스 없음 (storage.py 142행 / 547~551행)**
`snapshots` 테이블엔 `idx_snapshots_strategy(strategy, timestamp DESC)` 하나뿐이다(142행). 그런데 `prune_snapshots()`(535~552행)의 삭제 쿼리는 `DELETE FROM snapshots WHERE timestamp < ?`로 strategy 필터가 전혀 없다(548~551행). 복합 인덱스의 선두 컬럼(strategy)을 못 쓰니 매일(main_loop.py의 하루 1회 보관주기 정리 시점, main_loop.py 807~848행) 전체 테이블 스캔+삭제가 된다. `trades`(storage.py 124~128행, idx_trades_timestamp)와 `model_trainings`(166~169행, idx_model_trainings_timestamp)는 "전략/코인 필터 없는 시간 기준 쿼리"를 위해 이미 똑같은 패턴으로 timestamp 단독 인덱스를 추가해놨는데, `snapshots`만 빠졌다. snapshots는 모든 전략×variant(reset/cumulative)가 1분마다 1행씩 쌓이는 구조라(main_loop.py 548행 `storage.add_snapshot(conn, key, ...)`, key는 `make_portfolio_key` 합성키) 테이블 행수가 다른 두 테이블보다 더 빨리 늘어날 수 있고, 보관기간도 365일로 가장 길다(SNAPSHOTS_PRUNE_KEEP_DAYS). 전략 수가 늘어날수록 이 매일 전체 스캔 비용이 커진다.

**2) `case_sensitive_like=ON` 수정 검증 결과: 정상, 사이드이펙트 없음**
`local/` 전체에서 LIKE를 쓰는 곳은 storage.py 658~662행(`stop_loss_counts_by_coin`) 두 줄뿐임을 grep으로 확인했다. 둘 다 고정 한글 접두어(`'손절%'`, `'강제청산%'`)라 대소문자 구분 여부가 결과에 영향을 주지 않고, 다른 LIKE 쿼리가 이 pragma 때문에 의도치 않게 깨질 여지도 없다. pragma는 connect()마다 매번 재설정되므로(284행) 커넥션 재사용/재시작에도 누락될 일이 없다. 코드 내 주석(277~283행)도 "새 LIKE 추가 시 이 pragma와 충돌 확인"을 명시해둬 추가 조치 불필요.

**3) `portfolios`의 `"<전략>__reset"/"<전략>__cumulative"` 합성키 — 현재로선 적정, 장기적으로는 재검토 여지**
`make_portfolio_key`/`parse_portfolio_key`(52~93행)가 variant 검증, strategy 내 구분자 금지, 역파싱 폴백까지 갖춰 현재 스키마 안에서는 모호함 없이 잘 동작한다. 다만 한 컬럼에 두 논리 차원(전략, variant)을 인코딩하는 설계라 SQL로 "특정 variant만" 조회/집계하려면 문자열 패턴 매칭이 필요하다는 근본적 한계는 남아있다(코드가 84~89행 TODO로 이미 인지하고 있음). 지금 당장 바꿀 필요는 없다는 판단에 동의한다.

## 구체적 제안
storage.py 142행 바로 아래에 다음 한 줄을 추가:
```
CREATE INDEX IF NOT EXISTS idx_snapshots_timestamp ON snapshots(timestamp);
```
그리고 idx_trades_timestamp(126~128행) 주석과 동일한 톤으로 "prune_snapshots()가 strategy 필터 없이 timestamp만으로 삭제하므로 전체 스캔 방지" 취지의 주석을 붙인다. 기존 IF NOT EXISTS 패턴 그대로라 마이그레이션 위험 없음.

## 리스크/트레이드오프
인덱스 추가는 `add_snapshot()`(INSERT, 1분마다 전략×variant 수만큼)의 쓰기 비용을 B-tree 하나만큼 늘린다. 다만 이미 strategy 복합 인덱스가 있는 테이블에 단독 인덱스 하나 더하는 정도라 쓰기 오버헤드는 미미하고, 하루 1회 전체 스캔 삭제를 인덱스 레인지 스캔으로 바꾸는 이득이 훨씬 크다. (3)의 스키마 변경은 지금 손대지 말 것 — TODO대로 데이터가 쌓인 상태에서 마이그레이션하면 변환 비용/버그 위험이 이득보다 크다.
