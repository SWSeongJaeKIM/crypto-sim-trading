## 한줄 요약
스키마/인덱스, append-only 테이블 보관주기, 동시성(WAL+재시도)은 이전 분석 사이클들을 거치며 이미 상당히 성숙한 상태이고, 이번 회차에서 남은 실질적 개선점은 `prediction_accuracy_by_coin()`의 코인 목록 조회 1곳 정도다.

## 발견한 점 (우선순위 순)

1. **`prediction_accuracy_by_coin()`의 코인 목록 조회가 이미 알고 있는 정보를 다시 풀스캔으로 구함** — `storage.py:676`의 `SELECT DISTINCT coin FROM predictions`는 `lookback_days` 필터가 없어 predictions 전체(코인당 최대 ~13만 행, 최대 90일치)를 매 호출마다 스캔한다(직접 `EXPLAIN QUERY PLAN`으로 확인: `SCAN ... USING COVERING INDEX`, 인덱스 스캔이라 완전 전체 테이블 스캔보다는 가볍지만 여전히 레코드 수에 비례). 그런데 호출부인 `dashboard.py:924`에 바로 두 줄 위에서 `training_coins = ["BTC","ETH","XRP","SOL","DOGE","ADA"]`로 코인 리스트를 이미 들고 있고, 바로 아래(925행)에서 같은 리스트를 `model_training_history_by_coins(conn, training_coins, ...)`에 넘긴다. 그런데 929행의 `storage.prediction_accuracy_by_coin(conn)` 호출만 이 리스트를 재사용하지 않고 내부에서 다시 조회한다. 15초 폴링 핫패스라 조회 수가 아니라 "불필요한 반복 작업"이 누적되는 구조다.

2. **portfolios 합성키(`"<전략>__reset"/"<전략>__cumulative"`) 설계** — 한 컬럼에 두 논리 차원(전략, variant)을 문자열로 인코딩하는 방식이라 원론적으로는 복합 PK(`strategy`, `variant`)가 더 깔끔하다. 다만 이미 코드(`storage.py:44-98`)가 이 부채를 명시적으로 인지하고, 쓰기 시점 검증(`make_portfolio_key`가 variant 오타·`__` 포함 strategy를 즉시 거부)으로 "조용한 오분류" 위험은 이미 차단했으며, 마이그레이션 시 영향 범위(portfolios/trades/snapshots/slot_values 4개 테이블)까지 TODO로 적어뒀다. 지금 데이터 마이그레이션 비용 대비 이득이 작다는 판단은 합리적이다.

3. **동시 쓰기(main_loop)/읽기(dashboard) 충돌** — WAL 모드 + `busy_timeout` + 애플리케이션 레벨 재시도(`_RetryingConnection`) + 예외 시 명시적 rollback의 3중 방어가 이미 되어 있다. 모의투자 특성(실거래 자금 없음)을 고려한 `synchronous=NORMAL` 트레이드오프도 주석에 근거가 명시돼 있다. 이 부분은 추가 조치보다 현 상태 유지가 적절해 보인다.

4. **append-only 테이블 보관주기** — predictions/snapshots/model_trainings/slot_values 모두 `prune_*` 함수가 있고, `main_loop.py:926-969` 쪽에서 일별 1회 실제로 호출되는 것을 확인했다(죽은 코드 아님). trades는 1차 원장이라 삭제하지 않는 의도적 설계이며, 조회 쿼리들(`stop_loss_counts_by_coin`, `simultaneous_stop_events`)에 `lookback_days` 하한을 걸어 폴링 비용 문제도 이미 완화돼 있다.

## 구체적 제안
`storage.py`의 `prediction_accuracy_by_coin(conn, limit_per_coin=500, lookback_days=14)` 시그니처(648행 근처)에 `coins: list[str] | None = None` 파라미터를 추가한다. `coins`가 주어지면 676행의 `SELECT DISTINCT coin FROM predictions` 쿼리를 건너뛰고 그 리스트를 그대로 쓰고, `None`이면 지금처럼 DISTINCT로 폴백한다. 그리고 `dashboard.py:929`를 `storage.prediction_accuracy_by_coin(conn, coins=training_coins)`로 바꿔 924행의 리스트를 재사용한다.

## 리스크/트레이드오프 (제안을 적용하면 생길 수 있는 부작용)
- `coins`를 넘기면 "거래 유니버스에서 빠졌지만 predictions에 잔여 데이터가 남은 과거 코인"이 결과에서 누락될 수 있다 — 기존 DISTINCT 방식과 미묘하게 동작이 달라지므로, `coins=None`일 때의 기존 폴백 동작은 반드시 유지해야 한다.
- `dashboard.py`의 `training_coins`가 `portfolio.COINS`와 별도로 하드코딩돼 있어(두 리스트가 수동 동기화 대상), 코인 유니버스 변경 시 둘 다 고치지 않으면 누락이 생길 수 있다 — 이는 이번 변경이 새로 만드는 리스크가 아니라 기존에 이미 있던 하드코딩 중복이지만, 함께 짚어둘 가치가 있다.
- 실제 대시보드 체감 속도 개선폭은 운영 데이터(코인 수, 누적 행 수)를 봐야 판단 가능하다.
- portfolios 합성키 구조를 지금 당장 바꾸는 것은 권하지 않음 — 이미 문서화된 대로 4개 테이블에 걸친 마이그레이션 비용이 현재 이득보다 크다.
