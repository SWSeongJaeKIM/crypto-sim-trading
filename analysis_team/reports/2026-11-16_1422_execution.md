## 한줄 요약
전반적인 예외 격리와 Upbit API 페이지네이션/레이트리밋 처리는 이미 상당히 견고하게 되어 있으나, LSTM 재학습이 메인 루프를 블로킹하는 구조와 전략 내부 코인 단위 예외 격리 부재, 로그 경로 문제가 남아 있다.

## 발견한 점 (2~4개, 우선순위 순)

1. **LSTM 재학습이 매매 사이클을 완전히 정지시킴** — `local/main_loop.py` 433~446행. `while not _stop` 루프 안에서 `retrain_is_due()`가 True면 `retrain_lstm()`을 동기적으로 호출하고, 이 함수가 끝나야 다음 사이클(60초 슬립)로 넘어간다. `retrain_lstm()`은 6코인 × 90일치 1분봉 수집(페이지 수백 회)과 8epoch 학습을 포함하므로 실행 시간이 수분~십수분에 달할 수 있다. 하루 10회(RETRAIN_TIMES_LOCAL) 이 구간 동안은 `run_one_cycle()`이 전혀 돌지 않아 그 시간 동안 시세 수집·신호 계산·매매가 완전히 멈춘다. DB 락 문제는 이미 "매번 짧게 connect" 방식으로 해결했지만, 그와 별개로 "재학습 중 매매 루프 자체가 멈추는" 문제는 남아있다.

2. **전략 내부에서 코인 단위 예외 격리가 없음** — `local/main_loop.py` 268~334행. 전략(strategy) 단위로는 try/except로 격리되어 있어 한 전략의 실패가 다른 전략의 commit을 해치지 않는다(주석에 설명됨, 좋은 설계). 하지만 283~297행의 "코인별 신호 계산" 루프는 그 바깥의 전략 단위 try/except에만 걸려있어, 코인 세분화된 try/except가 없다. 예를 들어 `lstm_predictor`에서 ADA 모델 파일이 손상되어 `predict_proba`나 `signal_with_confidence`에서 예외가 나면, 이미 신호를 계산한 BTC/ETH 등 나머지 5개 코인의 매매까지 이번 사이클에서 전부 스킵된다(331행에서 전체 strat_name에 대해 continue).

3. **run.log 경로가 실행 디렉토리에 의존함** — `local/main_loop.py` 60행 `logging.FileHandler("run.log", ...)`가 상대경로다. 반면 77행 `HEARTBEAT_PATH = Path(__file__).parent / "heartbeat.txt"`는 의도적으로 절대경로로 고정해두었다. 만약 watchdog.bat나 OS 서비스 등록이 `local/`이 아닌 다른 작업 디렉토리에서 프로세스를 띄우면, 모듈 docstring(20행: "로그는 콘솔과 local/run.log에 같이 남는다")과 달리 실제 로그 파일이 엉뚱한 위치에 생겨 문제 진단 시 로그를 못 찾을 수 있다.

## 구체적 제안

- (1) `retrain_lstm()` 호출을 별도 스레드/프로세스로 분리하거나, 최소한 재학습 도중에도 `run_one_cycle()`이 계속 돌 수 있도록 메인 while 루프 구조를 재학습 작업(백그라운드)과 사이클 작업(60초 주기)으로 분리하는 것을 검토. 간단한 완화책으로는 재학습을 별도 `threading.Thread`로 띄우고 메인 루프는 그대로 60초 사이클을 계속 돌리는 방식.
- (2) `local/main_loop.py` 283~297행의 `for coin, df in candles.items():` 블록 안쪽에 코인별 try/except를 추가해, 한 코인에서 예외가 나도 `continue`로 다음 코인은 계속 처리되게 함.
- (3) `local/main_loop.py` 60행을 `logging.FileHandler(Path(__file__).parent / "run.log", encoding="utf-8")`로 변경.

## 리스크/트레이드오프

- (1) 재학습을 별도 스레드로 분리하면 학습이 GPU/CPU를 점유하는 동안 매매 사이클과 리소스를 경합하게 되어 사이클 자체가 느려질 수 있고, `storage.connect()` 동시 접근이 늘어나 "database is locked" 재발 가능성을 다시 검토해야 한다(주석에 이미 이 이슈를 겪은 기록이 있음).
- (2) 코인별 try/except를 추가하면 코드량이 늘고 로그가 코인 단위로 더 자주 찍혀 다소 번잡해질 수 있음.
- (3) 로그 경로 변경은 리스크가 거의 없으나, 기존에 상대경로로 쌓인 run.log를 참조하던 외부 스크립트(watchdog.bat 등)가 있다면 경로를 함께 맞춰줘야 함.
- 재학습 주기나 실제 운영 중 모델 손상 빈도 등은 실제 운영 데이터를 봐야 판단 가능.
