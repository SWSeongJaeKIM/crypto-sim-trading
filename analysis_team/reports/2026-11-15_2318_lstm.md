## 한줄 요약
LSTM 파이프라인은 데이터 양·재학습 주기·모델 용량 측면에서 전반적으로 무리 없게 설계되어 있으나, train/val 분할 방식 때문에 검증 정확도(`val_accuracy`)가 실제보다 낙관적으로 보일 수 있는 구조적 문제가 가장 시급하다.

## 발견한 점 (우선순위 순)

1. **train/val 분할에 시퀀스 윈도우 겹침(leakage)** — `local/lstm_model.py` 129~132번 줄. `X, y`는 60분 슬라이딩 윈도우로 만들어지는데, `split = int(n * (1 - val_frac))`로 그냥 인덱스로 자르면 `X_train`의 마지막 몇 개와 `X_val`의 첫 몇 개가 최대 59분치 입력을 공유한다. 즉 검증 세트가 학습 세트와 거의 같은 데이터를 보고 평가되는 셈이라, `val_accuracy`(170번 줄, 대시보드에 "정확도 추이"로 표시됨)가 실제 일반화 성능보다 부풀려질 가능성이 높다.

2. **"파인튜닝"이 사실상 매일 30일 전체 데이터 재학습 + 웜스타트** — `local/main_loop.py` 271번 줄에서 매일 `history_days=30`로 받아온 데이터 전체를 다시 학습시키고, `lstm_model.py` 137~138번 줄에서 기존 가중치만 이어받는다. 즉 "최근 패턴만 추가 학습"하는 방식이 아니라 거의 동일한(29일이 겹치는) 데이터셋을 매일 8 epoch씩 다시 돌리는 것에 가깝다. 망각 문제보다는 "거의 같은 데이터로 반복 학습해서 얻는 추가 이득이 적을 수 있다"는 점이 더 실제적인 이슈다.

3. **피처에 변동성/가격범위 정보가 빠져 있음** — `FEATURE_COLS`(41번 줄)는 수익률·거래량변화·RSI·MACD·%b만 있고, OHLCV에서 바로 뽑을 수 있는 캔들 범위(고가-저가) 정보가 없다. 호가 스프레드나 타코인 상관관계는 데이터 소스상 당장 추가하기 어렵지만, high/low는 이미 `df`에 있으므로 추가 비용 없이 변동성 신호를 넣을 수 있다.

4. (참고, 문제 아님) `SEQ_LEN=60` + `hidden=32, layers=1`의 작은 모델 용량은 노이즈가 큰 1분봉 데이터에 비춰 과적합을 억제하는 합리적 선택으로 보이고, 30일치 데이터량과 하루 1회 재학습 주기도 1분봉 예측 과제 대비 과도하거나 부족하지 않은 수준이다.

## 구체적 제안

- **(1 대응)** `lstm_model.py` 129~132번 줄을 `split = int(n * (1 - val_frac))` 뒤에 `gap = seq_len`을 두고 `X_val, y_val = X[split + gap:], y[split + gap:]`로 바꿔, train 마지막 샘플과 val 첫 샘플 사이에 최소 `seq_len`만큼 간격을 둔다. 이렇게 하면 두 세트가 같은 원본 캔들을 공유하지 않는다.
- **(2 대응)** `main_loop.py`의 `retrain_lstm` 호출부(271번 줄)에서 요일 등을 기준으로 주 1회는 `finetune=False`를 넘겨 처음부터 재학습하도록 분기를 추가하면, 웜스타트가 특정 국면에 고착되는 것을 주기적으로 리셋할 수 있다.
- **(3 대응)** `build_features`(58~64번 줄)에 `"hl_range": (df["high"] - df["low"]) / close` 한 줄을 추가하고 `FEATURE_COLS`에 포함시킨다.

## 리스크/트레이드오프

- 제안 1(gap 추가)은 유효 검증 샘플 수를 줄여, 데이터가 적은 코인은 `len(X) < 500` 임계값(121번 줄)에 더 쉽게 걸려 학습이 스킵될 수 있다.
- 제안 2(주1회 전체 재학습)는 그날 학습 시간이 늘어나고, 초기화된 가중치가 바로 최적점에 도달하지 못해 해당 날짜의 신호 품질이 일시적으로 떨어질 수 있다.
- 제안 3(피처 추가)은 `N_FEATURES`가 바뀌므로 기존에 저장된 `models/{coin}_lstm.pt`를 `load_state_dict`로 불러올 때 shape 불일치로 에러가 날 수 있다 — 적용 시 기존 모델 파일을 삭제하고 처음부터 재학습해야 한다.
- 실제 정확도/수익성이 이 변경들로 어떻게 바뀔지는 운영 데이터를 봐야 판단 가능한 부분이며, 코드 구조만으로는 확정할 수 없다.
