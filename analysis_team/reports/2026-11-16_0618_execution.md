## 한줄 요약
전체적으로 예외처리와 재시작 복원력은 양호하나, 로깅 경로 불일치와 사이클 타이밍 드리프트, LSTM 모델 부분 누락 시의 복구 로직에 개선 여지가 있다.

## 발견한 점 (2~4개, 우선순위 순)

1. **로깅 경로 불일치 (data_fetcher.py 120, 139, 153)**: `main_loop.py`는 `logging` 모듈을 사용해 콘솔+`run.log` 파일에 동시 기록하지만, `data_fetcher.py`의 실패 경고는 전부 `print()`다. `main_loop.py` 상단 docstring(20번째 줄)은 "로그는 콘솔과 run.log에 같이 남는다"고 명시하는데, 코인별 수집 실패/히스토리 수집 실패 같은 실제로 가장 중요한 진단 정보가 `run.log`에는 남지 않는다. 서비스로 등록해 stdout이 별도 리다이렉트되지 않는 환경이면 이 경고들이 완전히 사라질 수 있다.

2. **사이클 주기 드리프트 (main_loop.py 319-340)**: `run_one_cycle` 실행 시간을 측정하지 않고, 끝난 뒤 무조건 `CYCLE_INTERVAL_SEC(60)`초를 그대로 sleep한다(337-340줄). 즉 실제 사이클 주기는 "60초 + 해당 사이클 처리 시간(API 호출/학습 등)"이 되어 고정 60초가 아니다. `fetch_latest_minute_candles`가 매번 "최신" 캔들을 가져오므로 데이터 손실은 없지만, 하루 동안 실행되는 매매 판단 횟수가 설계 의도보다 체계적으로 줄어든다. 특히 재학습(retrain_lstm)이 끼는 사이클은 수 분 걸릴 수 있어 그 사이클만 큰 공백이 생긴다.

3. **LSTM 모델 부분 누락 시 초기학습 트리거 로직 (main_loop.py 307)**: `has_any_model = any(...)`이므로 6개 코인 중 1개라도 모델 파일이 존재하면 `not has_any_model`이 False가 되어 초기학습을 건너뛴다. "하나도 없으면"이라는 주석 의도상 any()가 맞지만, 과거 학습이 중간에 실패해 일부 코인만 모델이 생성된 상태로 재시작되면, 나머지 코인은 다음 날 정기 재학습(RETRAIN_HOUR_LOCAL)까지 모델 없이 방치된다.

## 구체적 제안

- **main_loop.py 319-340**: 사이클 시작 시각을 `t0 = time.monotonic()`으로 기록하고, 끝난 뒤 `elapsed = time.monotonic() - t0`, `sleep_for = max(0, CYCLE_INTERVAL_SEC - elapsed)`로 바꿔 그 값만큼만 sleep. `elapsed > CYCLE_INTERVAL_SEC`이면 `log.warning(f"사이클 처리 {elapsed:.1f}초로 60초 초과 — 지연 발생")` 추가.
- **data_fetcher.py**: 상단에 `import logging; log = logging.getLogger("data_fetcher")` 추가하고 117-121, 138-139, 152-153줄의 `print(f"[WARN] ...")`를 `log.warning(...)`으로 교체. `main_loop.py`가 이미 root logger에 `FileHandler`+`StreamHandler`를 등록하므로(53-57줄) 모듈만 바꾸면 자동으로 `run.log`에도 남는다. 단, 단독 실행(157-161줄 `__main__`) 시에는 `if __name__ == "__main__":` 블록 앞에 `logging.basicConfig(level=logging.INFO)` 한 줄 추가 필요.
- **main_loop.py 307 부근**: `has_any_model`을 코인별로 나눠 `missing = [c for c in COINS if not (lstm_model.MODEL_DIR / f"{c}_lstm.pt").exists()]`로 바꾸고, 누락 코인이 있으면 로그로 명시적으로 알리는 정도로 보완.

## 리스크/트레이드오프

- 사이클 타이밍을 "경과시간 차감" 방식으로 바꾸면, 처리 시간이 60초를 넘는 상황이 반복될 경우 사이클 간격이 좁아져 Upbit API 호출이 빡빡해질 수 있다.
- `data_fetcher.py`를 `logging`으로 바꾸면 root logger 설정에 의존하게 되어, 단독으로 임포트하는 다른 스크립트에서 `basicConfig` 호출이 없으면 경고가 조용히 사라질 수 있다.
- 모델 누락 감지를 "즉시 재학습"까지 확장하면, 재시작이 반복되는 환경에서 매번 전체 학습 파이프라인이 돌아 PC 리소스를 과도하게 쓸 위험이 있다 — 알림 수준에서 멈추는 것이 안전하다.
