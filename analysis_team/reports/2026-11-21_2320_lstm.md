## 한줄 요약
피처 구성과 모델 크기, 파인튠 안전장치는 문제 난이도(1분봉 방향 예측)에 맞게 이미 신중하게 설계되어 있고, 남은 개선 여지는 "다른 코인 상관관계" 피처 추가와 파인튠 체인 자동 리셋 정책 부재 두 가지입니다.

## 발견한 점 (2~4개, 우선순위 순)

1. **재학습 주기/데이터 기간이 과제 배경과 다름**: 실제 코드(주석 18-20행, `HISTORY_DAYS_FOR_TRAIN`)는 "하루 1회, 30일"이 아니라 하루 10회(약 2시간24분 간격), 90일 히스토리 윈도우를 사용합니다. 이렇게 겹치는 윈도우를 자주 재학습하면 "오늘 들어온 새 데이터"의 비중이 구조적으로 작아지는 문제를 코드 주석(152-158행)이 이미 인지하고 `finetune_lr = lr/3`으로 완화해둔 상태입니다 — 적절한 대응입니다.

2. **FEATURE_COLS(71행)가 전부 단일 코인의 자기 OHLCV 파생치뿐**: ret, vol_chg, rsi14, macd_hist, bb_pctb 모두 해당 코인 자신의 가격/거래량에서만 나옵니다. 호가 스프레드는 Upbit 1분봉 캔들 데이터 구조상 애초에 없을 가능성이 높아 이건 자료 한계 쪽이지만, "다른 코인(특히 BTC)과의 동시 수익률" 같은 상대적 모멘텀 피처는 추가 가능한데 빠져 있습니다. 알트코인 1분 방향은 BTC 추종 성향이 커서 이 정보가 누락된 채 예측하는 것은 아쉬운 지점입니다.

3. **모델 구조/SEQ_LEN은 문제 난이도에 비해 적절히 작음**: 1층 LSTM(hidden=32) + SEQ_LEN=60은 val_accuracy 54~62%(주석 52행)라는 거의 랜덤에 가까운 과제 특성을 감안하면 과대 용량이 아니고, 과적합보다는 오히려 피처 부족 쪽이 성능 상한을 제한하고 있을 가능성이 큽니다. 임계값을 0.60/0.40으로 올려 과매매를 줄인 조치(60행)도 실측 문제(166건 과매매, 3배 레버리지 손익 악화)에 대한 합리적 대응으로 보입니다.

4. **파인튠 체인 길이(`finetune_chain_length`)는 추적되지만 자동 리셋 정책이 없음**: 240-266행 주석에서 이미 "전체 재학습이 언제 일어났는지 호출부가 알 방법이 없다"는 점을 인지하고 메타데이터만 추가했다고 명시되어 있습니다. 즉 가중치가 영구 파인튠으로 과거 패턴에 고착(stale)될 위험을 관측은 하지만 자동 대응은 아직 없는 알려진 미해결 지점입니다.

## 구체적 제안
- `build_features` (75-95행)에 선택적 파라미터로 `market_df`(예: BTC 1분봉)를 받아 `market_ret = market_df["close"].pct_change()` 피처를 FEATURE_COLS에 추가 (`FEATURE_COLS`를 71행에서 `["ret", "vol_chg", "rsi14", "macd_hist", "bb_pctb", "market_ret"]`로 확장). BTC 자신에 대해서는 이 피처를 0 또는 생략 처리.
- `train_model`이 반환하는 `finetune_chain_length`(296행)를 `main_loop.py` 호출부에서 읽어, 예를 들어 30(3일치, 하루 10회 기준) 이상이면 다음 호출 시 `finetune=False`를 넘겨 전체 재학습을 강제하는 로직을 추가.

## 리스크/트레이드오프
- BTC 상관 피처 추가는 데이터 파이프라인에 멀티코인 동기화 의존성을 만들어, BTC 데이터 결측/지연 시 NaN 전파 위험이 생기고 학습 코드 복잡도가 늘어남.
- 체인 길이 기반 자동 전체 재학습은 트리거 시점에 그동안 쌓인 파인튠 효과를 버리므로, 변동성이 큰 시점에 초기화되면 일시적으로 더 나쁜 가중치가 실거래 신호로 배포될 수 있음. `VAL_ACC_ROLLBACK_THRESHOLD` 안전망이 전체 재학습 직후 결과에도 똑같이 적용되는지 확인 필요.
- (참고) 실제 val_accuracy 추이, 임계값 상향 이후 거래 건수/손익 변화 여부는 실제 운영 데이터를 봐야 판단 가능하여 이 리포트에서는 다루지 않았습니다.
