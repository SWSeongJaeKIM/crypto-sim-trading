## 발견한 점 (2~4개, 우선순위 순)

1. **retention 미구현** — `db_file_size_mb()` (67~75행)는 "DB가 커졌는지 사람이 보는" 관측용 헬퍼일 뿐, `predictions`/`model_trainings`/`trades`/`snapshots`를 실제로 줄이는 코드는 파일 전체에 없다. `add_prediction`(362행)은 매 사이클·코인마다 1행씩 쌓이므로(1분봉 기준 하루 코인당 1440행), 수개월 운영 시 `predictions` 테이블이 가장 빠르게 커질 테이블이다. 인덱스가 잘 잡혀 있어 조회 성능은 당장 괜찮지만, 파일 크기·백업 시간·WAL 체크포인트 비용은 계속 늘어난다.

2. **`make_portfolio_key`에 variant 검증 없음 (51~54행)** — `parse_portfolio_key`(57~64행)는 variant가 `"reset"`/`"cumulative"` 둘 중 하나가 아니면 전체 키를 strategy로, variant는 무조건 `"cumulative"`로 취급해버린다. 그런데 `make_portfolio_key`는 호출 시 variant 값을 전혀 검증하지 않아서, 향후 호출부에 오타(`"reste"`)나 새 variant(`"paper"` 등)가 들어오면 쓰기 시점엔 조용히 성공하고, 읽기 시점(`parse_portfolio_key`)에서 조용히 다른 전략 데이터로 잘못 라벨링된다 — 즉시 에러가 아니라 조용한 데이터 오분류로 이어지는 정합성 리스크다.

3. **인덱스/쿼리 패턴 — 이미 잘 돼 있음.** `trades`/`model_trainings`/`predictions` 모두 "필터 있는 조회"와 "필터 없는 전체 조회(dashboard)" 두 경로를 각각 커버하는 복합 인덱스가 이미 존재한다(94~154행 주석에 이전 리뷰 근거 명시). 추가로 손댈 필요 없음.

4. **동시 쓰기/읽기 — 이미 잘 돼 있음.** WAL 모드 + `busy_timeout` + 애플리케이션 레벨 재시도(`_RetryingConnection`, 187~204행) + 예외 시 명시적 rollback(236행)까지 갖춰져 있어, main_loop와 dashboard의 동시 접근으로 인한 "database is locked"는 이미 다층 방어되어 있다.

## 구체적 제안

- `/home/claude/crypto-sim-trading/local/storage.py` 420행(파일 끝) 근처에 prune 함수 추가:
```python
def prune_predictions(conn, keep_days: int = 30) -> int:
    cur = conn.execute(
        "DELETE FROM predictions WHERE resolved=1 AND predicted_at < datetime('now', ?)",
        (f"-{keep_days} days",),
    )
    return cur.rowcount
```
  `model_trainings`/`snapshots`도 같은 패턴으로 추가하고, main_loop.py 쪽에서 `db_file_size_mb()` 값이 임계치(예: 200MB)를 넘을 때만 호출하도록 연결.

- 51~54행 `make_portfolio_key`에 `if variant not in ("reset", "cumulative"): raise ValueError(...)` 추가하여 오타/새 variant를 쓰기 시점에 즉시 실패시킨다.

(참고: `trading.db`의 실제 현재 크기·증가 속도는 실제 운영 데이터를 봐야 판단 가능하며 이 리뷰에서는 코드 구조상의 가능성만 지적함.)

## 리스크/트레이드오프

- `prune_predictions` 삭제는 과거 적중률 추이 분석(모델 성능 회귀 비교)용 원본 데이터를 영구히 잃게 한다 — `keep_days`를 충분히 크게 잡거나, 삭제 전 코인·일자별 집계 요약 테이블에 롤업 후 원본만 지우는 방식을 권장.
- `make_portfolio_key`에 검증을 추가하면, 혹시 호출부(main_loop.py/dashboard.py)가 이미 `"reset"`/`"cumulative"` 외 값을 쓰고 있었다면 배포 즉시 예외가 터진다 — 적용 전 두 파일에서 `make_portfolio_key(` 호출 지점을 먼저 grep해 확인 필요.
- 자동 prune을 DB 크기 임계치 기반으로 트리거할 경우, main_loop가 쓰기 중인 타이밍과 겹치면 대량 DELETE가 오히려 락 경합을 늘릴 수 있다 — 재학습 직후 등 쓰기 빈도가 낮은 시점에 실행하거나 `LIMIT`로 쪼개서 삭제하는 것이 안전하다.
