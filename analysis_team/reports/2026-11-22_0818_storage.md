## 한줄 요약
스키마/인덱스, append-only 테이블 보관주기(prune), 동시 쓰기/읽기 충돌 방지는 과거 분석팀 제안이 이미 충실히 반영되어 안정적인 상태이고, 남은 것은 portfolios 합성키의 장기 스키마 개선 여지와 trades 테이블의 보관정책 미결정 정도다.

## 발견한 점 (우선순위 순)

1. **(확인됨, 이미 잘 돼 있음) 쿼리 패턴 대응 인덱스**: trades(strategy+timestamp, timestamp 단독, reason), snapshots(strategy+timestamp), model_trainings(coin+timestamp, timestamp 단독), predictions(coin+resolved+시간, resolved+시간, resolved+coin+시간) 모두 실제 WHERE/ORDER BY/PARTITION BY 패턴과 정확히 맞물려 있다(storage.py 116~191줄). WHERE 없는 전체 스캔처럼 보이는 `get_all_portfolios`(294~296줄)와 `prediction_accuracy_by_coin`의 `SELECT DISTINCT coin`(537줄)은 대상 행/값 수 자체가 적어(전략 수, 코인 종류 수 모두 한 자릿수~수십) 실질적 성능 문제는 아니다.

2. **(확인됨, 이미 잘 돼 있음) append-only 테이블 보관주기**: predictions(90일, resolved=1만), snapshots(365일), model_trainings(365일, trained=0 실패기록만)에 대해 `prune_*` 함수가 구현돼 있고, `main_loop.py` 754~763줄에서 실제로 호출됨을 확인했다. 성공한 학습 기록(trained=1)은 영구 보존해 "모델 성능 추이" 목적과 충돌하지 않도록 한 것도 적절한 설계다.

3. **(미결정 상태, 코드 결함 아님) trades 테이블에는 prune이 없다.** 실거래 발생 시에만 쌓여 predictions보다 증가 속도가 훨씬 느리지만 무기한 누적은 동일하다. "거래 감사기록을 몇 년 보존할지"는 사람이 먼저 정책을 정해야 하는 사안이라 과거에도 보류됐고 지금도 그대로다.

4. **동시성(connect(), 224~286줄)**: WAL + busy_timeout + 애플리케이션 레벨 재시도(`_RetryingConnection`) + 예외 시 명시적 rollback으로 "database is locked" 경합을 다층으로 방어하고 있어, main_loop(쓰기)/dashboard(읽기) 동시 접근 설계는 안정적이다.

## 구체적 제안
- **portfolios 합성키(44~86줄)**: `make_portfolio_key`/`parse_portfolio_key`로 조립·역파싱을 한 곳에 모으고 variant 검증 및 "__" 포함 strategy 거부까지 추가돼 있어 현재 수준에서는 안전하다. 실제 PK 마이그레이션 없이 더 나아가려면, `set_portfolio()`(299~304줄) 안에서 `parse_portfolio_key(strategy)`로 얻은 strategy_name/variant를 `ALTER TABLE portfolios ADD COLUMN strategy_name TEXT, ADD COLUMN variant TEXT`로 추가한 두 컬럼에 같이 써 넣는 방식을 권장한다. 기존 PK(strategy)는 그대로 둬 하위 호환을 유지하면서, 향후 "변동 모드(variant)별로만 필터링" 같은 쿼리가 필요해지면 문자열 분해 없이 바로 `WHERE variant=?`를 쓸 수 있다.
- **trades 보관정책(현재 없음)**: `prune_snapshots`(464~481줄)와 동일 패턴으로 `prune_trades(conn, keep_days=...)`를 추가할 수 있으나, keep_days 값은 "거래 감사기록을 몇 년 보존할지"를 사람이 먼저 정해야 하므로 코드만으로 결정하지 않는다.

## 리스크/트레이드오프
- portfolios에 strategy_name/variant 컬럼을 추가하면 저장 공간과 쓰기 비용이 소폭 늘고, 기존 행에는 NULL이 남아 백필 스크립트(UPDATE로 파싱 결과 채우기)를 한 번 돌려야 한다. 이는 과거 리포트(2026-11-21_2221)가 우려한 "PK 자체를 바꾸는 마이그레이션"보다는 훨씬 가벼운 리스크다.
- prune_trades를 도입하면 과거 전체 거래 기록이 필요해지는 장기 성과 재분석(예: 손절 패턴 연간 비교)이 불가능해질 수 있어, keep_days를 보수적으로 길게 잡거나 삭제 전 CSV 아카이브를 권장한다.
- 실제로 predictions/trades가 지금 몇 행이나 쌓여 있는지, 90일/365일이 충분한지는 운영 데이터를 봐야 판단 가능 — 이 리포트만으로는 결정할 수 없다.
