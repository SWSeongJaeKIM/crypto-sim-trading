## 한줄 요약
전반적인 예외처리 구조(사이클 단위 try/except, 코인별 개별 try/except)는 잘 설계되어 있으나, 최초 LSTM 학습 구간의 예외처리 누락과 data_fetcher의 일부 예외 미포착/로깅 공백이 복구력을 약화시킬 수 있다.

## 발견한 점 (2~4개, 우선순위 순)

1. **최초 1회 LSTM 학습에 예외처리가 없음** — `main_loop.py` 307~310행: `has_any_model`이 False일 때 호출하는 `retrain_lstm(conn)`이 try/except로 보호되지 않는다. 같은 함수가 while 루프 안에서 재학습될 때는 326~331행에서 `try/except Exception`으로 감싸져 있는데, 시작 시점의 최초 학습만 보호가 빠져 있다. 네트워크 타임아웃이나 Upbit 응답 문제로 `fetch_all_minute_history`가 실패하면 프로그램 전체가 `main()` 밖으로 예외를 던지며 종료된다.

2. **data_fetcher의 재시도 로직이 JSON 파싱 오류를 못 잡음** — `data_fetcher.py` 46~56행 `_http_get_json`의 except 튜플은 `(urllib.error.URLError, urllib.error.HTTPError, TimeoutError)`만 잡는다. `json.loads()`가 던지는 `json.JSONDecodeError`(예: Upbit이 에러 HTML/빈 바디를 반환하는 경우)는 이 튜플에 없어 재시도 없이 즉시 예외가 전파되고, 호출부의 `except FetchError`로도 잡히지 않는다.

3. **data_fetcher.py가 logging 모듈 대신 print()를 사용** — 120, 139, 153행의 수집 실패 경고가 모두 `print()`다. `main_loop.py`의 `logging.FileHandler("run.log")`는 logging 호출만 파일에 남기므로, 서비스로 등록되어 콘솔 출력이 캡처되지 않는 환경에서는 코인별 수집 실패 경고가 run.log에 전혀 남지 않는다.

4. **사이클 주기가 "작업시간 + 60초"로 누적됨** — `main_loop.py` 337~340행에서 사이클 처리 시간과 무관하게 매번 60초를 추가로 대기한다. 실제 주기는 고정 60초가 아니라 `처리시간+60초`이며, 재시도 백오프 등으로 처리시간이 늘어나면 실행 시점이 매분 경계에서 서서히 멀어진다. 치명적이지 않지만 타이밍 정합성에는 영향.

## 구체적 제안

- `main_loop.py` 307~310행을 `try: retrain_lstm(conn) except Exception as e: log.exception(...)`로 감싸고, 실패 시 `has_any_model`은 False로 남겨두되 while 루프는 정상 진입시킨다(재학습 재시도는 326행의 `retrain_is_due` 로직이 다음날까지는 다시 안 돌 수 있으므로, 실패 플래그를 두고 다음 사이클에서 바로 재시도하도록 보완 고려).
- `data_fetcher.py` 53행의 except 튜플에 `json.JSONDecodeError`(또는 `ValueError`)를 추가해 `(urllib.error.URLError, urllib.error.HTTPError, TimeoutError, json.JSONDecodeError)`로 확장한다.
- `data_fetcher.py` 상단에 `import logging; log = logging.getLogger("data_fetcher")`를 추가하고 120/139/153행의 `print(...)`를 `log.warning(...)`로 교체한다(루트 로거 설정은 main_loop.py가 이미 하므로 파일 핸들러에 자동 포함됨).
- `main_loop.py` 319행 while 루프 시작에 `cycle_start = time.monotonic()`을 두고, 337행 전에 `elapsed = time.monotonic() - cycle_start`, `sleep_for = max(0, CYCLE_INTERVAL_SEC - elapsed)`로 바꿔 남은 시간만 1초 단위로 대기시킨다.

## 리스크/트레이드오프

- 1번 제안: 재학습이 반복 실패하면 while 루프가 매일 같은 시도를 반복하며 에러 로그가 누적될 수 있음 — 다만 기존에도 일간 재학습 실패는 동일하게 로그만 남기고 계속 도는 구조라 일관성은 유지됨.
- 2번 제안: 예외 포착 범위를 넓히면 진짜 파싱 버그(응답 스키마 변경 등)도 "재시도 후 실패"로 뭉뚱그려질 수 있음 — 다만 재시도는 3회로 제한되어 있어 결국 `FetchError`로 드러나므로 디버깅 난이도가 크게 늘지는 않음.
- 4번 제안: 처리 시간이 60초를 넘기면 `sleep_for=0`이 되어 곧바로 다음 사이클이 시작되고 Upbit 호출 빈도가 순간적으로 높아질 수 있음 — overrun 발생 시 경고 로그를 남기는 처리를 함께 추가하는 것을 권장.
- 실제 운영 환경에서 재학습 실패가 얼마나 자주 발생했는지, 사이클 지연이 실측으로 몇 초/분 수준인지는 로그/운영 데이터를 봐야 판단 가능하며 이 분석에서는 코드 구조만으로 가능성만 짚었다.
