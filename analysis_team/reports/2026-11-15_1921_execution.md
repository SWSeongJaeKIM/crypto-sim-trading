## 한줄 요약
전반적인 예외처리 구조는 양호하나(사이클 전체를 감싸는 try/except, 코인별 폴백), 최초 구동 시 학습 호출이 보호되지 않는 지점과 사이클 간격이 고정 60초가 아니라 "처리시간+60초"로 누적되는 구조가 실행 안정성 측면의 핵심 리스크다.

## 발견한 점 (2~4개, 우선순위 순)

1. **(높음) 최초 1회 학습 호출이 try/except 밖에 있음** — `main_loop.py` 275~278번 줄: `has_any_model`이 False일 때 호출하는 `retrain_lstm(conn)`은 while 루프 안의 재학습 호출(289~293번 줄, try/except로 보호됨)과 달리 보호되지 않은 상태로 호출된다. 이 시점에 네트워크 장애나 Upbit API 오류(`fetch_minute_history`가 `FetchError`를 던지고 캐시도 없는 경우 등)가 나면 프로세스 전체가 즉시 죽고, PC에 상주시켜 둔 서비스가 재시작 전까지 완전히 멈춘다.

2. **(높음) 사이클 주기가 고정 60초가 아니라 "처리시간 + 60초"로 매 사이클 늘어남** — `main_loop.py` 299~302번 줄: `run_one_cycle` 실행이 끝난 뒤 조건 없이 `for _ in range(CYCLE_INTERVAL_SEC): time.sleep(1)`을 수행한다. 즉 실제 사이클 간격은 "`run_one_cycle` + `retrain_lstm`(해당 시간대) 소요시간 + 60초"가 되어, 1분봉 수집 주기라는 설계 의도(주석 41번 줄)와 점점 어긋난다. API 재시도(`_http_get_json`의 backoff)가 자주 발생하거나 재학습이 겹치는 시간대일수록 실제 틱 간격이 벌어지고, 벌어진 만큼 영구히 복구되지 않는다(보정 로직 없음).

3. **(중간) data_fetcher.py의 경고 로그가 파일에 남지 않음** — `data_fetcher.py` 120, 139, 153번 줄: 코인별 수집 실패 시 `print()`를 사용하는데, `main_loop.py`의 `logging.FileHandler("run.log")`는 `logging` 모듈 호출만 캡처하므로 이 경고들은 콘솔에만 보이고 `run.log`에는 남지 않는다. 운영 PC를 직접 보고 있지 않을 때는 어느 코인이 왜 실패했는지 로그 파일만으로 추적할 수 없다.

4. **(낮음) 코인별 예외 격리 수준이 일관되지 않음** — `fetch_all_latest_candles`(data_fetcher.py 113~121번 줄)는 `FetchError`만 코인 단위로 잡는다. `_parse_minute_df`나 JSON 파싱 과정에서 `FetchError`가 아닌 예외(예: 응답 포맷이 예상과 다를 때의 `KeyError`/`JSONDecodeError`)가 나면 한 코인 문제로 전체 사이클이 중단된다(상위 `main()`의 try/except가 받아서 사이클만 스킵하므로 치명적이진 않지만, 의도는 "코인별 격리"인데 실제로는 부분적으로만 격리됨).

## 구체적 제안
- `main_loop.py` 276~278번 줄을 `try: retrain_lstm(conn) / except Exception as e: log.exception(...)`로 감싸 while 루프 안의 패턴과 동일하게 맞춘다.
- `main_loop.py`의 사이클 대기 로직을 시작 시각 기록 방식으로 바꾼다: `cycle_start = time.monotonic()` 후 `run_one_cycle`/재학습 실행, `elapsed = time.monotonic() - cycle_start`, `sleep_time = max(1, CYCLE_INTERVAL_SEC - elapsed)`만큼만 대기.
- `data_fetcher.py` 상단에 `logging.getLogger("data_fetcher")`를 만들고 120, 139, 153번 줄의 `print`를 `log.warning`으로 교체(또는 main_loop의 로거를 재사용).

## 리스크/트레이드오프
- 초기 학습 호출을 try/except로 감싸면 모델 파일이 끝까지 생성되지 않는 채로 매매 사이클이 계속 돌 수 있다. `lstm_model.py`가 모델 부재 상황을 안전하게 처리하는지는 이번 분석 범위(지정된 2개 파일) 밖이라 별도 확인이 필요하다.
- 사이클 보정 로직 적용 시 처리시간이 60초를 넘으면 `sleep_time`이 0에 가까워져 API 호출이 연속으로 몰릴 수 있으므로 최소 대기(예 1~2초)를 보장해야 한다.
- `print`를 `logging`으로 바꾸면 `run.log` 파일 크기가 더 빨리 커진다. 현재 로그 로테이션 설정이 없다면(코드상 미확인) 별도로 고려해야 한다.

(실제로 현재 PC에서 재학습이 얼마나 자주 실패하거나 사이클이 얼마나 지연되고 있는지는 운영 로그를 봐야 판단 가능하며, 이번 분석은 코드 구조만으로 판단한 것이다.)
