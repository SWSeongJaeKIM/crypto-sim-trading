## 한줄 요약
인덱스·보관주기·동시성(WAL+재시도)·portfolios 합성키 검증 등 기존에 지적됐던 문제들은 이미 대부분 코드에 반영되어 있고 구조적으로 안정적이다. 다만 `predictions` 테이블에서 "영구 미확정(resolved=0)" 행이 보관주기 없이 무한 누적될 수 있는 경로가 하나 남아 있다.

## 발견한 점 (우선순위 순)

1. **`predictions`의 미확정(resolved=0) 행이 영구 축적될 수 있음** (storage.py:420-444, 447-461)
   `resolve_predictions()`는 `current_prices_krw`에 코인이 없으면 그냥 `continue`해서 해당 행을 `resolved=0`으로 남긴다. 코인이 거래 유니버스에서 빠지거나(상장폐지, 설정 변경) 가격 피드가 영구적으로 끊기면 그 코인의 예측 행들은 영원히 미확정 상태로 남는다. 그런데 `prune_predictions()`(447~461행)는 `WHERE resolved = 1`인 행만 지우므로, 이런 "고아 미확정" 행은 보관주기 적용 대상에서 완전히 빠져 DB가 서서히 무한정 커질 수 있다.

2. **`portfolios` 합성키 설계는 write-time 검증으로 충분히 보강됐음 — "이미 잘 돼 있음"**
   `make_portfolio_key`/`parse_portfolio_key`(52~86행)가 variant 화이트리스트 검사와 strategy 내 구분자(`__`) 금지 검사를 쓰기 시점에 수행해, 애초 우려였던 "조용한 오분류" 가능성을 실질적으로 막았다. 억지로 더 손볼 필요는 없다고 판단한다.

3. **동시 쓰기(main_loop)/읽기(dashboard) 충돌은 WAL+busy_timeout+애플리케이션 레벨 재시도로 이미 적절히 대응됨**
   `connect()`(243~286행)가 WAL 모드, `synchronous=NORMAL`, `busy_timeout`, 그리고 `_RetryingConnection`을 겹겹이 적용해 "database is locked" 경합을 다층으로 방어하고 있다. 모의투자 시스템 특성(실거래 자금 손실 없음)을 고려하면 트레이드오프도 합리적이다.

4. **append-only 테이블 보관주기는 이미 설계돼 있으나 `predictions`만 한 군데 공백이 있음**
   `prune_snapshots`(365일), `prune_model_trainings`(실패 건만, 365일)는 의도가 명확하고 일관성 있게 구현돼 있다. 위 1번과 같은 맥락에서 `predictions`만 "영구 미확정" 경로가 빠져 있다.

## 구체적 제안
`storage.py`의 `prune_predictions()` 함수(447~461행) 바로 아래에, 동일한 패턴으로 "오래된 미확정 건"을 정리하는 함수를 추가한다:

```python
def prune_stale_unresolved_predictions(conn, keep_days: int = 7) -> int:
    cutoff = (datetime.now(timezone.utc) - timedelta(days=keep_days)).isoformat()
    cur = conn.execute(
        "DELETE FROM predictions WHERE resolved = 0 AND predicted_at < ?",
        (cutoff,),
    )
    return cur.rowcount if cur.rowcount is not None and cur.rowcount > 0 else 0
```
`keep_days`는 7일 정도로 짧게 잡는다 — 정상 케이스는 1사이클(1분) 안에 확정되므로, 7일 넘게 미확정이면 거의 확실히 "확정 불가능한" 고아 행이다. 이 함수를 `prune_predictions()`와 같은 호출 지점(스케줄러/정기 정리 루틴, 이 파일 밖)에서 함께 호출하면 된다.

## 리스크/트레이드오프
- `keep_days=7`을 너무 짧게 잡으면, 가격 피드가 일시적으로(예: 거래소 API 장애로 수 시간~며칠) 끊겼다가 복구되는 정상 케이스의 미확정 행까지 지워버려 그 구간의 예측-적중 기록이 영구히 사라진다. 피드 복구 주기를 감안해 여유 있게 잡거나, 삭제 대신 `resolved=1, correct=NULL`("만료")로 표시해 집계에서 자연히 제외시키는 쪽이 더 안전할 수 있다.
- "실제로 지금 미확정 행이 얼마나 쌓여 있는지"는 운영 데이터를 봐야 판단 가능한 부분이라, `keep_days` 적정값과 긴급성은 `db_file_size_mb()`와 미확정 행 수를 실측한 뒤 정하는 것이 바람직하다.
- portfolios 스키마를 두 컬럼(strategy, variant) 복합키로 정규화하는 "더 근본적인" 대안은 구조적으로는 더 깔끔하지만, main_loop.py/dashboard.py의 호출부 변경과 기존 데이터 마이그레이션이 필요해 지금 시점에 득보다 위험(코드 변경 범위, 트레이딩 로직 영향 가능성)이 커 보류를 권한다.
