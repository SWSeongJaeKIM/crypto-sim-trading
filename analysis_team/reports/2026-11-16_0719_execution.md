## 발견한 점 (2~4개, 우선순위 순)

1. **(재확인, 미수정) 로깅 경로 불일치** — `data_fetcher.py` 120/139/153줄의 실패 경고는 여전히 `print()`로만 출력된다. `main_loop.py`는 `logging.FileHandler("run.log", ...)`(56줄)로 콘솔+파일 동시 기록을 설정해 두었지만 `data_fetcher.py`는 이 체계를 전혀 쓰지 않으므로, 코인별 캔들/히스토리 수집 실패가 `run.log`에는 남지 않는다. 서비스로 등록해 stdout이 버려지는 환경이면 가장 중요한 실패 원인이 완전히 소실된다.

2. **(신규) `run_one_cycle` 예외처리가 전략 단위로 분리되지 않음** (`main_loop.py` 203-252줄, 호출부 319-323줄) — `main()`의 `try/except`는 `run_one_cycle()` 호출 전체를 감싸고 있을 뿐, `for strat_name in STRATEGY_NAMES:` 루프(203줄) 내부에는 전략별 `try/except`가 없다. 따라서 5개 전략 중 하나(특히 `lstm_predictor` — 모델 파일 손상, `predict_proba` 내부 예외 등)에서 예외가 발생하면 그 시점 이후의 전략들(나머지 조건식 전략 포함)은 이번 사이클에서 신호 계산/매매/스냅샷 저장을 전혀 수행하지 못한 채 전체 사이클이 스킵된다. 전략들은 서로 독립적인 로직인데, 한 전략의 버그가 나머지 4개 전략의 가동률까지 떨어뜨리는 비대칭적 장애 전파 구조다.

3. **(관련, 신규) `data_fetcher.py`의 예외 처리가 `FetchError`만 포착** (74-80줄 `fetch_latest_minute_candles`, 118-120줄 `fetch_all_latest_candles`) — `_http_get_json`이 재시도 끝에 던지는 `FetchError`는 코인별로 잡아내지만(119줄 `except FetchError`), Upbit이 예상과 다른 JSON 구조를 반환해 `_parse_minute_df`에서 `KeyError`/`ValueError` 등이 발생하면 이 예외는 `FetchError`가 아니므로 `fetch_all_latest_candles` 루프 밖으로 그대로 전파되어 "6개 코인 중 1개의 파싱 문제"가 "이번 사이클 전체 캔들 수집 실패"로 번진다. 2번 항목과 결합하면 영향 범위가 더 커진다.

4. **(재확인, 미수정) 사이클 주기 드리프트** — `main_loop.py` 337-340줄은 `run_one_cycle` 소요 시간을 측정하지 않고 매 사이클 뒤 고정 60초를 그대로 sleep한다. 재학습이 끼는 사이클은 수 분 추가 지연된다.

## 구체적 제안

- **main_loop.py 203-252줄**: `for strat_name in STRATEGY_NAMES:` 루프 본문을 `try: ... except Exception as e: log.exception(f"[{strat_name}] 전략 처리 중 에러 — 이 전략만 스킵"); continue` 로 감싸, 한 전략의 실패가 나머지 전략 처리를 막지 않도록 한다.
- **data_fetcher.py 118-121줄, 132-139줄**: `except FetchError as e:` 바로 아래 `except Exception as e: print(...)` (또는 아래 제안대로 `log.warning`)를 추가해, 예상 못한 파싱/형식 오류도 해당 코인만 건너뛰고 나머지 코인 수집은 이어가도록 한다.
- **data_fetcher.py**: 지난 리포트와 동일하게, 상단에 `log = logging.getLogger("data_fetcher")`를 추가하고 120/139/153줄의 `print(f"[WARN] ...")`를 `log.warning(...)`으로 교체한다.
- **main_loop.py 337-340줄**: `t0 = time.monotonic()`을 사이클 시작 시 기록하고 `sleep_for = max(0, CYCLE_INTERVAL_SEC - (time.monotonic() - t0))`만큼만 대기하도록 변경.

## 리스크/트레이드오프

- 전략별 `try/except`를 추가하면 특정 전략이 반복적으로 예외를 던질 때 로그가 매분 쌓여 `run.log`가 빠르게 커질 수 있다 — 동일 전략의 연속 실패는 일정 횟수 이후 경고 빈도를 줄이는 처리가 필요할 수 있다.
- `fetch` 함수에서 `Exception`까지 넓게 잡으면 진짜 버그(예: 코드 자체의 타입 오류)도 "API 실패"처럼 조용히 넘어가 디버깅이 늦어질 위험이 있다 — 포착한 예외 타입과 traceback을 반드시 로그에 남겨야 한다.
- 사이클 타이밍을 경과시간 차감 방식으로 바꾸면 처리 시간이 60초를 넘는 상황이 반복될 때 사이클 간격이 좁아져 Upbit API 호출 빈도가 높아질 수 있다.
