## 한줄 요약
스키마/인덱스/보관주기/동시성/포트폴리오 키 설계는 이전 여러 차례 분석 라운드를 거쳐 이미 상당히 잘 정리되어 있고, 남아있는 실질적 문제는 `dashboard.py`가 `model_training_history()`를 코인별로 반복 호출하는 N+1 쿼리 패턴 하나뿐이다.

## 발견한 점 (우선순위 순)

1. **`model_training_history()` N+1 쿼리 패턴이 아직 남아있음** — `local/dashboard.py` 894~897번째 줄(`api_data()` 안)에서 하드코딩된 6개 코인(`BTC, ETH, XRP, SOL, DOGE, ADA`)에 대해 `storage.model_training_history(conn, coin=coin, limit=10)`를 루프로 6번 호출한다. 각 쿼리 자체는 `idx_model_trainings_coin(coin, timestamp DESC)`을 그대로 타서 개별적으로는 가볍지만, 바로 같은 파일 바로 아래(899번째 줄) `prediction_accuracy_by_coin()`은 정확히 동일한 "코인별 최근 N건" 패턴을 과거에 N+1이던 것을 윈도우 함수(`ROW_NUMBER() OVER (PARTITION BY coin ...)`) 1쿼리로 고친 사례가 `storage.py` 553~593번째 줄 docstring에 명시돼 있음에도, 같은 대시보드 새로고침 경로에 있는 `model_training_history` 호출부에는 같은 수정이 적용되지 않았다. 코인 수가 늘어나면 쿼리 수도 그만큼 선형으로 늘어나는 동일한 구조적 문제가 그대로 남아있다.

2. **인덱스/보관주기/동시성/포트폴리오 키 설계는 이미 양호함** — `trades`, `predictions`, `model_trainings`, `snapshots` 모두 실제 쿼리 패턴(대시보드 호출 경로 포함)에 맞춘 인덱스가 갖춰져 있고(`idx_trades_timestamp`, `idx_trades_reason`, `idx_predictions_resolved_coin_time` 등), append-only 테이블(`predictions`, `snapshots`, `model_trainings`)에는 모두 보관주기가 적용되어 `main_loop.py`에서 매일 1회 실행된다(711~833번째 줄). WAL 모드 + `busy_timeout` + 애플리케이션 레벨 재시도(`_RetryingConnection`) + 전략별 예외 격리로 동시 쓰기/읽기 충돌도 잘 방어돼 있다. 포트폴리오 키("`<전략>__reset`")도 `make_portfolio_key`/`parse_portfolio_key`로 조립·파싱이 일원화되고 입력 검증이 걸려 있어, 설계상 한계(한 컬럼에 두 차원 인코딩)는 코드 내 TODO(84~89번째 줄)로 이미 인지되었고 "지금 마이그레이션할 가치는 없다"는 결론도 합리적이다.

## 구체적 제안
`storage.py`에 `prediction_accuracy_by_coin()`과 같은 방식의 함수를 추가한다. 예: `model_training_history_by_coins(conn, coins: list[str], limit_per_coin: int = 10) -> dict[str, list[dict]]` — `WITH ranked AS (SELECT *, ROW_NUMBER() OVER (PARTITION BY coin ORDER BY timestamp DESC) AS rn FROM model_trainings WHERE coin IN (...)) SELECT * FROM ranked WHERE rn <= ?` 형태로 1쿼리에 전체 코인을 가져온 뒤, `dashboard.py` 894~897번째 줄의 `for coin in [...]: storage.model_training_history(...)` 루프를 이 결과를 `dict`에서 꺼내 `reversed()`로 재배열하는 코드로 교체한다. `feature_cols_json` 파싱(기존 `model_training_history`의 pop/json.loads 로직)도 그대로 가져가야 한다.

## 리스크/트레이드오프
이 변경은 쿼리 수만 6회→1회로 줄이는 순수 조회 최적화라 트레이딩 로직이나 기존 데이터에는 영향이 없다. 다만 현재 코인 수(6개)·`limit=10`이라는 작은 규모에서는 체감 성능 차이가 거의 없을 가능성이 높으므로, 급하게 고칠 "버그"는 아니고 "코드 일관성 + 코인 수가 늘어날 미래에 대한 선제 조치" 성격의 개선이다. 새 윈도우 함수 쿼리는 SQLite 3.25+가 필요하지만, 바로 옆 `prediction_accuracy_by_coin()`이 이미 같은 요구사항으로 동작 중이므로 환경상 문제는 없다.

(참고: 실제 운영 데이터(trading.db의 실제 거래/학습 기록 규모, DB 파일 실측 크기 등)를 봐야 판단 가능한 질문에는 답하지 않았음 — 이번 리뷰는 코드 구조·로직만으로 수행.)
