## 한줄 요약
스키마/인덱스 설계는 실제 쿼리 패턴(`strategy+timestamp DESC`, `coin+predicted_at DESC`, `resolved`)에 잘 맞지만, SQLite 동시성 설정 부재와 predictions/snapshots의 무제한 누적이 장기 운영 시 리스크이며, `portfolios.strategy`에 "__reset"/"__cumulative"를 문자열로 인코딩한 설계는 유지보수성이 떨어진다.

## 발견한 점 (우선순위 순)
1. **동시 읽기/쓰기 보호 설정이 없음**: `connect()`(storage.py 106~115줄)는 매 호출마다 새 `sqlite3.connect()`를 열 뿐 `PRAGMA journal_mode`나 `busy_timeout`을 설정하지 않는다. main_loop.py는 60초 주기(41줄 `CYCLE_INTERVAL_SEC`)로 `with storage.connect()` 블록 안에서 포트폴리오/거래/스냅샷/예측을 한 트랜잭션에 커밋하고(248~254줄), dashboard.py는 새로고침마다 별도 커넥션으로 동일 DB를 읽는다(508줄). SQLite 기본 rollback-journal 모드에서는 writer 커밋 순간 reader가 겹치면 대기 없이 즉시 "database is locked" 예외가 날 수 있다.
2. **append-only 테이블이 보관주기 없이 무한 증가**: `predictions`는 코인 6개(data_fetcher.py COINS) × 1분 사이클마다 1행씩 쌓여(238~246줄) 하루 약 8,640행, 연간 300만 행 이상이 된다. `snapshots`도 전략×variant(reset/cumulative) 조합마다 분당 1행씩 쌓인다. storage.py 어디에도 삭제/압축(retention) 로직이 없다. 인덱스가 있어 조회 자체는 LIMIT으로 버티지만, DB 파일 크기와 백업/VACUUM 비용이 시간에 비례해 계속 커진다.
3. **`strategy` 컬럼에 "<전략>__reset"/"<전략>__cumulative" 합성 문자열 인코딩**: `portfolios`, `trades`, `snapshots` 세 테이블 모두 이 문자열을 키처럼 공유하며(main_loop.py 12~15줄, dashboard.py 516줄 주석), 실제 전략명+variant 구분자를 "__"에 의존한다. variant별 집계(예: "reset 포트폴리오 전체 합산 수익률")를 하려면 매번 문자열 split/LIKE가 필요하고, 전략명 자체에 "__"가 들어가면 파싱이 깨질 수 있다. storage.py에는 이 분리/조합을 전담하는 헬퍼가 없어 호출부(main_loop.py, dashboard.py)에 로직이 흩어져 있다.
4. (양호) `recent_trades(strategy=None)`처럼 WHERE 없이 전체 테이블을 스캔하는 조회도 LIMIT이 걸려 있고, 인덱스(`idx_trades_strategy`, `idx_predictions_coin`, `idx_predictions_unresolved` 등)가 실제 질의 조건과 정확히 맞아 느려질 전체 스캔 쿼리는 눈에 띄지 않는다.

## 구체적 제안
- storage.py `connect()`(107줄) 내부에서 `conn.executescript(SCHEMA)` 호출 전후에 `conn.execute("PRAGMA journal_mode=WAL")`와 `conn.execute("PRAGMA busy_timeout=5000")`를 추가한다. WAL 모드는 reader와 writer가 서로 블로킹하지 않게 해주므로 dashboard 읽기와 main_loop 쓰기가 겹쳐도 즉시 예외가 나지 않는다.
- storage.py에 `purge_old_predictions(conn, keep_days=90)`(예: `DELETE FROM predictions WHERE resolved=1 AND predicted_at < ?`)와 `purge_old_snapshots(conn, keep_days=180)` 헬퍼를 추가하고, main_loop.py의 사이클 종료 지점(254줄 `set_meta("status", ...)` 근처)에서 "하루 1회만" 호출하도록 날짜 체크를 건다. 적중률/학습추이 집계가 필요하면 삭제 전에 일별 요약을 별도 집계 테이블(`daily_prediction_stats` 등)에 먼저 적재하는 방식을 함께 고려한다.
- `portfolios`/`trades`/`snapshots`의 `strategy TEXT` 컬럼을 `strategy TEXT`와 `variant TEXT`(reset/cumulative) 두 컬럼으로 분리하고, `portfolios`는 PRIMARY KEY를 `(strategy, variant)`로 바꾸는 마이그레이션을 `migrate_dual_portfolio.py`의 기존 패턴을 참고해 작성한다. 전면 변경이 부담되면 최소한 `encode_key(strategy, variant)` / `decode_key(key)` 같은 공용 헬퍼를 storage.py에 추가해 main_loop.py·dashboard.py의 "__" split 로직 중복을 한 곳으로 모은다.

## 리스크/트레이드오프 (제안을 적용하면 생길 수 있는 부작용)
- WAL 모드로 바꾸면 `.db-wal`/`.db-shm` 파일이 추가로 생겨 수동 백업 시 세 파일을 함께 챙겨야 한다(로컬 PC 상주 전제이므로 네트워크 드라이브 이슈는 해당 없음).
- purge는 되돌릴 수 없는 삭제라서, 파일 상단 주석(21~30줄)이 밝힌 "모델 성능/적중률 추이를 전부 보존"하려는 원래 설계 의도와 충돌할 수 있다. 보관 기간을 짧게 잡기 전에 일별 요약 테이블을 먼저 두는 단계적 적용이 안전하다.
- strategy/variant 컬럼 분리는 세 테이블 스키마뿐 아니라 main_loop.py·dashboard.py의 쿼리/조회 코드도 함께 고쳐야 해서 변경 범위가 storage.py 밖으로 넓어지고, 기존 `migrate_dual_portfolio.py`처럼 1회성 마이그레이션 스크립트가 추가로 필요하다.

(참고: 실제 DB 파일 크기, 현재 row 수, lock 충돌 발생 빈도, 실제 운영 수익/적중률 등은 코드만으로 알 수 없고 실제 운영 데이터를 봐야 판단 가능하다.)
