## 한줄 요약
피처 구성과 모델 크기는 데이터 양 대비 적절한 편이나, 파인튜닝 시 "이전 모델보다 나빠져도 무조건 덮어쓰는" 구조와 검증 지표가 실전 난이도보다 쉬운 부분집합만 보는 점이 가장 먼저 손볼 만하다.

## 발견한 점 (2~4개, 우선순위 순)

1. **파인튜닝에 성능 비교/롤백 장치가 없음** (`local/lstm_model.py` 162~168행). `train_model`은 매일 `val_acc`를 계산하지만, 이 값을 기존 저장 모델(`existing_path`)의 성능과 비교하지 않고 무조건 새 가중치로 덮어씁니다(168행 `torch.save`). `local/learner.py`의 `tune_strategy`(120~173행)는 백테스트 점수가 개선될 때만 파라미터를 교체하는 "수용/거부" 구조인데, LSTM 쪽만 이 안전장치가 빠져 있습니다. 운 나쁜 하루치 데이터로 파인튜닝하면 모델이 전날보다 더 나빠진 채로 그대로 실전에 들어갈 수 있습니다.

2. **검증 정확도가 실전 과제보다 쉬운 부분집합만 측정** (`build_dataset`, 76~81행 / `train_model`의 `val_acc`, 162~166행). 학습·검증 모두 `NEUTRAL_BAND`(0.05%) 이내 변동 샘플을 제외하고 만든 `X, y`로 쪼갭니다. 그런데 실제 추론(`predict_proba`, `signal`)은 이런 필터링 없이 매분 모든 구간에 대해 신호를 냅니다. 즉 `val_accuracy`는 "방향이 비교적 뚜렷한 구간"에서만의 정확도이고, 실전에서 마주치는 애매한(노이즈성) 구간의 성능은 대시보드 지표에 전혀 반영되지 않습니다.

3. **FEATURE_COLS에 코인 간 상관관계 피처가 없음** (41행). 알트코인은 흔히 BTC 움직임을 짧은 지연을 두고 따라가는데, 현재 피처 5개(`ret, vol_chg, rsi14, macd_hist, bb_pctb`)는 모두 해당 코인 자신의 단일 시계열에서만 계산됩니다. 호가 스프레드는 애초에 1분봉 OHLCV 데이터에 없는 정보라 현재 데이터 소스(`data_fetcher`)로는 추가가 어려워 보이지만, BTC 동시 수익률은 다른 코인 df를 같이 넘기면 계산 가능한 정보라 우선순위가 더 높습니다.

4. SEQ_LEN(60)·모델 구조(hidden=32, 1-layer LSTM, head 16유닛)는 30일치 1분봉(필터 후 수만~수십만 샘플) 규모에 비해 작은 편이라 과적합 위험은 낮고, 학습/검증 분할도 시간순(130~132행)이라 미래 데이터 누출이 없는 점은 좋은 설계입니다. 이 부분은 "이미 잘 돼 있음"으로 봅니다.

## 구체적 제안
- `train_model` 162~168행 사이에, `resumed_from_existing`이면 기존 `existing_path` 가중치로 같은 `X_val_t`를 평가한 `old_val_acc`를 구하고, `val_acc < old_val_acc - tolerance`(예: 0.01)면 새 가중치 저장을 건너뛰고(단, `history/` 사본과 반환값의 `val_accuracy`는 그대로 기록해 대시보드 추이는 유지) 기존 `{coin}_lstm.pt`를 보존하도록 분기 추가.
- `build_dataset`에 `include_neutral: bool = False` 옵션을 추가해, 검증 구간만큼은 중립 구간을 포함한 전체 윈도우로 별도 `val_accuracy_all`을 함께 계산·반환(`train_model` 반환 dict에 필드 추가)해 대시보드에서 "실전형 정확도"와 "방향 뚜렷한 구간 정확도"를 구분해 보이게 함.
- `build_features`에 선택적 `ref_close: pd.Series | None` 인자를 추가해 BTC 동시 1분 수익률을 피처로 넣고, `train_all`/`retrain_lstm`에서 BTC df를 다른 코인 학습 시 같이 전달(알트코인 전용, BTC 자신은 제외).

## 리스크/트레이드오프
- 성능 비교 후 롤백 로직을 넣으면 "나쁜 날"엔 모델이 갱신되지 않아 최근 급변한 시장 패턴 반영이 늦어질 수 있음(반영 지연 vs 안정성의 트레이드오프).
- `val_accuracy_all` 추가는 코드 복잡도와 계산량을 늘리고, 두 지표가 다르게 움직이면 운영자가 어느 쪽을 신뢰할지 혼란을 줄 수 있어 대시보드 표기를 명확히 해야 함.
- BTC 상관 피처 추가는 알트코인 모델의 입력 차원을 늘려 재학습 시간이 늘고, BTC 자체에 문제가 생기면(급락 등) 알트코인 신호가 과도하게 BTC에 의존하는 부작용이 생길 수 있음.

(참고: local/learner.py, local/main_loop.py, local/retrain_now.py도 학습 파이프라인 맥락 확인을 위해 읽었음. 실제 운영 데이터(학습 정확도 추이, trading.db 등)는 접근 범위 밖이라 "실제로 정확도가 얼마나 되는지"는 운영 데이터를 봐야 판단 가능.)
