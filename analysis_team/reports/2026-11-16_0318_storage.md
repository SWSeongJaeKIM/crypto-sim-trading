## 한줄 요약
스키마와 인덱스는 현재 쿼리 패턴에 대체로 맞게 설계되어 있으나, WAL 미적용에 따른 동시성 리스크, portfolios의 문자열 인코딩 키, predictions 보관주기 부재가 보완 포인트다.

## 발견한 점 (우선순위 순)

1. **(동시성) WAL 미설정 + 매 connect마다 스키마 재실행** — `connect()`(storage.py:106-115)는 연결마다 `executescript(SCHEMA)`를 실행하고, journal 모드를 WAL로 전환하는 코드가 없다. 기본 rollback journal 모드에서는 쓰기 트랜잭션 중 DB 파일 전체가 잠기므로, main_loop가 60초마다 쓰는 순간 dashboard의 읽기가 "database is locked"로 실패할 가능성이 있다. 특히 읽기 전용 호출(dashboard)도 매번 `CREATE TABLE IF NOT EXISTS` 트랜잭션을 거치며 불필요하게 락 경합 기회를 만든다.

2. **(스키마 설계) portfolios의 "<strategy>__reset"/"<strategy>__cumulative" 인코딩** — storage.py는 strategy를 단순 TEXT PK(44행)로만 다루기 때문에, "전략별 reset/cumulative 모두 조회"나 "전략명만으로 묶기" 같은 연산이 호출부의 문자열 분해/LIKE 패턴매칭에 의존하게 된다. 구분자("__")가 전략명 자체에 우연히 포함되거나 오타가 나도 DB 레벨에서 전혀 검증되지 않는다.

3. **(append-only 보관주기 부재) predictions, model_trainings** — 196~293행 전체에 DELETE 문이 없다. predictions는 코인 수 × 1행/분 속도로 쌓여 수개월 뒤 수백만 행 규모가 될 수 있다. 각 조회에 LIMIT과 적합한 인덱스(idx_predictions_coin, idx_predictions_unresolved)가 있어 조회 성능 자체는 유지되지만, DB 파일 크기·백업 비용은 계속 증가한다.

4. **(경미) recent_trades(strategy=None)** (168-171행) — idx_trades_strategy가 (strategy, timestamp DESC) 복합 인덱스라, strategy 없이 호출하면 이 인덱스를 못 쓰고 timestamp 전체 스캔이 된다. 다만 trades는 거래 발생시에만 쌓이므로 현재 빈도로는 당장 문제가 아니다.

## 구체적 제안
- storage.py `connect()`에서 `conn = sqlite3.connect(...)` 직후 `conn.execute("PRAGMA journal_mode=WAL")`, `conn.execute("PRAGMA busy_timeout=5000")`을 추가. WAL은 쓰기 1개+읽기 다수 동시 허용이 기본값보다 안전해 main_loop(쓰기)/dashboard(읽기) 패턴에 정확히 맞는다.
- `executescript(SCHEMA)`를 매 connect마다 실행하지 말고 앱 시작 시 1회만 호출하는 `init_db()`로 분리.
- portfolios 스키마를 `strategy TEXT, mode TEXT, data_json, updated_at, PRIMARY KEY(strategy, mode)`로 바꾸고 `get_portfolio(conn, strategy, mode)`처럼 인자를 분리. 기존 값은 "__" 기준 1회 split 마이그레이션 스크립트로 이전.
- predictions에 보관정책 함수 추가: `def prune_old_predictions(conn, keep_days=90): conn.execute("DELETE FROM predictions WHERE resolved=1 AND predicted_at < ?", (cutoff,))`를 만들어 main_loop에서 하루 1회 호출. `resolved=1` 조건을 반드시 넣어 미확정 행은 보존.

## 리스크/트레이드오프
- WAL로 바꾸면 DB 파일 옆에 `-wal`, `-shm` 보조 파일이 생기고 비정상 종료 시 체크포인트가 지연돼 디스크 사용량이 잠깐 늘 수 있다. 다만 로컬 PC 상주 환경이라 네트워크 드라이브 관련 WAL 불안정 이슈는 해당하지 않을 것으로 보인다.
- portfolios 스키마 변경은 "<strategy>__mode" 문자열을 그대로 쓰는 main_loop.py, dashboard.py 호출부도 함께 바꿔야 하는 마이그레이션 비용이 있다. 이 리포트는 storage.py만 검토했으므로 실제 영향 범위는 해당 파일들을 봐야 확정 가능.
- predictions 삭제 정책을 넣으면 보관기간 이후의 "장기 예측 적중률 추이" 분석이 불가능해진다 — keep_days 값은 분석 요구사항에 맞게 신중히 정해야 한다.

(실제 DB에 쌓인 행 개수, 실제 쿼리 성능, 현재 수익/적중률 등은 운영 데이터를 봐야 판단 가능하며 본 리포트 범위 밖이다.)
