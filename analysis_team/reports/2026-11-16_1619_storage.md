## 한줄 요약
스키마/인덱스와 동시성 처리는 쿼리 패턴에 잘 맞게 견고히 유지되고 있고, predictions/model_trainings의 보관주기 부재와 portfolios 문자열 키 설계는 여러 차례 지적되었으나 설계 의도·마이그레이션 비용 문제로 의도적으로 보류된 채 그대로 남아 있다.

## 발견한 점 (2~4개, 우선순위 순)

1. **(정보) 스키마/인덱스는 실제 쿼리 패턴에 잘 맞춰져 있다.** `local/storage.py` 59-64행, 95-99행은 strategy/coin 필터 없이 전체를 조회하는 경로(대시보드의 "전체 최근 거래"/"전체 모델 학습 기록")를 위해 timestamp 단독 인덱스를 별도로 둬서 전체 스캔을 피하고 있고, 111-119행은 predictions의 "resolved 필터 + predicted_at 정렬"을 기존 단일컬럼 인덱스 2개 대신 복합 인덱스(`idx_predictions_coin_resolved_time`, `idx_predictions_resolved_time`)로 교체해 `prediction_accuracy()`/`prediction_accuracy_by_coin()` 경로를 커버한다. 현재 쿼리들(WHERE 조건+ORDER BY)이 모두 인덱스 선두 컬럼과 일치해, "느려질 만한 전체 스캔"은 보이지 않는다.
2. **(정보) 동시 쓰기/읽기 정합성도 잘 처리돼 있다.** `connect()`(171-204행)가 WAL 모드 + busy_timeout(5초) + 애플리케이션 레벨 재시도(`_RetryingConnection`, 152-168행)를 겹쳐 두고, 스키마 초기화도 프로세스당 1회로 캐시(127-132행, 189-192행)해 매 사이클 connect마다의 불필요한 트랜잭션 경합을 줄였다. main_loop(쓰기)와 dashboard(읽기)가 동시에 돌아도 WAL 특성상 읽기가 쓰기를 블로킹하지 않는 구조다.
3. **(중, 반복 지적 그대로 유지) predictions/model_trainings가 append-only로 무한 누적되는데 삭제/보관주기 로직이 storage.py에 전혀 없다**(DELETE 문 없음). predictions는 코인별 1분 사이클마다 1행씩 쌓여 장기 운영 시 수백만 행 규모가 될 수 있다. 조회는 LIMIT+복합인덱스로 보호돼 있어 "쿼리 지연"보다는 "DB 파일 크기/백업 비용 증가" 쪽 리스크다. `prune_predictions()` 류 제안은 과거에도 여러 번 나왔지만 "실전 적중률을 시간순으로 전부 보존"하려는 파일 상단 docstring(27-30행)의 설계 의도와 충돌하고, 실제 필요한 보관 기간은 운영 데이터를 봐야 정할 수 있어 사람 판단으로 매번 보류됐다.
4. **(낮음, 반복 지적 그대로 유지) portfolios의 `"<전략>__reset"/"<전략>__cumulative"` 문자열 인코딩**: storage.py는 `strategy TEXT PRIMARY KEY`(44-48행) 하나만 정의하고, reset/cumulative 구분은 호출부(main_loop.py, dashboard.py)가 각자 `"__"`로 조립/역파싱한다. storage.py 자체에는 이 구분을 아는 로직이 없다. 복합키(strategy, variant) 전환이 반복 제안됐지만 기존 데이터 마이그레이션 + 호출부 수정까지 범위가 커서 매번 보류됐다.

## 구체적 제안

- **(발견 3 관련, 저위험)** 삭제 로직보다 먼저 "판단에 필요한 관측 지표"를 코드로 깔아두는 것을 제안한다. `local/storage.py` 끝(386행 이후)에 `def db_file_size_mb() -> float: return DB_PATH.stat().st_size / 1024 / 1024` 같은 한 줄짜리 헬퍼를 추가하고 dashboard.py에서 호출해 "DB 파일 크기: N MB"를 표시하면, 보관주기가 실제로 필요해지는 시점을 숫자로 확인할 수 있다. DB 스키마/기존 데이터를 전혀 건드리지 않는 변경이다.
- **(발견 4 관련, 저위험)** 전체 복합 PK 마이그레이션 대신, `local/storage.py`에 `PORTFOLIO_KEY_SEP = "__"`와 `make_portfolio_key(strategy, variant)` / `parse_portfolio_key(key)` 헬퍼 두 개만 추가(207행 `get_portfolio` 위쪽)한다. main_loop.py/dashboard.py에 흩어진 조립·`rpartition("__")` 역파싱 로직을 이 함수 호출로 교체하면, DB 스키마나 기존 데이터는 그대로 두면서 구분자 로직을 한 곳으로 모을 수 있다.

## 리스크/트레이드오프 (제안을 적용하면 생길 수 있는 부작용)

- DB 크기 관측 헬퍼는 부작용이 거의 없지만, 그것만으로는 보관주기 문제를 해결하지 않고 "측정 가능하게"만 만든다 — 삭제 여부는 결국 trading.db 실측치를 사람이 보고 결정해야 한다(이 분석팀이 볼 수 없는 부분).
- `portfolio_key` 헬퍼는 storage.py 내부에서는 안전하지만, main_loop.py/dashboard.py가 실제로 이를 가져다 쓰도록 호출부를 바꿔야 효과가 나며, 바꾸지 않으면 중복 로직이 남아 헬퍼가 죽은 코드가 된다. 또한 헬퍼를 쓰더라도 전략명에 `"__"`가 포함될 경우의 모호성 자체는 여전히 남는다(근본 해결은 복합 PK 마이그레이션뿐).
