## 한줄 요약
피처/구조/재학습 주기 설계는 전반적으로 합리적이나, 학습 라벨과 피처 윈도우 사이에 1분 오프셋 불일치가 있어 추론 시점과 학습 시점의 "현재" 정의가 어긋나는 문제가 가장 먼저 고쳐야 할 지점입니다.

## 발견한 점 (2~4개, 우선순위 순)

**1) (최우선) 학습 데이터 생성에서 피처 윈도우와 라벨의 1분 오프셋 불일치** — `lstm_model.py` 76~81행
```python
for i in range(seq_len, n - 1):
    next_ret = (close[i + 1] - close[i]) / close[i]
    ...
    xs.append(arr[i - seq_len: i])   # 마지막 행 = i-1
```
라벨은 `close[i]→close[i+1]` 전환인데, 피처 윈도우의 마지막 시점은 `i-1`로 한 칸 모자랍니다. 즉 "다음 캔들" 예측에 가장 중요한 정보인 바로 직전 봉(`i`)의 피처가 학습에서 빠집니다. 반면 `predict_proba`(216행)는 `feat[-seq_len:]`로 가장 최신 봉까지 포함한 윈도우를 넣습니다. 학습 때는 윈도우 끝과 라벨 시작 사이에 1분 공백이 있는데, 추론 때는 공백이 없는 구조라 모델이 실제로 학습한 과제와 서빙 시 받는 입력의 "시점 정의"가 어긋납니다. 가장 신선하고 예측력이 큰 바로 직전 봉 정보를 매번 버리는 셈입니다.

**2) 피처에 동시간대 타 코인(특히 BTC) 신호가 없음** — `FEATURE_COLS`(41행)는 전부 해당 코인 단독의 가격/볼륨 지표(`ret`, `vol_chg`, `rsi14`, `macd_hist`, `bb_pctb`)뿐입니다. 암호화폐는 BTC가 알트코인에 선행하는 경향이 강한데, `main_loop.py`가 이미 6개 코인 캔들을 같은 사이클에서 동시에 들고 있음(188행 `candles` dict)에도 이 정보가 LSTM 입력으로 전달되지 않습니다. 반면 호가 스프레드는 `data_fetcher.py`(74~145행)가 캔들 API만 호출하고 오더북 API를 쓰지 않아 애초에 데이터 자체가 없어 지금 구조에선 추가할 수 없는 항목입니다(정보 제공).

**3) 파인튜닝에 성능 저하 가드/롤백이 없음** — `train_model`(162~172행)은 검증정확도(`val_acc`)를 계산하지만, 기존 저장 모델보다 나빠져도 조건 없이 `existing_path`를 덮어씁니다. 재학습이 매일 자동으로 돌기 때문에, 특정 날 데이터 품질 문제나 과적합으로 val_acc가 떨어져도 그대로 운영에 반영됩니다.

**4) 재학습 주기(1일)·학습기간(30일)·검증 분할 방식 자체는 적절** — 1분봉 예측에서 하루 1회 재학습 + 30일 롤링 윈도우는 과제 특성에 맞고, `val_frac`을 시계열 뒷부분으로 분리(130~132행)해 미래 데이터 누수를 피한 점도 좋습니다. 이 부분은 억지로 고칠 필요 없습니다. SEQ_LEN=60 + hidden=32 1-layer LSTM도 30일치(수만 샘플) 데이터량 대비 모델 용량이 과하지 않아 구조적 과적합 소지는 크지 않습니다.

## 구체적 제안
- `lstm_model.py` 80행 `xs.append(arr[i - seq_len: i])` → `arr[i - seq_len + 1: i + 1]`로 변경해 윈도우 마지막 시점을 라벨의 "현재" 시점(`i`)과 일치시킵니다. 수정 후 다음 재학습 때부터 전 코인 모델을 새로 학습해야 일관성이 맞습니다.
- `FEATURE_COLS`에 `btc_ret`(해당 사이클의 BTC `close.pct_change()`)을 추가하려면 `build_features`에 선택적 `btc_df` 매개변수를 넣고, `main_loop.py` 188·230행 근처 호출부에서 `candles["BTC"]`를 함께 넘기도록 변경합니다.
- `train_model`에서 `storage`에 기록된 직전 `val_accuracy`(main_loop.py 274~291행에서 쌓는 `model_training` 기록)를 조회해, 신규 `val_acc`가 그보다 임계치(예: 0.02) 이상 낮으면 `torch.save`를 건너뛰고 `"trained": True, "applied": False`로 반환하는 가드를 추가합니다.

## 리스크/트레이드오프
- 오프셋 수정 직후에는 기존 `.pt` 가중치가 옛 정의로 학습된 상태라 즉시 1회 강제 재학습이 필요하며, 그 전까지는 구/신 정의 혼재로 성능 비교가 무의미해집니다.
- BTC 피처 추가는 알트코인 모델이 BTC 급변(거시 이벤트 등)에 더 동조화되어, BTC발 급락 시 여러 코인 신호가 한꺼번에 틀릴 상관 리스크를 키울 수 있습니다.
- 파인튜닝 가드 임계값을 너무 엄격히 잡으면 실제 레짐 전환 초기(일시적으로 val_acc가 낮게 보이는 날)에 모델 갱신이 막혀 적응이 느려질 수 있습니다.

(※ 실제 수익률, 적중률, 거래 손익 등 운영 데이터 기반 판단은 코드만으로는 불가능하며 실제 운영 데이터 확인이 필요합니다.)
