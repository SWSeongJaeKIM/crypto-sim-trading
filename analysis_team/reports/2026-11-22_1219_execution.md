## 한줄 요약
예외처리·로깅·사이클 타이밍 전반은 이미 여러 차례의 리뷰를 거쳐 상당히 견고하게 다져져 있고, 남은 문제는 두 곳의 좁은 엣지케이스 정도다.

## 발견한 점 (2~4개, 우선순위 순)

1. **(우선순위 1) data_fetcher.py의 캐시 폴백 read 자체가 예외처리 없음 — 코인별 격리 철학이 이 경로에서만 깨짐.**
   `fetch_all_minute_history()`의 `_fetch_one`(약 504~512행)은 `fetch_minute_history` 실패 시 캐시 CSV로 폴백하는데, 이 폴백용 `pd.read_csv(cache_path, ...)` 호출(511행)은 try/except 밖에 있다. 캐시 파일이 손상되어 있거나 동시 쓰기 중이어서 이 read마저 실패하면, 예외가 스레드 작업 함수 밖으로 그대로 올라가 `future.result()`(520행)에서 재발생하고, 이는 `fetch_all_minute_history()` → `retrain_lstm()` 호출부(570행, try/except 없음)를 그대로 통과해 결국 main()의 while 루프 상위 try/except(764행)까지 전파된다. 결과적으로 "코인 1개"의 이중 실패(네트워크 실패 + 캐시도 손상)가 "이번 재학습 슬롯 전체(6코인 모두)"를 실패시킨다 — 이 파일이 다른 모든 곳에서 일관되게 지키고 있는 "코인 하나의 장애가 다른 코인을 막지 않는다"는 설계 원칙이 이 경로에서만 예외적으로 깨져 있다.

2. **(우선순위 2, 구조적 리스크·조건부) `fetch_latest_minute_candles`에 count 상한 안전장치 없음.**
   모듈 docstring 자체가 "Upbit은 페이지당 최대 200개 제한"이라고 명시하는데, main_loop.py 366행은 `data_fetcher.fetch_all_latest_candles(count=max(lstm_model.SEQ_LEN + 5, 200))`로 호출한다. `fetch_latest_minute_candles`(data_fetcher.py 188~210행)는 단일 요청(페이지네이션 없음)이라 count가 200을 넘으면 Upbit이 조용히 200개로 잘라서 돌려줄 가능성이 있다. 지금 당장은 SEQ_LEN 값이 195 이하라면 문제가 없지만(이 값은 lstm_model.py에 있어 이번 리뷰 범위 밖), 코드 어디에도 count<=200을 강제하거나 경고하는 장치가 없어 향후 SEQ_LEN이 늘어나면 "캔들 부족" 경고(443행)가 영원히 반복되는 조용한 회귀가 생길 수 있다.

## 구체적 제안

- **data_fetcher.py 511행 근처**: 캐시 폴백 read를 자체 try/except로 한 번 더 감싼다.
  ```python
  if cache_path.exists():
      try:
          return coin, pd.read_csv(cache_path, parse_dates=["open_time"]), False
      except Exception as cache_e:
          log.warning(f"[{coin}] 캐시 CSV 폴백 read도 실패, 이 코인만 이번 슬롯 건너뜀: {cache_e}")
  return coin, None, False
  ```
  이렇게 하면 이중 실패 시에도 해당 코인만 `None`으로 빠지고 나머지 5코인은 정상 학습이 진행된다.

- **data_fetcher.py 188행 `fetch_latest_minute_candles` 시작부**: `count = min(count, 200)`로 클램프하고, 잘렸을 때 1회성 디버그 로그를 남긴다. main_loop.py 쪽 호출부(366행)는 바꿀 필요 없음 — 호출자가 몰라도 안전하도록 피호출부에서 막는 것이 더 견고하다.

## 리스크/트레이드오프

- 제안 1은 순수 방어 코드 추가라 기존 동작을 바꾸지 않으며 부작용이 거의 없다. 다만 "이중 실패"가 실제로는 매우 드문 상황이라 체감 효과는 작을 수 있다.
- 제안 2의 `min(count, 200)` 클램프는 현재 SEQ_LEN 값에서는 아무 동작 변화가 없는 순수 안전장치이므로 리스크가 낮다. 다만 이 수정은 "지금 문제가 실제로 발생 중"이 아니라 "향후 SEQ_LEN 변경 시를 대비한 선제적 안전장치"이므로, 우선순위를 낮게 두고 다른 작업과 묶어 처리해도 무방하다.
- 참고: 실제로 캐시 손상이나 SEQ_LEN 값이 지금 문제를 일으키고 있는지는 운영 데이터(run.log, trading.db)를 봐야 확인 가능한 영역이라, 이 분석팀은 "코드 구조상 가능성"만 판단했음을 명시한다.
