## 한줄 요약
스키마와 인덱스 설계는 쿼리 패턴에 맞게 합리적이나, `main_loop.py`가 커넥션 하나를 프로세스 수명 전체로 유지하는 구조 때문에 "정상 종료 전까지 디스크에 커밋 안 됨" 문제와 대시보드의 데이터 지연(stale read)이 생길 수 있다. (코드가 지난 리포트 이후 변경되지 않아 동일 결론.)

## 발견한 점 (우선순위 순)
1. **쓰기가 커밋되지 않고 쌓임.** `storage.py:106-115`의 `connect()`는 `with` 블록 종료 시에만 `conn.commit()`을 호출하는 contextmanager인데, `main_loop.py:273-304`는 `while not _stop:` 루프 전체를 단일 `with storage.connect() as conn:` 안에 넣어 프로세스가 살아있는 내내 같은 커넥션·트랜잭션을 유지한다. `set_portfolio`/`add_trades`/`add_snapshot`/`add_prediction`/`resolve_predictions`/`set_meta`/`add_model_training`이 모두 이 미커밋 트랜잭션에 쌓인다. 다른 스크립트(`retrain_now.py:21`, `migrate_dual_portfolio.py:37`, `dashboard.py:325`)는 짧게 `connect()`를 열고 닫는데 `main_loop.py`만 예외다.
2. **동시성: 대시보드가 최신 데이터를 못 볼 수 있음.** SQLite는 커넥션 간 격리가 있어, `dashboard.py`가 별도 커넥션으로 읽어도 main_loop가 아직 커밋하지 않은 행은 보이지 않는다(쓰기 충돌이 아니라 "안 보임" 문제). 비정상 종료(크래시, OOM-kill, `kill -9`)가 나면 마지막 정상 종료 시점 이후의 거래/스냅샷/예측 기록이 전부 사라진다.
3. **append-only 테이블(predictions, snapshots)에 보관주기 없음.** `storage.py`에 prune/archive 함수가 전혀 없다. 1분 주기 × 코인 수로 선형 누적되어, 현재 규모에서 SQLite가 못 버틸 정도는 아니지만 장기 무중단 운영 시 파일 크기·백업 비용이 계속 늘어난다. 단, `model_trainings`는 docstring(storage.py:21-23)에 "전부 보존해 추이를 본다"는 설계 의도가 명시돼 있어 정리 대상에서 제외해야 한다.
4. **`portfolios` PK 네이밍.** `"<전략>__reset"/"<전략>__cumulative"`(`main_loop.py:84-87`)는 strategy/mode를 문자열 결합으로 인코딩해, mode 값이 DB 레벨에서 검증되지 않고(CHECK 제약 없음) 소비 측(`dashboard.py:333-336`)이 각자 `rpartition("__")` 파싱을 복제해야 한다. 당장 기능상 문제는 없지만 mode 종류가 늘어나면 파싱 로직을 전부 손봐야 한다.

## 구체적 제안
- `main_loop.py`의 `main()`에서 273줄의 `with storage.connect() as conn:`을 while 루프(281줄) 바깥이 아니라 **사이클마다 새로 여닫는 구조**로 바꾸거나, 최소한 `run_one_cycle`/`retrain_lstm` 각각 끝에 `conn.commit()`을 명시적으로 추가한다.
- `storage.py`에 `prune_old_snapshots(conn, keep_days)` / `prune_old_predictions(conn, keep_days)`를 추가하고, `main_loop.py:288` 근처 일일 재학습 트리거 시 하루 1번만 호출한다.
- `portfolios` 테이블을 `(strategy TEXT, mode TEXT CHECK(mode IN ('reset','cumulative')), PRIMARY KEY(strategy, mode))`로 분리하고 `get_portfolio`/`set_portfolio` 시그니처를 `(strategy, mode)`로 바꿔 문자열 파싱을 제거한다(`migrate_dual_portfolio.py` 전례처럼 1회 마이그레이션 스크립트 필요).

## 리스크/트레이드오프
- 사이클마다 커밋하면 쓰기 I/O가 늘어 느린 디스크에서 지연이 소폭 생길 수 있으나, 1분 주기 시스템 특성상 무시 가능한 수준이고 데이터 안전성 이득이 훨씬 크다.
- prune 적용 시 predictions/snapshots만 정리 대상으로 한정하고 model_trainings는 건드리지 않아야 설계 의도를 해치지 않는다.
- portfolios 스키마 분리는 기존 DB 마이그레이션과 `dashboard.py` 등 소비 코드의 동시 수정이 필요해 일회성 작업 비용이 발생한다.
- "실제로 지금 데이터 손실이 일어나고 있는지/대시보드가 지연을 보이는지"는 실제 운영 환경(재시작 빈도, 실행 시간)을 봐야 확정 가능 — 이는 실제 운영 데이터를 봐야 판단 가능한 질문이라 이 분석 범위 밖이다.
