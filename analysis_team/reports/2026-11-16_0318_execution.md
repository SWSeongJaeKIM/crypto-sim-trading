## 한줄 요약
전체 구조(재시도, 캐시 폴백, reset/cumulative 분리, 재학습 복구 로직)는 견고하게 설계되어 있으나, 예외 처리의 "범위"가 너무 넓은 단위(코인 전체 fetch, 사이클 전체)로 걸려 있어 한 코인/전략의 일시적 오류가 전체 사이클을 통째로 날릴 수 있는 지점이 있다.

## 발견한 점 (2~4개, 우선순위 순)

1. **[우선순위 높음] `data_fetcher.fetch_all_latest_candles`의 per-coin try/except가 `FetchError`만 잡음 (data_fetcher.py 117~121줄).** `_http_get_json`은 `urllib.error.URLError/HTTPError/TimeoutError`만 잡아 `FetchError`로 변환하는데(46~56줄), Upbit이 5xx/점검 페이지처럼 비-JSON 본문을 200으로 응답하면 `json.loads`가 `json.JSONDecodeError`를 던지고, 이는 `FetchError`가 아니므로 117번째 줄의 `except FetchError`에 걸리지 않는다. 이 경우 예외가 `fetch_all_latest_candles`의 for-loop를 즉시 중단시켜 **그 코인뿐 아니라 리스트상 뒤에 남은 코인들까지 전부 수집 실패**로 이어지고, 결국 `run_one_cycle`을 감싸는 `main()`의 try/except(main_loop.py 320~323줄)까지 전파되어 **그 사이클 전체(6코인×5전략)가 스킵**된다. API 자체 재시도 로직이 있는데도 이 경로에서는 무력화된다.

2. **[우선순위 중간] `run_one_cycle` 내부 5개 전략 루프(main_loop.py 203~252줄)가 하나의 try/except로만 보호됨.** 특정 전략의 `signal_with_confidence`나 LSTM `predict_proba`가 (예: NaN 캔들, 모델 파일 손상 등으로) 예외를 던지면 그 전략만 스킵되는 게 아니라 `run_one_cycle` 전체가 즉시 중단되어, 이미 신호 계산이 끝난 앞 전략들의 매매/저장(`storage.set_portfolio` 등)도 함께 유실된다. 전략 간 독립성이 설계 의도인데(reset/cumulative 분리 등) 예외 처리 단위가 이를 깨고 있다.

3. **[우선순위 낮음] 로그 파일 경로가 상대경로 `"run.log"`(main_loop.py 56줄).** 모듈 docstring(20줄)은 "`local/run.log`에 남는다"고 명시하는데, 실제로는 실행 시점의 cwd에 따라 달라진다. `local/` 밖에서 실행되거나 서비스(systemd 등)로 등록되어 WorkingDirectory가 다르면 로그가 엉뚱한 곳에 생겨 문제 진단 시 혼란을 줄 수 있다.

4. **[참고/트레이드오프, 버그 아님] 사이클 주기가 고정 60초가 아니라 "작업시간 + 60초"로 흘러감(main_loop.py 319~340줄).** 오버랩/누적 실행은 없지만(순차 실행이라 안전), 재학습(수 분~수십 분 소요)이 끼는 날은 그 시간 동안 매매 사이클이 전혀 돌지 않는다. 설계상 감내 가능한 트레이드오프로 보이나, 사이클 소요시간을 로그에 남기지 않아 드리프트 누적 여부를 진단하기 어렵다.

## 구체적 제안
- data_fetcher.py 46번째 줄: `except (urllib.error.URLError, urllib.error.HTTPError, TimeoutError) as e:`에 `json.JSONDecodeError`를 추가(`except (urllib.error.URLError, urllib.error.HTTPError, TimeoutError, json.JSONDecodeError) as e:`)하여 비정상 응답도 재시도 대상에 포함시킨다.
- data_fetcher.py 117~121줄: `except FetchError as e:`를 `except Exception as e:`로 넓혀, 코인 하나의 예기치 못한 오류가 나머지 코인 수집을 막지 않도록 한다.
- main_loop.py 203~252줄의 전략 for-loop 안쪽(각 `strat_name` 처리 블록)을 `try/except Exception`으로 감싸고 `log.exception(f"[{strat_name}] 전략 처리 중 에러, 스킵")` 후 `continue`하도록 수정한다.
- main_loop.py 56줄: `logging.FileHandler("run.log", ...)` → `logging.FileHandler(Path(__file__).parent / "run.log", ...)`로 절대경로화.
- (선택) run_one_cycle 시작/종료 시각을 측정해 `log.info(f"사이클 소요 {elapsed:.1f}s")`를 335줄 근처 로그에 추가하면 드리프트/지연 진단에 도움.

## 리스크/트레이드오프
- 예외 범위를 넓히면(`except Exception`) 디버깅 시 원인 파악이 더 어려워질 수 있으므로, `log.exception`으로 traceback을 반드시 남겨야 한다(이미 main()의 상위 레벨은 이렇게 하고 있어 패턴 일관성 유지 가능).
- 전략별 try/except 추가는 코드량과 들여쓰기 깊이를 늘려 가독성이 약간 떨어질 수 있다.
- 로그 경로를 절대경로로 바꾸면 기존에 상대경로 기준으로 쌓인 run.log와 위치가 달라져, 기존 로그 뷰어/알림 스크립트가 경로를 참조하고 있다면 함께 수정 필요.
- (실제로 이러한 예외가 운영 중 얼마나 자주 발생했는지, 즉 이 문제가 실제로 손실을 유발했는지는 실제 운영 데이터를 봐야 판단 가능.)
