## 한줄 요약
SEQ_LEN/모델 구조와 파인튠 롤백 안전장치는 현재 데이터 규모·과제 난이도(val_acc 54~62%)에 비춰 적절하게 설계되어 있으나, 재학습 시 매번 90일 전체를 다시 학습하는 구조, 코인별 변동성을 무시한 고정 NEUTRAL_BAND, 변동성 레짐을 직접 나타내는 피처의 부재는 개선 여지로 남아있다.

## 발견한 점 (우선순위 순)
1. (main_loop.py `HISTORY_DAYS_FOR_TRAIN=90`, line 48; `retrain_lstm` line 696-727 / `lstm_model.py train_model` line 154-237) 하루 10회 파인튠 호출마다 매번 90일 전체를 재수집·재학습한다. 윈도우가 거의 겹치므로 "오늘 새로 들어온 2시간24분치 데이터"가 전체 학습 신호에서 차지하는 비중이 구조적으로 희석되고, 연산비용도 매번 90일치만큼 든다.
2. (`lstm_model.py` `NEUTRAL_BAND=0.0005` line 50, `build_dataset` line 128) 모든 코인에 동일한 절대 수익률(0.05%) 기준으로 중립 구간을 제외한다. 코인별 평균 변동성이 다르면(예: 변동성이 낮은 코인) 상대적으로 더 많은 샘플이 제외되어, 코인마다 학습 데이터 양·라벨 분포가 불균일해질 수 있다.
3. (`FEATURE_COLS` line 84, `build_features` line 88-108) 5개 피처 전부 가격·거래량의 변화량/지표로만 구성되어 있고, "지금이 조용한 장인지 널뛰는 장인지"를 직접 나타내는 변동성 레짐 피처(예: rolling std of return)가 없다. RSI/MACD/볼린저는 모두 추세·과매수 신호 위주라 변동성 국면 구분에는 약하다.
4. SEQ_LEN(60분)·hidden=32의 소형 LSTM 구조, 그리고 파인튠 롤백(`VAL_ACC_ROLLBACK_THRESHOLD`)·체인 리셋(`FINETUNE_CHAIN_LENGTH_RESET_THRESHOLD=30`) 안전장치는 1분봉 예측이라는 저신호 과제에 맞춰 과적합을 의도적으로 억제한 설계로 보이며, 추가 변경이 필요해 보이지 않는다.

## 구체적 제안
- `main_loop.py`의 `retrain_lstm` 중 일반 파인튠 슬롯(line 696-727, `force_full_retrain`이 False인 경우)에서 `fetch_all_minute_history(days=HISTORY_DAYS_FOR_TRAIN)` 대신 더 짧은 윈도우(예: `days=14`)를 쓰고, `force_full_retrain`(line 722, chain≥30)일 때만 현재처럼 90일 전체를 쓰도록 분기한다. `lstm_model.py`의 학습 로직은 그대로 두고 호출부의 `days` 인자만 바꾸는 변경이다.
- `lstm_model.py` line 50의 `NEUTRAL_BAND`를 절대값 대신 각 코인 `ret`의 최근 구간 표준편차에 비례한 값(예: `0.1 * rolling_std(ret, 60)`)으로 바꿔, `build_dataset`(line 111-135)에서 코인마다 비슷한 비율의 샘플만 중립 제외되도록 한다.
- `build_features`(line 88-108)에 `ret.rolling(20).std()` 같은 단기 변동성 컬럼을 추가하고 `FEATURE_COLS`(line 84)에 포함시킨다.

## 리스크/트레이드오프
- 파인튠 윈도우를 줄이면(예: 14일) 모델이 과거 패턴을 덜 참고하게 되어 단기 이상 구간(급등락 하루)에 더 쉽게 흔들릴 수 있다. 현재 30체인(약 3일)인 전체 재학습 주기를 더 촘촘히 당기는 보완이 필요할 수 있다.
- `NEUTRAL_BAND`를 상대값으로 바꾸면 라벨 기준이 재학습 시점마다(변동성 추정값에 따라) 조금씩 달라져, 현재 `val_accuracy` 기반 롤백 비교(line 307)의 재학습 간 일관성이 흐려질 수 있어 전환 시 해당 로직도 함께 점검해야 한다.
- 변동성 피처 추가는 입력 차원이 늘어 hidden=32의 소형 모델이 과적합할 여지를 약간 키운다. 추가 시 val_accuracy 변화를 보며 hidden 크기 재검증이 필요하다.
- 세 제안 모두 실제 효과(거래 손익, val_accuracy 추이 변화)는 운영 데이터를 봐야 확정 가능 — 코드 구조만으로는 판단 불가.
