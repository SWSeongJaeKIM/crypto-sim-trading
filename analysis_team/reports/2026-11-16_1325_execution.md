## 한줄 요약
직전 회차에 적용된 전략별 try/except(main_loop.py 258~334번째 줄)와 Upbit API 공유 레이트리미터(data_fetcher.py `_RateLimiter`)는 코드에 그대로 반영되어 있어 정상 동작 중이다. 이번에는 "부분 API 오류가 전체 코인 수집을 날리는 문제"와 "재학습 중 거래 사이클 완전 정지" 두 가지를 새로 짚는다.

## 발견한 점 (우선순위 순)

1. **`_fetch_one`이 `FetchError`만 잡아서 예외 하나가 전체 6코인 수집을 통째로 실패시킬 수 있음** — `data_fetcher.py` 201~206번째 줄(`fetch_all_latest_candles`의 내부 함수), 241~270번째 줄(`fetch_all_minute_history`의 내부 함수) 모두 `except FetchError as e:`만 처리한다. `_http_get_json`은 네트워크/파싱 오류를 재시도 끝에 `FetchError`로 변환하지만, `_parse_minute_df`(94~106번째 줄)에서 Upbit이 예상과 다른 필드 구조의 응답을 주면(`KeyError` 등) 이건 `FetchError`가 아니다. 이 예외는 `ThreadPoolExecutor`의 `future.result()`를 통해 그대로 전파되어, `fetch_all_latest_candles` 자체가 예외를 던지며 끝난다 — 즉 한 코인만의 문제가 **그 사이클의 6개 코인 전체 수집**을 날리는 결과가 된다. (main의 try/except가 프로그램 다운은 막아주지만, 사이클 전체가 스킵되는 건 막지 못함.)

2. **LSTM 재학습이 메인 스레드에서 동기 실행되어, 그 동안 매매 사이클이 완전히 정지함** — `main_loop.py` 441~446번째 줄은 `retrain_lstm()`을 호출부와 같은 스레드에서 블로킹으로 돌린다. `HISTORY_DAYS_FOR_TRAIN`이 90일로 확장된 뒤(47번째 줄), 공유 레이트리미터(0.12초 간격, 전체 요청 기준)로 역산하면 6코인 × 약 648페이지 ≈ 3,888회 요청 × 0.12초 ≈ 최소 7.8분이 데이터 수집만으로 소요된다(학습 시간은 별도). 하루 10회(43~46번째 줄) 재학습이면 하루 70분 이상 거래가 멈출 수 있다 — 단, 실제 누적 정지 시간은 운영 로그(run.log)로 확인해야 정확하다(이 부분은 실제 운영 데이터를 봐야 정확히 판단 가능).

## 구체적 제안

- `data_fetcher.py` 204번째 줄과 265번째 줄의 `except FetchError as e:`를 `except Exception as e:`로 넓혀서, 예상 못한 파싱/형식 오류도 해당 코인 하나만 `None`/캐시 폴백으로 처리되게 한다. (265번째 줄은 기존처럼 캐시 폴백 분기를 그대로 타게 하면 됨.) 또한 현재 `print(...)`로만 남기는 경고를 `logging.exception`으로 바꾸면 스택트레이스가 run.log에 남아 원인 진단이 쉬워진다.
- `main_loop.py` 441~446번째 줄의 `retrain_lstm()` 호출을 `threading.Thread(target=..., daemon=True)`로 백그라운드 실행하고, 중복 실행 방지를 위해 `threading.Lock`으로 감싼다. 이렇게 하면 데이터 수집/학습 중에도 60초 매매 사이클이 계속 돈다.

(부가 관찰, 우선도 낮음) `main_loop.py` 452~455번째 줄의 `for _ in range(CYCLE_INTERVAL_SEC): time.sleep(1)`은 사이클 작업 소요 시간을 고려하지 않는 고정 추가 슬립이라, 실제 사이클 간격은 "작업시간+60초"가 된다. 누적 지연은 아니고(매 사이클 현재 시각 기준으로 재계산) 평상시 영향은 미미하지만, 네트워크 지연이 커지는 구간에서는 체감 주기가 늘어난다.

## 리스크/트레이드오프

- `except Exception`으로 넓히면 진짜 심각한 버그(예: 코드 로직 오류)까지 "경고 후 넘어가기"로 숨겨질 수 있다 — 로그에 스택트레이스가 남는지 반드시 함께 바꿔야 안전하다.
- 재학습을 별도 스레드로 돌리면, 학습 중 모델 파일(.pt)을 저장하는 시점에 같은 시각 매매 사이클이 `lstm_model.predict_proba()`로 그 파일을 읽을 수 있어 레이스 컨디션(쓰다 만 파일 읽기) 위험이 생긴다. `last_retrain_at` 전역 변수도 두 스레드에서 접근하므로 락 또는 원자적 갱신이 필요하다. 이 변경은 단순 패치가 아니라 모델 저장 방식(임시파일+rename 등 원자적 교체)까지 같이 봐야 안전하므로, 적용 전 별도 검토 단계를 권장한다.
