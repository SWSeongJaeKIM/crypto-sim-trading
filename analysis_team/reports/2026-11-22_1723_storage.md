## 한줄 요약
인덱스/보관주기/동시성 처리는 이전 여러 차례의 분석을 거쳐 쿼리 패턴에 맞게 이미 잘 구현되어 있으며, 남은 가장 구체적인 개선 여지는 `snapshots` 테이블의 보관주기 설정값과 `portfolios` 합성키 스키마 두 가지다.

## 발견한 점 (우선순위 순)

1. **`snapshots` 보관주기(365일)가 실제 조회 패턴보다 과도하게 길게 잡혀 있을 가능성** — `local/main_loop.py` 53행 `SNAPSHOTS_PRUNE_KEEP_DAYS = 365`와 `local/main_loop.py` 70행 `STRATEGY_NAMES`(전략 4종 + lstm_predictor = 5개) × `PORTFOLIO_MODES`(reset/cumulative = 2) × `CYCLE_INTERVAL_SEC = 60`(43행)을 조합하면, 매 사이클마다 `storage.add_snapshot`(548행)이 10행씩 쌓여 연간 최대 약 525,600분 × 10 ≈ 526만 행이 쌓일 수 있다(코드 상수로 계산한 이론적 상한, 실제 누적량은 운영 데이터를 봐야 확인 가능). 그런데 `storage.py` 337~345행 `recent_snapshots()`는 항상 "최근 N개"(기본 30개)만 조회하므로, 365일치 1분 단위 원본을 전부 남겨둘 실익이 조회 패턴상 크지 않다.

2. **`portfolios` 합성키 방식은 이미 코드 스스로 기술 부채로 인지하고 있으며, 지금 당장 바꿀 필요는 없다는 결론이 타당함** — `storage.py` 84~89행 TODO가 "복합 PK 전환"을 명시해뒀고, `make_portfolio_key`/`parse_portfolio_key`(52~93행)로 조립·역파싱 로직을 한 곳에 모아 두어 당장의 유지보수 부담은 크지 않다. 다만 질문에 직접 답하자면, 더 나은 스키마는 분명히 존재한다(아래 제안 참고).

3. **인덱스·동시성 설계는 쿼리 패턴과 잘 맞음** — `trades`/`predictions`/`model_trainings`의 조회 함수(`recent_trades`, `prediction_accuracy_by_coin`, `model_training_history_by_coins`, `stop_loss_counts_by_coin` 등)를 하나씩 대조해보면 전부 대응하는 커버링 인덱스가 `SCHEMA`(107~199행)에 존재하고, WAL + busy_timeout + 애플리케이션 레벨 재시도(`_RetryingConnection`, 231~247행)로 쓰기/읽기 동시 접근도 3단으로 방어돼 있다. `prune_*` 함수들도 `main_loop.py` 815~834행에서 실제로 호출되는 것을 grep으로 확인했다(죽은 코드가 아님).

## 구체적 제안

- `local/main_loop.py` 53행 `SNAPSHOTS_PRUNE_KEEP_DAYS`를 365에서 90~180 정도로 낮추거나, `storage.py` 535행 `prune_snapshots` 옆에 "최근 30일은 원본 1분 단위 유지, 그 이전은 날짜별 1행(종가/평균 pnl_pct)으로 집약"하는 `compact_old_snapshots(conn, older_than_days=30)` 함수를 추가해 장기 추이는 유지하면서 행 수 증가를 선형에서 꺾는 방식을 검토할 것.
- `portfolios` 테이블을 차기 스키마 개편 시 `strategy TEXT, variant TEXT, data_json TEXT, updated_at TEXT, PRIMARY KEY(strategy, variant)`로 바꾸고, `get_portfolio`/`set_portfolio`(storage.py 304~319행)에 `variant` 매개변수를 추가해 `make_portfolio_key`/`parse_portfolio_key` 호출 자체를 없애는 방향을 제안.

## 리스크/트레이드오프

- `snapshots` 보관기간을 줄이면 대시보드에서 분 단위 장기 추이(storage.py 538~540행 주석이 의도한 "사람이 장기 pnl 추이를 직접 들여다볼 여지")를 잃는다. 다운샘플링 방식은 이 트레이드오프를 완화하지만 구현 복잡도가 늘어난다.
- `portfolios` 복합 PK 전환은 기존 `trading.db`의 "`strategy__variant`" 형태 데이터를 1회성 마이그레이션해야 하고, `main_loop.py`/`dashboard.py`에서 해당 키를 쓰는 모든 지점을 함께 수정해야 하므로 사용자 PC마다 다른 로컬 DB 파일에 자동 마이그레이션 로직이 필요하다.
- 두 제안 모두 지금 당장 긴급한 장애 요인은 아니며, 실제로 얼마나 급한지는 현재 `trading.db` 파일 크기와 전략 수 변화 추이 같은 실제 운영 데이터를 봐야 판단 가능하다(이는 실제 운영 데이터 없이는 답할 수 없는 부분).
