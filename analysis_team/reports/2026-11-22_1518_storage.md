## 한줄 요약
스키마/인덱스/보관주기/동시성 설계는 수십 차례 리뷰를 거쳐 이미 매우 성숙한 상태이지만, `stop_loss_counts_by_coin()`을 위해 추가했던 `idx_trades_reason` 인덱스가 SQLite의 기본 LIKE 대소문자 구분 설정 때문에 실제로는 전혀 쓰이지 않는다는 것을 EXPLAIN QUERY PLAN으로 직접 확인했다.

## 발견한 점 (우선순위 순)

1. **`idx_trades_reason`(storage.py 134번째 줄) 인덱스가 실제로는 사용되지 않음 — 검증됨.** `stop_loss_counts_by_coin()`(storage.py 647~658번째 줄)의 `WHERE reason LIKE '손절%' OR reason LIKE '강제청산%'`를 동일 스키마로 재현해 `EXPLAIN QUERY PLAN`을 직접 돌려본 결과, SQLite 기본값(`case_sensitive_like=OFF`)에서는 prefix LIKE가 인덱스를 전혀 타지 않고 `SCAN trades`(전체 스캔)로 나왔다. `PRAGMA case_sensitive_like=ON`을 설정하면 그제서야 `SEARCH ... USING COVERING INDEX idx_reason`로 바뀐다. 즉, 2026-11-22_0618 리포트가 "이 인덱스로 전체 스캔을 막는다"고 기대했던 효과가 코드상으로는 실현되지 않고 있다(SQLite 3.53.1 기준 실측, ASCII 패턴으로도 동일하게 재현되어 한글 여부와는 무관함).
2. **append-only로 계속 쌓이는 `trades` 테이블 관점에서 이 문제는 시간이 지날수록 악화된다.** `trades`는 (의도적으로, 실거래 이력 보존 목적으로) prune 대상이 아니므로 건수가 영구적으로 늘어난다. 인덱스가 실제로 안 먹는 채로 방치되면, `dashboard.py`가 새로고침마다 호출하는 `stop_loss_counts_by_coin()`의 전체 스캔 비용이 trades 건수에 비례해 계속 커진다 — 지금 당장은 미미하지만 보관주기가 없는 테이블이라 장기적으로 유일하게 "느려지는 방향"으로 가는 쿼리다.
3. **그 외 구조는 양호함.** `model_training_history()` N+1 패턴은 `model_training_history_by_coins()`(storage.py 416~446번째 줄)로 이미 수정되어 `dashboard.py` 900번째 줄에서 사용 중이고, `prune_predictions/prune_snapshots/prune_model_trainings/prune_stale_unresolved_predictions`도 `main_loop.py` 802~839번째 줄에서 하루 1회 실제로 호출되며 WAL 체크포인트까지 함께 수행된다. `portfolios` 합성키 설계도 `make_portfolio_key`/`parse_portfolio_key`로 일원화되어 있고 한계는 TODO로 문서화되어 있어 현재로서는 추가 조치가 불필요하다고 판단한다.

## 구체적 제안
`storage.py`의 `connect()` 함수(275~276번째 줄, `PRAGMA synchronous=NORMAL` 다음)에 `conn.execute("PRAGMA case_sensitive_like=ON")`를 추가한다. 이 저장소 전체(`local/`)에서 LIKE를 쓰는 곳은 `stop_loss_counts_by_coin()`의 `'손절%'`/`'강제청산%'` 두 패턴뿐이고(grep으로 확인), 둘 다 고정된 한글 접두어 매칭이라 대소문자 구분 여부가 결과에 영향을 주지 않으므로 다른 쿼리 결과는 전혀 바뀌지 않는다. 이 한 줄만으로 이미 존재하는 `idx_trades_reason` 인덱스가 실제로 적용되게 된다(추가 인덱스 생성이나 쿼리 재작성 불필요).

## 리스크/트레이드오프
- `case_sensitive_like=ON`은 커넥션 전역 설정이라, 앞으로 누군가 영어 텍스트에 대소문자 구분 없는 LIKE 검색을 추가하면 의도와 다르게 동작할 수 있다 — 적용한다면 `connect()` 함수 주석에 "이 프로젝트의 유일한 LIKE 사용처(한글 접두어 매칭)를 위해 켜둔 설정이니, 새로 대소문자 무시 LIKE가 필요해지면 이 pragma와 충돌하는지 먼저 확인할 것"이라는 메모를 남겨두는 것이 안전하다.
- 현재 트레이딩 건수 규모에서는 전체 스캔이어도 체감 성능 차이가 거의 없을 가능성이 높아 긴급 버그는 아니다. 다만 코드가 "인덱스로 해결했다"고 문서화해둔 상태와 실제 동작이 다르다는 점은 바로잡아둘 가치가 있다.
- (참고: 실제 PC의 trading.db 실측 크기, 실제 거래/학습 건수 등 운영 데이터를 봐야 판단 가능한 질문에는 답하지 않았음 — 이번 리뷰는 코드 구조·로직 및 로컬 재현 테스트로만 수행함.)
