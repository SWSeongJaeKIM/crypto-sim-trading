## 한줄 요약
전체적으로 예외 격리(전략별/코인별), 사이클 타이밍 보정(monotonic 기반), 레이트리밋 공유 처리가 이미 잘 구현되어 있다. 다만 "모델 파일 손상"에 대한 로그 폭주 방지가 "모델 파일 없음" 케이스만 커버하고 있어 구체적 추가 보완 지점이 하나 있다.

## 발견한 점 (2~4개, 우선순위 순)

1. **[중] 모델 파일 "손상" 시 로그 폭주 방지가 적용되지 않음** — `main_loop.py` 82번 줄 주석과 331~336번 줄 코드를 보면, 코인별 모델 결손 경고 중복 방지(`_warned_missing_model`)는 `FileNotFoundError`에만 적용된다. 하지만 같은 파일 472~474번 줄 주석에서 이미 "특정 코인 모델 파일만 손상/삭제돼도"라고 손상(corrupted) 케이스를 직접 언급하고 있다. 만약 `.pt` 파일이 존재하지만 내용이 손상(예: PC 강제종료 중 쓰다 만 파일)되어 `torch.load`가 `RuntimeError`/`EOFError`/`pickle.UnpicklingError` 등을 던지면, 이는 337~340번 줄의 일반 `except Exception` 분기로 떨어져 **매 사이클(1분마다)** `log.exception`으로 전체 스택트레이스를 반복 적재한다. 즉 "없음"은 고쳤지만 "손상"은 여전히 로그 폭주 가능성이 있다.

2. **[낮음] HTTP 429(레이트리밋 초과) 응답에 대한 전용 처리 없음** — `data_fetcher.py` 78~94번 줄 `_http_get_json`은 네트워크 오류/타임아웃/JSON 파싱 오류를 모두 동일하게 취급해 고정된 1초/2초/3초 선형 백오프만 적용한다. Upbit이 429를 반환하며 `Retry-After` 유사 헤더나 응답 바디로 대기 시간을 알려주는 경우에도 이를 활용하지 않고 일반 네트워크 오류와 동일하게 재시도한다. 현재 sleep_sec=0.12초(공유 리미터)로 요청 자체가 Upbit 공개 API 한도(초당 약 10회) 안에 있어 평소엔 429가 거의 안 날 가능성이 높아 심각도는 낮다.

3. **[낮음] `_warned_missing_model`이 코인 단위로만 키를 잡음** — `main_loop.py` 82번 줄. 현재 모델 기반 전략은 `lstm_predictor` 하나뿐이라 문제없지만, 향후 모델 기반 전략이 추가되면 전략 A의 코인 X 결손 경고가 뜬 뒤 전략 B의 같은 코인 X 결손은 경고가 안 뜨고 조용히 묻힐 수 있다.

## 구체적 제안

1. `main_loop.py` 326번 줄 `except FileNotFoundError as e:` 바로 아래에 모델 로딩류 예외(예: `RuntimeError`, `EOFError`, `pickle.UnpicklingError` 등 손상 파일에서 흔히 나는 예외)를 같은 분기로 묶거나, `except (FileNotFoundError, RuntimeError, EOFError) as e:`로 확장해 동일하게 `_warned_missing_model` 기반 1회성 경고로 처리. 다만 이 경우 "코인별 모델 로딩 실패"라는 더 일반적인 예외 클래스로 처리 범위를 넓히면 진짜 버그(전략 코드 자체의 버그)까지 묵음처리할 위험이 있으므로, `lstm_model.py`에서 모델 로드 부분을 별도 함수로 감싸 "모델 로드 실패"만 의미하는 전용 예외(예: `ModelLoadError`)로 재포장해 올리는 방식이 더 안전함.
2. `data_fetcher.py` 85~94번 줄에서 `urllib.error.HTTPError`의 `e.code == 429`인 경우만 별도로 분기해 좀 더 긴 고정 대기(예: 5초)를 주는 정도로 충분 — 현재 트래픽 규모에서는 과설계일 수 있음.

## 리스크/트레이드오프
제안 1처럼 예외 범위를 넓히면, 전략 로직 자체의 버그(예: 인덱싱 오류)가 우연히 같은 예외 타입이면 "모델 손상"으로 오분류되어 경고가 묵음 처리되고 실제 버그 발견이 늦어질 수 있다. 전용 예외 클래스로 감싸는 방식이 더 안전하지만 `lstm_model.py` 수정이 추가로 필요하다. 제안 2는 Upbit API 응답 헤더 구조를 추가로 파싱해야 해 코드 복잡도가 약간 늘고, 실제 운영에서 429가 얼마나 발생하는지는 운영 로그를 봐야 확인 가능(실제 운영 데이터를 봐야 판단 가능).
