## 한줄 요약
특징(feature) 구성·파인튠 전략·재학습 주기는 이미 과거 analysis_team 제안(체인 길이 리셋, val_acc 롤백 등)이 반영되어 전반적으로 잘 잡혀 있으나, 6개 코인이 같은 루프에서 동시에 수집됨에도 각 코인 모델이 BTC 등 타 코인과의 동행성 신호를 전혀 쓰지 않는 점은 구체적으로 보강할 여지가 있다.

## 발견한 점 (우선순위 순)

1. **FEATURE_COLS(71번 줄)에 타 코인 동행성 피처 부재.** `ret, vol_chg, rsi14, macd_hist, bb_pctb` 전부 해당 코인 자신의 OHLCV에서만 계산된다. `main_loop.py:544`의 `retrain_lstm()`은 `data_fetcher.fetch_all_minute_history()`로 BTC/ETH/XRP/SOL/DOGE/ADA 6개 코인 데이터를 이미 동시에 수집하는데도, 알트코인 모델이 "시장 전체(특히 BTC)가 지금 오르는지/내리는지"를 입력으로 받지 못한다. 1분봉 알트코인 움직임의 상당 부분은 BTC 동행성에서 오므로, 이 신호가 빠져 있는 것은 실질적 공백이다.
2. 호가 스프레드 피처는 Upbit 캔들(OHLCV) API 자체에 호가 정보가 없어 현재 데이터 소스로는 추가가 불가능하다 — 설계 결함이 아니라 데이터 소스 제약.
3. `SEQ_LEN=60`, `LSTMClassifier(hidden=32, layers=1)`은 실측 val_accuracy 54~62%(52번 줄 주석)라는 저신호 상황에 맞춰 의도적으로 소형화된 구조로 보이며, 과적합 소지는 낮다. 파인튠 방식(`lr/3`, 63~69번 줄 val_acc 롤백)과 체인 길이 기반 전체 재학습 강제(`main_loop.py` `FINETUNE_CHAIN_LENGTH_RESET_THRESHOLD=30`, 557~564번 줄)도 "최근 반영 vs 과거 망각" 트레이드오프를 이미 수치화된 임계값으로 다루고 있어 추가 조치가 필요하지 않다.
4. 참고: 지시서의 "재학습 하루 1회/30일치"는 현재 코드와 다르다. 실제로는 하루 10회(약 2시간24분 간격), 90일 윈도우로 이미 더 빈번하게 운영 중이다(`main_loop.py:44,48`).

## 구체적 제안
- `lstm_model.py`의 `build_features(df)`에 선택적 `market_df: pd.DataFrame | None = None` 인자를 추가하고, 있을 경우 `market_df["close"].pct_change()`를 `open_time` 기준으로 맞춰 `market_ret` 컬럼으로 병합 → `FEATURE_COLS`에 `"market_ret"` 추가(BTC 자신의 모델에는 적용 불필요, 나머지 5개 코인에만 적용).
- `main_loop.py:563` `train_model()` 호출 시 이미 손에 있는 `history["BTC"]`를 `market_df`로 함께 넘기도록 `train_model`/`build_dataset` 시그니처를 확장.
- 추론 경로(`predict_proba`, `LSTMStrategy.signal`)는 현재 `signal(df)` 하나만 받으므로, 공통 인터페이스를 유지하려면 `LSTMStrategy.__init__`에 `market_df` 참조(또는 BTC 최근 시세 getter)를 주입해 `signal()` 내부에서만 사용하는 방식을 권장.

## 리스크/트레이드오프
- 입력 피처 수(`N_FEATURES`)가 바뀌므로 기존 저장 가중치(`.pt`)와 차원이 안 맞아 모든 코인 전체 재학습(`finetune=False`)이 한 번 강제로 필요하다 — 그 사이 구버전 모델로 신호가 나가거나 공백이 생길 수 있다.
- `strategies.py`의 `Strategy` 인터페이스는 `signal(df)` 하나만 받는 공통 규약인데, LSTM 쪽만 `market_df`를 추가로 쓰면 리더보드 공통 인터페이스가 미묘하게 갈라질 수 있어 설계 일관성에 신경 써야 한다.
- market_ret 피처가 오히려 코인 고유 신호를 희석시켜 특정 코인/구간에서는 성능이 떨어질 수도 있다 — 적용 전후 val_accuracy 비교가 필요하며, 이는 실제 운영 데이터를 봐야 판단 가능하다.
