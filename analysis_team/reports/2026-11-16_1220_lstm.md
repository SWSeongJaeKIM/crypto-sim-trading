## 한줄 요약
피처/모델 구조와 임계값 설계는 이미 실전에서 드러난 문제(과매매)에 합리적으로 대응한 흔적이 보이며, 가장 개선 여지가 큰 지점은 "파인튜닝이 매일 거의 동일한 30일 윈도우를 반복 학습해 최신 데이터 비중이 희석되는 구조"다.

## 발견한 점 (2~4개, 우선순위 순)

1. **파인튜닝 시 최신 데이터 비중이 구조적으로 낮음** (`lstm_model.py:127-139`, `158-174`). `train_model`은 매일 30일 전체 윈도우로 fine-tune을 돌리는데(`finetune=True`면 기존 가중치 이어 학습), 어제도 거의 같은 30일 창(29일 중첩)으로 학습했을 것이므로 "오늘 새로 들어온 1일"이 전체 학습 신호에서 차지하는 비중은 약 1/30 수준이다. 주석에 적힌 "최근 패턴 반영" 의도에 비해 실제 가중치 업데이트는 과거 패턴 재확인에 더 가깝다. 추가로 Adam 옵티마이저 상태(모멘텀)는 저장/로드되지 않고 매 파인튠마다 초기화되므로(`opt = torch.optim.Adam(...)` at line 168), 이어받는 건 가중치뿐이고 최적화 궤적은 매번 리셋된다.

2. **피처가 단일 코인 내부 지표에 한정됨** (`FEATURE_COLS`, line 57). `ret, vol_chg, rsi14, macd_hist, bb_pctb` 모두 해당 코인의 OHLCV에서만 파생된다. 호가 스프레드는 Upbit 캔들 API 특성상 원래 수집 안 되는 정보라 당장 추가하기 어렵지만, 다른 코인(특히 BTC) 동조화 신호는 데이터만 있으면 바로 추가 가능한데 빠져 있다. 1분봉 방향성은 알트코인이 BTC 움직임을 지연 추종하는 경우가 흔해, 이 신호 부재는 "1분 뒤 방향"이라는 과제와 직결된 공백이다.

3. **SEQ_LEN=60 / 모델 크기는 데이터량 대비 과적합 위험이 낮게 설계되어 있음 — 긍정적**. `LSTMClassifier`가 hidden=32, 1-layer + 작은 head로 파라미터 수가 적고, train/val 분리도 시계열 순서를 지켜(`split`, line 154-156) 데이터 누수가 없다. 샘플 500개 미만이면 학습을 거부하는 가드(line 145)도 있어 과소 데이터에서 무리하게 학습하는 상황은 막혀 있다.

4. **재학습 주기(1일)+윈도우(30일) 조합이 1분봉 예측에 적합한지는 실제 val_accuracy 추이를 봐야 판단 가능** — 코드 주석(line 46-53)에 이미 54~62% 수준이라고 기록돼 있고, 이에 대응해 임계값을 0.55/0.45→0.60/0.40으로 올린 것은 합리적 조치로 보인다. 다만 이 수치가 현재도 유지되는지, 임계값 상향 후 실제 거래 건수/손익이 어떻게 바뀌었는지는 운영 데이터 없이는 판단할 수 없다.

## 구체적 제안
- `lstm_model.py:158` 부근: `train_model`에 `finetune_lr` 파라미터를 별도로 받아 파인튠 시엔 `lr`보다 낮게(예: `lr/3`) 설정. 초기 학습(`resumed_from_existing=False`)에는 기존 `lr=1e-3` 그대로, 이어학습에는 낮은 lr을 써서 과거 가중치가 매일 급격히 덮이지 않게 한다.
- `build_features` (line 61) 시그니처에 `btc_df: pd.DataFrame | None = None`을 추가하고, `ret_btc = btc_df["close"].pct_change()`를 `FEATURE_COLS`에 추가(`N_FEATURES`도 자동 반영). `train_model`/`predict_proba` 호출부(`main_loop.py` 쪽)에서 BTC 캔들을 함께 넘겨주면 된다.

## 리스크/트레이드오프 (제안을 적용하면 생길 수 있는 부작용)
- 파인튠 lr을 낮추면 실제로 급변한 시장 레짐(예: 급락 후 변동성 급증)에 모델이 둔감하게 반응할 수 있어, 반대로 "최근 패턴 반영"이 너무 느려지는 트레이드오프가 생긴다 — lr 축소 비율은 실데이터로 튜닝 필요.
- BTC 상관 피처 추가는 입력 차원(N_FEATURES)을 늘려 작은 모델(hidden=32) 기준 과적합 위험을 약간 높이므로, 추가 시 hidden을 소폭 늘리거나 val_accuracy 변화를 모니터링해야 한다.
