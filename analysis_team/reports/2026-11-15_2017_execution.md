## 한줄 요약
전체적으로 예외처리 틀은 잘 잡혀 있으나, "전략 1개 실패가 전체 사이클을 막는 범위 문제"와 "고정 60초 슬립으로 인한 사이클 주기 드리프트"가 가장 먼저 손볼 지점이다.

## 발견한 점 (우선순위 순)

1. **전략 루프에 개별 예외처리가 없어, 한 전략의 오류가 그 사이클의 나머지 전략 전체를 막는다** (`main_loop.py` 171~220행). `run_one_cycle()` 자체는 `main()`의 try/except(284행)로 보호되지만, `for strat_name in STRATEGY_NAMES:` 루프 안에는 개별 try/except가 없다. 예를 들어 `lstm_predictor`의 모델 파일이 없거나 `predict_proba`가 예외를 던지면, 그 시점 이후 순서의 다른 조건식 전략들은 이번 사이클에서 신호 계산/매매/스냅샷 저장을 전혀 받지 못한 채 사이클이 통째로 스킵된다. 이미 처리된 앞선 전략들의 포트폴리오 저장은 남아있어 데이터 일관성 문제는 아니지만, "한 전략 문제가 다른 전략 가동률을 깎아먹는" 구조다.

2. **고정 60초 슬립 방식이라 사이클 실제 주기가 처리 시간만큼 매번 밀린다** (`main_loop.py` 281~302행). `run_one_cycle()` 수행 시간(API 6코인 호출+전략 10개 계산)과 재학습 체크 시간이 끝난 "뒤에" 60초를 더 기다리는 구조다. 다음 사이클 시작 시각을 절대시각 기준으로 맞추지 않으므로, 처리 시간이 늘어날수록(예: API 지연, 거래소 응답 느림) 실제 주기는 60초보다 계속 길어지며 이 지연이 누적된다. 1분봉 기반 전략이므로 몇 초 밀리는 것은 치명적이지 않지만, 장기 운영 시 "1분봉 하나를 통째로 건너뛰는" 상황이 생길 수 있는 구조적 여지가 있다.

3. **data_fetcher.py의 예외 처리 범위가 네트워크 오류로만 좁게 잡혀 있다** (`data_fetcher.py` 46~56행, 113~121행). `_http_get_json`은 `URLError/HTTPError/TimeoutError`만 재시도·래핑하고, `fetch_all_latest_candles`도 `except FetchError`만 잡는다. 만약 Upbit이 비정상 JSON(필드 누락 등)을 반환해 `_parse_minute_df`에서 `KeyError`/`pandas` 예외가 나면 `FetchError`가 아니므로 해당 코인 skip 없이 `fetch_all_latest_candles` 자체가 예외를 던지고, 결과적으로 1번 발견과 같은 "사이클 전체 스킵"으로 번진다.

4. **data_fetcher.py는 `print()`만 쓰고 `logging`을 쓰지 않아 run.log에 기록되지 않는다** (`data_fetcher.py` 120, 139, 153행). `main_loop.py`는 `logging`으로 콘솔+`run.log` 둘 다 남기지만, 캔들 수집 실패/히스토리 수집 실패 경고는 `print()`로만 나가 콘솔 출력이 캡처되지 않는 환경(서비스로 등록해 실행 시 등)에서는 사후 진단이 불가능해진다.

## 구체적 제안
- 전략 루프(171행)를 `try/except`로 감싸서 `log.exception(f"{strat_name} 처리 중 에러, 스킵")` 후 `continue`로 다음 전략으로 넘어가게 한다.
- `main()`의 while 루프(281행)를 `next_tick = time.monotonic() + CYCLE_INTERVAL_SEC` 방식으로 바꿔, 처리 시간을 차감한 나머지만 슬립하도록 수정한다(처리 시간이 60초를 넘으면 즉시 다음 사이클 진행).
- `data_fetcher.py`의 `_parse_minute_df`/`fetch_latest_minute_candles` 호출부를 `except Exception`으로 넓히고 `FetchError`로 재포장해 상위에서 일괄 처리되게 한다.
- `data_fetcher.py` 상단에 `import logging; log = logging.getLogger("data_fetcher")`를 추가하고 `print()`를 `log.warning()`으로 교체한다(단, `main_loop.py`의 `logging.basicConfig`가 루트 로거에 적용되므로 같은 핸들러를 공유하게 됨을 확인 필요).

## 리스크/트레이드오프
- 전략별 try/except 추가 시 예외를 삼키는 폭이 넓어져, 반복되는 설정 오류(예: 파라미터 타입 오류)가 조용히 매 사이클 반복될 위험이 있다 → 실패 카운트를 메타에 기록해 임계치 초과 시 별도 경고하는 보완이 필요.
- 절대시각 기준 틱 방식으로 바꾸면, 처리 시간이 60초를 초과하는 경우 슬립이 0이 되어 연속으로 즉시 재실행되므로 API 호출 빈도가 순간적으로 늘 수 있다 → 최소 슬립(예: 5초) 하한을 둘 것을 권장.
- 실제로 사이클이 밀리고 있는지, 어떤 전략이 얼마나 자주 예외를 내는지는 현재 코드만으로는 알 수 없고 운영 로그(run.log)를 봐야 판단 가능하다.
