## 한줄 요약
예외처리·사이클 타이밍·Upbit API 호출 패턴은 수십 차례의 보강을 거쳐 이미 매우 견고하며, 직전 두 회차(1326, 1418)에서 지적된 LSTM predict_proba 중복 호출과 force_full 부분성공 문제는 현재 코드에 모두 반영되어 있다. 새로 찾은 문제는 `data_fetcher.py`의 "멈춘 페이지네이션(stuck_count)" 탈출 경로가 `is_partial`을 True로 세팅하지 않는 누락 1건이다.

## 발견한 점 (우선순위 순)

**1) (신규, 중간 심각도) 멈춘 페이지네이션으로 break할 때 `is_partial=True`가 빠짐 — `local/data_fetcher.py` 325~335행**
`fetch_minute_history()`는 같은 `to` 파라미터가 3회 반복되면(API가 같은 페이지를 되돌리는 경우) 324~335행에서 `log.warning` 후 `break`하는데, 이 분기에는 `is_partial = True`가 설정되어 있지 않다(바로 아래 `max_pages` 도달 분기(345~349행)나 페이지 요청 실패 분기(297~311행)는 모두 `is_partial=True`를 세팅하지만 이 분기만 빠짐). 그 결과 `fetch_all_minute_history`의 `_fetch_one`(545행: `force_full and not is_partial`)이 이 경우를 "오늘 전체 재수집 완료"로 오인해 `last_full_refresh[coin]`을 기록한다(585~586행). 실제로는 목표 90일치보다 훨씬 적게 모은 상태인데도, 당일 남은 재학습 슬롯 동안 증분 수집만 반복되어 그 코인의 학습 데이터 창이 작게 고착된 채로 당일 복구되지 않는다. 로그도 `elif is_partial:`(531행) 분기를 타지 못해 "전체 재수집 완료"(540행)로 잘못 찍혀 사후 추적도 어렵다.

**2) (기존 일부 지적, 정상 경로는 미반영) 사이클 완료 후 progress 단계가 "cycle_running"/"training"에 멈춰 있음**
`main_loop.py` 전체에서 `set_progress("idle"...)`는 681행(최초 학습 후) 하나뿐이며, 매 사이클 정상 완료 시점에는 어떤 `set_progress` 호출도 없다(379/383/386행에서 찍은 뒤 다음 사이클 379행 "collecting"까지 그대로). 즉 60초 중 약 55초 이상 동안 대시보드의 progress.stage는 실제로는 "대기 중"인데도 "cycle_running"으로 표시된다. 2026-11-16_0917 리포트는 "예외 발생 시" 멈춘 상태를 지적했는데, 그 수정은 candles 실패 시 "error"(383행)만 추가됐을 뿐, 정상 완료 시의 "idle/sleeping 전환 누락" 자체는 지금도 그대로다. 워치독(heartbeat.txt, mtime 기반)에는 영향 없지만, 사람이 대시보드로 "진짜 멈춤"과 "정상 대기"를 구분하기 어렵다.

## 구체적 제안
1. `local/data_fetcher.py` 327~335행의 `stuck_count >= 3` 분기 안, `break` 직전에 `is_partial = True`를 추가한다. 한 줄 추가로 끝나고, 이후 `_fetch_one`의 force_full 판정과 로그 분기(531행 `elif is_partial:`)가 자동으로 올바르게 동작한다.
2. `local/main_loop.py`의 `run_one_cycle()` 끝부분(566행 `log.info("사이클 완료...")` 직후)에 `set_progress("idle", "대기 중")` 호출을 추가한다.

## 리스크/트레이드오프
- 제안 1은 기존에 있던 보호 패턴을 다른 분기와 동일하게 맞추는 것뿐이라 리스크가 거의 없다. 다만 "멈춘 페이지네이션" 자체가 자주 발생하면 그만큼 다음 슬롯에서 전체 재수집이 더 자주 재시도되어 API 호출이 소폭 늘 수 있다(기존 max_pages/stuck_count 로직이 과도한 반복은 이미 막아줌).
- 제안 2는 대시보드 표시만 바뀌는 순수 로깅 변경이라 매매 로직에는 영향 없다. 단, `set_progress()`가 매번 DB connect를 여는 구조(203~220행)이므로 사이클마다 호출이 1회 늘어 SQLite 쓰기가 아주 약간(짧은 commit 1회) 추가된다 — 영향은 미미하다.

**참고(운영데이터 필요 영역)**: 멈춘 페이지네이션(stuck_count)이 실제로 몇 번 발생했는지, 그로 인해 특정 코인의 학습 데이터 창이 실제로 축소된 적이 있는지는 코드만으로 알 수 없고 run.log 실측이 필요하다.
