## 한줄 요약
WAL 모드 + busy_timeout + 애플리케이션 레벨 재시도로 동시성 처리는 이미 잘 돼 있고, 가장 신경 써야 할 부분은 `predictions`/`model_trainings`처럼 계속 쌓이는 테이블에서 "최신순 정렬 + LIMIT" 조회가 인덱스를 완전히 못 타는 지점과, 보관주기(retention) 부재다.

## 발견한 점 (2~4개, 우선순위 순)

1. **`predictions` 테이블: `resolved` 단독 인덱스로는 "적중률 조회"가 느려질 수 있음** — `prediction_accuracy()`(storage.py 354-369행)는 `WHERE resolved=1 ORDER BY predicted_at DESC LIMIT ?`를 실행하는데, 현재 인덱스는 `idx_predictions_unresolved ON predictions(resolved)`(108행) 하나뿐이다. `resolved`만 걸린 인덱스로는 `resolved=1`인 행들을 모아놓고 별도로 `predicted_at` 정렬을 해야 하므로, `predictions`가 매 사이클·매 코인마다 1행씩 계속 쌓이면 `resolved=1` 행 수가 늘어날수록 이 정렬 비용이 커진다. `(coin, predicted_at DESC)` 인덱스(107행)도 `resolved` 조건과 결합되지 않아 `coin` 필터가 있는 호출(357행)에서도 동일한 문제가 있다.

2. **`model_trainings`: 코인 미지정 조회는 전체 스캔+정렬** — `model_training_history(coin=None)`(297-307행)은 `SELECT * FROM model_trainings ORDER BY timestamp DESC LIMIT ?`를 실행하지만, 존재하는 인덱스는 `idx_model_trainings_coin(coin, timestamp DESC)`(95행)뿐이라 `coin` 선두 컬럼을 못 써 전체 스캔이 재발한다. 다만 재학습 빈도가 거래/예측보다 훨씬 낮아 우선순위는 2번째로 낮춤.

3. **append-only 테이블(`predictions`, `model_trainings`)에 보관주기(retention)/삭제 로직이 storage.py 어디에도 없음** — `DELETE` 문이 코드 전체에 전혀 없다. `predictions`는 코인당 분당 1행씩 무한 누적되는 구조라 수개월~1년 운영 시 수백만 행 규모가 될 수 있다. 다만 실제로 이게 문제가 되는 시점(파일 용량, 쿼리 실측 속도)은 운영 중인 trading.db 실데이터를 봐야 판단 가능하므로 여기서는 "코드상 보관주기 메커니즘이 없다"는 사실만 확인한다.

4. **`portfolios` 테이블의 `<전략>__reset`/`<전략>__cumulative` 네이밍** — storage.py 44-48행 스키마는 `strategy TEXT PRIMARY KEY` 하나로만 돼 있어, "reset/cumulative" 구분이 PK 문자열 안에 `__` 구분자로 암묵적으로 인코딩되는 방식임을 알 수 있다(196-211행 `get_portfolio`/`set_portfolio`/`get_all_portfolios`는 strategy를 불투명한 문자열로만 다룬다). 전략명 자체에 `__`가 들어가면 파싱이 깨질 위험이 있고, "모든 reset 변형만 조회" 같은 쿼리를 하려면 `LIKE '%__reset'` 식의 패턴 매칭을 해야 한다.

## 구체적 제안

- storage.py 108행 `CREATE INDEX IF NOT EXISTS idx_predictions_unresolved ON predictions(resolved);`를 `CREATE INDEX IF NOT EXISTS idx_predictions_resolved_time ON predictions(resolved, predicted_at DESC);`로 교체(컬럼 추가). `resolve_predictions()`(327-351행)가 쓰는 `WHERE resolved=0` 조건도 이 복합 인덱스로 그대로 처리된다.
- 107행 `idx_predictions_coin`을 `ON predictions(coin, resolved, predicted_at DESC)`로 바꿔 `prediction_accuracy(coin=...)`(356-360행)의 `coin` + `resolved` + 정렬을 한 인덱스로 커버.
- 95행 뒤에 `CREATE INDEX IF NOT EXISTS idx_model_trainings_timestamp ON model_trainings(timestamp DESC);` 한 줄 추가해 `model_training_history(coin=None)`(305-307행) 경로를 인덱스로 처리.
- `portfolios` 스키마(44-48행)를 `strategy TEXT NOT NULL, variant TEXT NOT NULL DEFAULT 'reset', PRIMARY KEY(strategy, variant)`로 바꾸고, `get_portfolio`/`set_portfolio`/`get_all_portfolios`(196-211행)에 `variant` 파라미터를 추가하는 방식을 검토. 단, 이 변경은 storage.py만으로는 완결되지 않고 호출부(main_loop.py/dashboard.py에서 "__reset"/"__cumulative" 문자열을 조립·분해하는 부분)도 함께 바꿔야 하므로, 해당 호출부는 이 분석 범위(storage.py) 밖이라 별도 확인이 필요하다.

## 리스크/트레이드오프 (제안을 적용하면 생길 수 있는 부작용)

- 인덱스 추가(predictions, model_trainings)는 쓰기 비용을 약간 늘린다(매 INSERT/UPDATE마다 인덱스 갱신 1~2개 추가) — 다만 읽기 빈도(대시보드 새로고침)가 훨씬 잦은 시스템이라 순이익이 클 것으로 예상.
- `portfolios` PK를 `(strategy, variant)`로 바꾸면 기존 trading.db의 `strategy` 컬럼 값("xxx__reset" 형태 문자열)을 마이그레이션(분리)해야 하므로, 운영 중인 실제 DB 파일에 대한 1회성 데이터 마이그레이션 스크립트가 필요하고 호출부 코드도 동시에 바꿔야 해 리스크가 가장 크다 — 당장 급하지 않다면 보류하고 신규 전략 추가 시점에만 적용하는 것도 대안.
- retention(오래된 predictions/model_trainings 삭제) 도입 시, 대시보드의 "장기 추이" 그래프가 과거 데이터 일부를 잃게 되므로 삭제 대신 별도 아카이브 테이블/파일로 옮기는 방식이 더 안전할 수 있음 — 이 판단은 실제 보관 기간 요구사항(사용자가 몇 개월치 추이를 보고 싶은지)을 알아야 하며, 이는 코드만으로 결정할 수 없다.
