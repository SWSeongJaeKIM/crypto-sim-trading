## 한줄 요약
storage.py는 이미 여러 차례의 자체 분석 이력(주석에 명시된 analysis_team 리포트들)을 통해 인덱스/보관주기/동시성 문제를 대부분 해결한 상태이며, 실질적으로 남은 이슈는 적다.

## 발견한 점 (2~4개, 우선순위 순)

1. **(이미 해결됨, 확인됨)** predictions/snapshots/model_trainings는 모두 `prune_predictions`/`prune_snapshots`/`prune_model_trainings`로 보관주기가 구현돼 있고, `main_loop.py` 710~734행에서 날짜가 바뀔 때마다 실제로 호출되며 `PRAGMA wal_checkpoint(TRUNCATE)`까지 같이 수행한다. 쿼리 패턴(coin/strategy 필터, resolved 필터, ORDER BY timestamp)에 맞춰 복합 인덱스도 세분화되어 있다(storage.py 116~185행). 추가로 손댈 필요는 없어 보인다.

2. **공간 재사용은 되지만 파일 크기 자체는 줄지 않음 (우선순위 중)** `prune_*`가 행을 DELETE해도 SQLite 기본 `auto_vacuum=NONE` 상태라 해당 디스크 페이지는 "free list"로만 남고 trading.db 파일 크기는 줄지 않는다(이후 INSERT가 그 free list를 재사용하므로 장기적으로는 크기가 "증가 없이 안정화"되는 효과는 있지만, 사람이 파일 크기만 보고 "정리가 안 됐다"고 오판할 수 있음). 실제로 파일 크기가 안정화되는지, 아니면 계속 느리게 늘어나는지는 운영 중인 trading.db를 직접 봐야 판단 가능 — 이건 실제 운영 데이터를 봐야 판단 가능.

3. **predictions 테이블의 인덱스 3종 중첩 (우선순위 하, 참고용)** `idx_predictions_coin_resolved_time`, `idx_predictions_resolved_time`, `idx_predictions_resolved_coin_time` 세 개가 모두 유지되고 있다(storage.py 175, 176, 185행). 각각 서로 다른 쿼리 모양(코인 필터+정렬 / 전체 resolved+정렬 / coin별 파티션)에 대응하므로 불필요한 중복은 아니지만, predictions가 사이클마다(코인당 1분 1행) INSERT/UPDATE되는 가장 핫한 테이블이라 인덱스 3개 유지 비용이 쓰기 경로에 누적된다는 점은 트레이드오프로 인지하고 있으면 된다. 실제 코인 수가 적은 현재 규모에서는 문제될 수준은 아닐 것으로 보이나, 이는 실제 코인 수·쓰기 빈도를 봐야 확정 가능.

4. **portfolios 네이밍 방식은 이미 안전장치가 추가됨** `"<strategy>__<variant>"` 합성 키 자체는 여전히 쓰이지만, `make_portfolio_key`가 variant를 reset/cumulative로 제한하고 strategy 안에 구분자가 섞이는 것도 즉시 거부하도록 막아놔서(storage.py 70~76행) 과거에 우려됐던 "조용한 데이터 오분류" 리스크는 해소된 상태다. 정규화된 `(strategy, variant)` 복합 PK로 바꾸는 것이 스키마상으론 더 깔끔하지만, 기존 `portfolios.strategy` 데이터를 마이그레이션해야 하는 비용 대비 지금 당장 얻는 이득이 크지 않아 우선순위는 낮다.

## 구체적 제안
- (선택) trading.db 파일 크기가 실제로 계속 느리게 늘어나는 것이 운영 데이터로 확인되면, `connect()`의 PRAGMA 설정부(storage.py 252~263행) 근처에 스키마 최초 생성 시 1회 `PRAGMA auto_vacuum=INCREMENTAL`을 추가하고, 일일 prune 루틴(main_loop.py 729행 wal_checkpoint 다음 줄)에 `PRAGMA incremental_vacuum(N)`을 소량씩 추가 호출하는 방식을 검토. 단, `auto_vacuum` 모드는 빈 DB에서만 설정 가능하므로 기존 trading.db에는 `VACUUM` 1회 선행이 필요 — 운영 중 파일에 적용하려면 반드시 백업 후 유지보수 시간에 수동으로 진행해야 함(코드만으로 자동화하면 위험).
- 다른 항목들은 지금 구조를 바꿀 근거가 부족하므로 현재 상태 유지를 권장.

## 리스크/트레이드오프 (제안을 적용하면 생길 수 있는 부작용)
- `auto_vacuum=INCREMENTAL` 적용 시 기존 DB에 1회 `VACUUM`이 필요한데, 이는 DB 전체를 재작성하는 무거운 작업이라 그 순간만큼은 main_loop/dashboard 양쪽 접근이 막히거나 느려질 수 있음 — 반드시 트레이딩이 쉬는 시간대에, 백업 확보 후 수동 실행해야 하며 코드에서 자동 트리거하면 안 됨.
- `incremental_vacuum`을 일일 prune 루틴에 추가하면 그 날의 해당 사이클 커밋 시간이 소폭 늘어나, WAL 재시도/락 경합 창이 아주 조금 늘어날 수 있음(이미 WAL+busy_timeout+재시도 로직이 있어 치명적이진 않음).
