## 한줄 요약
WAL+재시도+사이클별 커넥션 재오픈 방식의 동시성 처리는 이번 코드에서도 견고하게 유지되고 있으나, 과거 회차부터 지적돼 온 `predictions`/`model_trainings`의 무제한 append-only 적재와 `portfolios`의 `"<전략>__reset"/"<전략>__cumulative"` 문자열 합성 키 인코딩은 이번 회차에도 수정되지 않고 그대로 남아 있다.

## 발견한 점 (우선순위 순)

1. **(미해결, 중) append-only 테이블에 retention 로직 없음** — `local/storage.py`의 `predictions`(91~103행), `model_trainings`(72~90행), `snapshots`(60~67행)는 삭제/정리 함수가 전혀 없다. `predictions`는 코인별로 매 사이클(약 1분)마다 1행씩 쌓이므로 코인 수×1년 기준 수백만 행 규모까지 커질 수 있다. 인덱스(`idx_predictions_coin`, `idx_predictions_unresolved`)가 있어 당장 쿼리 속도가 느려지진 않지만 DB 파일 크기·백업 비용은 시간에 비례해 계속 증가한다. 이 부분은 이전 리포트들에서 반복 지적됐는데 그대로다.

2. **(미해결, 낮음) `portfolios` PK의 문자열 합성 인코딩** — `storage.py` 44~48행 `portfolios` 테이블은 `strategy TEXT PRIMARY KEY` 하나뿐이고, `mode`(reset/cumulative) 구분은 DB 레벨 검증 없이 호출부 문자열에 의존한다. `local/main_loop.py` 112행 `portfolio_key()`가 `"<strategy>__<mode>"` 문자열을 만들고, `local/dashboard.py` 547행·566행에서 각각 `name.rpartition("__")`로 역파싱하는 동일 로직이 중복돼 있다. 과거에 `migrate_dual_portfolio.py`가 별도로 필요했던 전례가 이 설계의 마이그레이션 비용을 이미 보여준다.

3. **(개선 확인, 긍정적) 동시 쓰기/읽기 충돌 처리는 견고하게 유지되고 있음** — `connect()`(155~188행)는 WAL 모드+`busy_timeout`+애플리케이션 레벨 재시도(`_RetryingConnection`, 119~153행)를 갖추고 있고, `main_loop.py` 419~422행을 보면 `while not _stop:` 루프 **안에서 매 사이클마다** `with storage.connect() as conn: run_one_cycle(conn)`으로 커넥션을 새로 열고 닫는다(주석 389~391행에 명시). 즉 커넥션이 루프 전체 동안 길게 잠금을 들고 있지 않아, dashboard의 읽기와 충돌할 창이 짧다. 이 설계는 그대로 잘 유지되고 있어 추가 수정이 필요하지 않다.

4. **스키마/인덱스는 실제 쿼리 패턴에 맞음** — `idx_trades_strategy`, `idx_snapshots_strategy`, `idx_predictions_coin`, `idx_predictions_unresolved`가 각각의 `WHERE strategy=?/coin=?/resolved=0` + `ORDER BY timestamp DESC` 패턴과 일치한다(storage.py 59, 67, 102~103행). `get_all_portfolios`(196~198행)의 전체 스캔은 행 수가 전략×모드 조합 수로 제한돼 문제없다. `prediction_accuracy_by_coin`(363~365행)만 `SELECT DISTINCT coin` 후 코인별로 `prediction_accuracy`를 반복 호출하는데, 코인 수가 적으면(수개) 무시할 수준이다.

## 구체적 제안

- `local/storage.py`의 `prediction_accuracy_by_coin` 함수(363행) 아래에 `prune_predictions(conn, keep_days: int = 90)` 함수를 추가해 `DELETE FROM predictions WHERE resolved=1 AND predicted_at < datetime('now', ?)`(`-90 days` 전달)를 실행하고, `local/main_loop.py`의 일일 재학습 분기(`retrain_lstm` 호출 지점, 329행 부근)에서 하루 1회만 호출하도록 조건을 건다. `resolved=1`만 지워 미확정 예측은 보존한다.
- 위와 동시에 `snapshots`에도 동일 패턴으로 `prune_snapshots(conn, keep_days: int = 180)`을 추가할 수 있으나, 대시보드의 "최근 30개" 조회(`recent_snapshots`, 224~232행) 용도상 급하지 않으므로 predictions보다 낮은 우선순위로 둔다.
- `portfolios` 스키마를 `(strategy TEXT, mode TEXT CHECK(mode IN ('reset','cumulative')), data_json TEXT, updated_at TEXT, PRIMARY KEY(strategy, mode))`로 바꾸고 `get_portfolio`/`set_portfolio`/`get_all_portfolios` 시그니처에 `mode` 파라미터를 추가해, `main_loop.py` 112행과 `dashboard.py` 547·566행의 문자열 split 로직을 제거한다.

## 리스크/트레이드오프 (제안을 적용하면 생길 수 있는 부작용)

- `predictions` 삭제(retention)는 파일 상단 주석(24~30행)이 밝힌 "실전 적중률을 시간순으로 전부 보존"하려는 원래 설계 의도와 충돌할 수 있다. 분석팀이 장기 적중률 추이를 봐야 한다면 삭제 전에 일별/월별 집계 테이블을 먼저 만들어 요약을 보존하는 단계를 선행해야 한다.
- `portfolios` 복합 키 전환은 `storage.py` 밖의 `main_loop.py`, `dashboard.py`, `migrate_dual_portfolio.py` 호출부까지 함께 고쳐야 하는 마이그레이션이라 범위가 크다. 기존 `"__reset"/"__cumulative"` 형식 데이터를 1회 변환하는 스크립트가 필요하다.
- 실제 DB 파일 크기, 현재 행 수, 디스크 압박이 실제로 문제가 되고 있는지는 운영 데이터(trading.db)를 봐야 판단 가능하며, 이 분석만으로는 "지금 당장 급한지"를 단정할 수 없다.
