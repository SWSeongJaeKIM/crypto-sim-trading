## 한줄 요약
전체적인 예외 복구 구조는 탄탄하지만(사이클 단위 catch-all, 코인별 fetch catch), 전략 루프 내부에 보호장치가 없어 LSTM 등 특정 전략 하나가 터지면 해당 사이클 전체(5개 전략 전부)가 스킵되는 게 가장 큰 리스크다.

## 발견한 점 (2~4개, 우선순위 순)

1. **[High] 전략별 예외처리 부재 — 한 전략 장애가 전체 사이클을 죽임**
   `main_loop.py` 203~232번째 줄, `for strat_name in STRATEGY_NAMES:` 루프 안에서 `strat.signal_with_confidence(df)`나 `lstm_model.predict_proba(coin, df)` 호출에 try/except가 없다. 바깥 `main()`의 319~323번째 줄 catch-all이 예외를 잡아 "사이클 스킵"으로 처리하긴 하지만, 그 결과 조건식 전략 4개까지 포함해 **해당 사이클 전체가 거래 없이 날아간다**. 모델 파일 손상/누락, 데이터 길이 이상 등으로 LSTM 쪽만 터져도 나머지 4개 조건식 전략까지 같이 멈추는 구조다.

2. **[Medium-High] LSTM 재학습 실패 시 매분 재시도 폭주 가능**
   `main_loop.py` 326~331번째 줄: `retrain_is_due`가 true인 동안 재학습이 예외로 실패하면 `last_retrain_date`가 갱신되지 않아, 다음 사이클(60초 후)에 또 재시도한다. 재학습 1회가 6코인×수백 페이지 API 호출을 수반하므로, 실패 원인이 지속되는 경우(네트워크 장애, 디스크 쓰기 실패 등) 새벽 4시부터 자정까지 **매분 대량 API 호출을 반복**하게 될 수 있다.

3. **[Medium] 사이클 소요시간이 60초 슬립에 더해져 주기가 누적 지연됨**
   `main_loop.py` 337~340번째 줄은 `run_one_cycle()` 실행 시간과 무관하게 항상 60초를 추가로 더 잔다. 즉 실제 주기는 `60초 + 사이클 처리 시간`이 되어, 1분봉 신호를 매 분 정각 근처에서 읽는다는 전제가 서서히 어긋난다. 평상시엔 처리 시간이 짧아 체감 영향이 적겠지만, API 재시도(코인당 최대 3회×1~3초 백오프)가 겹치면 수십 초씩 늘어날 수 있다.

4. **[Medium] data_fetcher.py의 print()가 run.log로 남지 않음**
   `data_fetcher.py` 120, 139, 153번째 줄은 `print()`로 경고를 출력하는데, `main_loop.py`의 `logging.FileHandler("run.log")`는 `logging` 모듈 호출만 캡처한다. PC에 상주 서비스로 돌릴 때 stdout이 리다이렉트/버려지는 환경이면, 코인별 수집 실패 경고가 **파일 로그에 전혀 남지 않아** 사후 진단이 어려워진다.

## 구체적 제안

- `main_loop.py` 218~232번째 줄의 코인/전략 처리 블록 전체를 `try: ... except Exception as e: log.exception(f"[{strat_name}/{coin}] 신호 계산 실패, 스킵"); continue`로 감싸서 코인 단위로만 스킵되게 한다.
- `main_loop.py` 328번째 줄 재학습 실패 시 `storage.set_meta(conn, "last_lstm_train_failed_at", ...)` 같은 걸 남기고, 재시도 간격을 60초가 아니라 최소 30분 이상으로 벌리는 로직(예: 실패 후 다음 재시도까지 `timedelta(minutes=30)` 체크)을 추가한다.
- `main_loop.py` 319번째 줄에서 `cycle_start = time.monotonic()`을 찍고, 337번째 줄 슬립을 `max(0, CYCLE_INTERVAL_SEC - (time.monotonic() - cycle_start))`로 바꿔 드리프트를 보정한다.
- `data_fetcher.py`의 `print(...)` 호출(120, 139, 153번째 줄)을 `logging.getLogger("data_fetcher").warning(...)`로 바꾸고, `main_loop.py`의 핸들러 설정을 공유하도록 한다.

## 리스크/트레이드오프

- 코인 단위 try/except를 넓게 걸면 진짜 버그(타입 오류 등)도 "복구"로 처리되어 조용히 넘어갈 수 있으므로 반드시 `log.exception`으로 스택트레이스를 남겨야 한다.
- 재학습 재시도 간격을 늘리면 일시적 네트워크 장애였을 경우 정상 복구가 그만큼 늦어진다.
- 사이클 타이밍 보정은 처리 시간이 60초를 넘는 극단적 상황에서는 슬립이 0이 되어 바로 다음 사이클이 시작되므로, API 호출이 더 몰릴 수 있다(다만 현재도 같은 상황에서 이미 지연되고 있으므로 악화는 아님).

(참고: 위 리포트는 코드 구조/로직만 분석한 것이며, 실제 거래내역·손익·재학습 정확도 등 운영 데이터는 확인하지 않았다. "지금 실제로 수익이 나고 있는가" 같은 질문은 이 분석으로 답할 수 없고 실제 운영 데이터 확인이 필요하다.)
