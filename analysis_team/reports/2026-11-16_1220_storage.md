## 한줄 요약
WAL+재시도+사이클별 커넥션 재오픈 기반의 동시성 처리는 이번에도 견고하게 유지되고 있고, 스키마/인덱스도 현재 쿼리 패턴과 대체로 잘 맞는다. 다만 `predictions`/`model_trainings`의 무제한 append-only 적재에 보관주기가 없다는 점과 `portfolios`의 `"<전략>__reset"/"<전략>__cumulative"` 문자열 합성 키 설계는 여전히 남아 있는 구조적 이슈다.

## 발견한 점 (2~4개, 우선순위 순)

1. **(중) append-only 테이블에 retention 로직 전혀 없음** — `local/storage.py`의 `predictions`(91~103행)는 코인별로 매 사이클(약 1분)마다 `add_prediction`(311~319행)으로 1행씩 쌓이고, 삭제 함수가 코드 전체에 없다. 코인 수×가동 시간에 비례해 무한히 늘어난다. `idx_predictions_coin`, `idx_predictions_unresolved` 인덱스가 있어 당장 조회 속도 저하는 없지만, DB 파일 크기와 `prediction_accuracy`(345~360행)가 매번 `resolved=1` 전체를 훑는 비용은 시간에 비례해 커진다. `model_trainings`(72~90행)는 재학습 시마다만 쌓이므로 증가 속도는 느려 우선순위가 낮다.

2. **(낮음) `portfolios` PK의 문자열 합성 인코딩** — `storage.py` 44~48행 `portfolios` 테이블은 `strategy TEXT PRIMARY KEY` 하나뿐이고, reset/cumulative 모드 구분을 DB 스키마가 보장하지 않는다. `local/main_loop.py` 112행 `portfolio_key()`가 `f"{strategy}__{mode}"`를 만들고, `local/dashboard.py` 547행·566행에서 각각 `name.rpartition("__")`로 역파싱하는 로직이 호출부 두 곳에 중복돼 있다. 전략 이름 자체에 `__`가 들어가면 `rpartition`은 마지막 `__` 기준으로 잘리므로 우연히는 깨지지 않지만(전략명이 고정돼 있다는 가정에 의존), 설계상 강제되는 제약은 아니다. `migrate_dual_portfolio.py`가 별도 스크립트로 존재한다는 사실 자체가 이 인코딩 때문에 과거 1회 마이그레이션이 필요했음을 보여준다.

3. **(긍정적, 변경 불필요) 동시 쓰기/읽기 충돌 처리** — `connect()`(155~188행)는 WAL 모드 + `busy_timeout` + 애플리케이션 레벨 재시도(`_RetryingConnection`, 136~153행)를 갖추고, 예외 시 명시적 `rollback()`(185행)으로 잠금을 빨리 푼다. `main_loop.py`가 사이클마다 커넥션을 새로 열고 닫는 패턴과 결합되어 dashboard의 읽기와 충돌할 창이 짧다. 이 부분은 그대로 두면 된다.

4. **스키마/인덱스는 쿼리 패턴에 맞음** — `idx_trades_strategy`, `idx_snapshots_strategy`, `idx_predictions_coin/_unresolved`가 각 함수의 `WHERE strategy=?/coin=?/resolved=0 ORDER BY timestamp DESC` 패턴(226~245행, 292~308행, 322~342행)과 일치한다. `get_all_portfolios`(196~198행)의 WHERE 없는 전체 스캔은 행 수가 전략×모드 조합 수로 제한돼 있어 문제없다.

## 구체적 제안

- `local/storage.py`의 `prediction_accuracy_by_coin` 함수(363행) 아래에 `prune_predictions(conn, keep_days: int = 90)`을 추가하고, `DELETE FROM predictions WHERE resolved = 1 AND predicted_at < datetime('now', ?)`에 `f"-{keep_days} days"`를 바인딩해 실행한다. `resolved=1`만 지워 미확정 예측(다음 사이클에 확정 대기 중인 것)은 보존한다. `local/main_loop.py`의 일일 재학습 분기 근처에서 하루 1회만 호출하도록 조건을 건다.
- `portfolios` 스키마를 `(strategy TEXT, mode TEXT CHECK(mode IN ('reset','cumulative')), data_json TEXT, updated_at TEXT, PRIMARY KEY(strategy, mode))`로 바꾸고, `get_portfolio`/`set_portfolio`/`get_all_portfolios`에 `mode` 파라미터를 추가해 `main_loop.py` 112행, `dashboard.py` 547·566행의 문자열 split/합성 로직을 제거한다. 이는 범위가 큰 변경이라 다음 항목과 함께 고려.

## 리스크/트레이드오프 (제안을 적용하면 생길 수 있는 부작용)

- `predictions` 삭제는 파일 상단 주석(24~30행)이 밝힌 "실전 적중률을 시간순으로 전부 보존"하려는 설계 의도와 충돌할 수 있다. 장기 적중률 추이 분석이 필요하다면 삭제 전에 일별/월별 집계 테이블로 요약을 먼저 보존하는 단계가 선행돼야 한다.
- `portfolios` 복합 키 전환은 `storage.py` 밖의 `main_loop.py`, `dashboard.py`, `migrate_dual_portfolio.py` 호출부까지 함께 고쳐야 하는 마이그레이션이라 범위가 크고, 기존 `"__reset"/"__cumulative"` 문자열 키 데이터를 1회 변환하는 스크립트가 추가로 필요하다.
- DB 파일의 실제 현재 크기, `predictions` 행 수, 디스크/백업 부담이 지금 시점에 실제로 문제를 일으키고 있는지는 운영 데이터(trading.db)를 직접 봐야 판단 가능하며, 코드 구조만으로는 "지금 당장 급한지" 여부를 단정할 수 없다.
