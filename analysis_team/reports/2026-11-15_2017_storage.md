## 한줄 요약
스키마와 쿼리 설계는 현재 규모에서는 대체로 적절하지만, 동시 쓰기/읽기 시 락 경합과 predictions 테이블의 무제한 누적이 장기 운영 시 문제가 될 수 있다.

## 발견한 점 (우선순위 순)

1. **동시성: WAL 모드 미사용** (storage.py 106-115행 `connect()`). main_loop.py가 주기적으로 쓰는 동안 dashboard.py가 읽기를 시도하면, SQLite 기본 저널 모드(DELETE)에서는 쓰기 중 읽기가 블로킹될 수 있다. Python `sqlite3.connect()`의 기본 `timeout=5.0`초가 있어 짧은 충돌은 재시도로 넘어가지만, 트래픽이 늘면 "database is locked" 예외가 날 가능성이 있다.

2. **predictions 테이블의 무제한 누적 + 전체코인 조회의 비효율** (90-102행 스키마, 272-287행 `prediction_accuracy`). 코인별 인덱스(`idx_predictions_coin` = coin+predicted_at)는 `coin` 지정 조회엔 잘 맞지만, `prediction_accuracy(conn, coin=None)`처럼 coin 없이 `WHERE resolved=1 ORDER BY predicted_at DESC LIMIT`을 돌리는 경로(280-283행)는 이 인덱스를 못 쓰고 테이블 전체를 스캔+정렬해야 할 수 있다. 1분마다 코인당 1행씩 쌓이므로(6코인 기준 하루 약 8,600행) 몇 달 뒤엔 이 전체조회가 느려질 수 있다. 다만 "실제로 얼마나 느려지는지"는 실운영 DB 크기를 봐야 판단 가능.

3. **portfolios 키에 모드를 문자열로 인코딩** (`"<strategy>__reset"` / `"<strategy>__cumulative"`, 43-47행 스키마 + 128-133행 `set_portfolio`). dashboard.py 332-336행, 353-358행에서 `name.rpartition("__")`로 역파싱하고, "__"가 없으면 구버전으로 간주하는 fallback 로직이 두 곳에 중복돼 있다. migrate_dual_portfolio.py가 존재한다는 것 자체가 이 설계의 마이그레이션 비용을 보여준다.

4. **매 `connect()` 호출마다 `executescript(SCHEMA)` 재실행** (111행). dashboard.py가 폴링할 때마다 10개 `CREATE TABLE IF NOT EXISTS`/`CREATE INDEX IF NOT EXISTS` 문을 매번 재실행한다. 오류는 안 나지만 불필요한 반복 I/O다.

## 구체적 제안

- **storage.py 108행 근처**: `conn = sqlite3.connect(str(db_path))` 다음 줄에 `conn.execute("PRAGMA journal_mode=WAL")`, `conn.execute("PRAGMA busy_timeout=5000")` 추가. WAL 모드는 읽기와 쓰기가 서로 블로킹하지 않게 해주므로 main_loop(쓰기)와 dashboard(읽기) 충돌 가능성을 크게 줄인다.
- **storage.py 90-102행**: predictions에 `CREATE INDEX idx_predictions_resolved_time ON predictions(resolved, predicted_at DESC)` 추가하면 coin 없는 `prediction_accuracy` 조회가 인덱스를 탈 수 있다. 추가로 "N일 이상 지난 resolved=1 행 삭제" 같은 보관주기 함수(예: `prune_old_predictions(conn, keep_days=90)`)를 만들어 main_loop.py 주기 작업에 끼워넣는 것을 고려.
- **storage.py 43-47, 128-133행**: portfolios 테이블을 `PRIMARY KEY(strategy, mode)`로 바꿔 `strategy TEXT, mode TEXT CHECK(mode IN ('reset','cumulative'))` 컬럼을 분리하면 dashboard.py의 rpartition 파싱(332-336, 353-358행)이 필요 없어진다. 단, 이는 스키마 변경이라 마이그레이션 스크립트가 다시 필요함.
- **storage.py 106-115행**: `executescript(SCHEMA)`를 `connect()` 안이 아니라 프로세스 시작 시 1회만 실행하는 `init_db()`로 분리하고, `connect()`는 단순히 커넥션만 열도록 분리.

## 리스크/트레이드오프

- WAL 모드 전환은 `trading.db` 옆에 `-wal`/`-shm` 파일이 추가로 생기며, 비정상 종료 시 체크포인트가 덜 되어 파일이 커질 수 있음(주기적 체크포인트 또는 재시작으로 관리 필요).
- predictions 보관주기(prune)를 넣으면 "과거 전체 적중률 추이"를 더 이상 볼 수 없게 되므로, 대시보드에서 장기 추이 그래프가 필요하면 삭제 대신 별도 집계 테이블(일별 요약)을 두는 편이 안전함.
- portfolios 스키마 변경(strategy/mode 분리)은 기존 데이터 마이그레이션이 또 한 번 필요하고, dashboard.py/main_loop.py의 관련 코드도 함께 수정해야 하므로 작업 범위가 storage.py 밖으로 커짐.
