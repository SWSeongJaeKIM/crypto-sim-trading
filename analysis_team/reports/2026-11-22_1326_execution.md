## 한줄 요약
예외처리·사이클 타이밍·Upbit API 호출 패턴은 이미 상당히 촘촘하게 보강되어 있어 큰 문제는 없고, 새로 찾은 점은 LSTM 추론 중복 계산 1건과 로그 메시지 정확도 1건 정도의 경미한 수준이다.

## 발견한 점 (우선순위 순)

**1) lstm_predictor 전략에서 코인당 매 사이클 predict_proba가 두 번 실행됨 (main_loop.py 470~477행)**
`strat.signal_with_confidence(df)`(470행)는 내부에서 이미 `lstm_model.predict_proba(self.coin, df)`를 호출해 `prob_up`을 구한다(lstm_model.py 398행). 그런데 main_loop.py는 바로 다음 줄(475행)에서 같은 코인·같은 `df`로 `lstm_model.predict_proba(coin, df)`를 다시 호출해 예측 기록용 `prob_up`을 또 구한다. 모델 파일 자체는 `_loaded_models` 캐시(lstm_model.py 343~349행)로 재사용되지만, 특징 생성(`build_features`)과 모델 forward pass는 코인당 사이클마다 2회씩 실행된다(6코인×매분 = 하루 약 8,640회 불필요한 추가 추론). 지금은 모델이 작아 ms 단위라 체감 영향은 작지만, "사이클 처리시간이 60초에 근접하는 드리프트"를 감시하는 장치(CYCLE_ELAPSED_WARN_THRESHOLD_SEC, main_loop.py 81행)가 이미 있는 만큼, 숨어 있는 중복 비용은 모델이 커지거나 SEQ_LEN이 늘어날 때 먼저 체감될 수 있다.

**2) 코인별 예외 로그가 "신호 계산"과 "예측 기록 저장" 실패를 구분하지 못함 (main_loop.py 462~505행)**
같은 try 블록 안에 "신호 계산"(470행)과 "예측 기록 저장"(`storage.add_prediction`, 477행)이 함께 들어 있고, 실패 시 동일한 메시지("...신호 계산 중 에러...", 498/502행)로 로깅된다. `signals[coin]`은 이미 471행에서 할당된 뒤라 거래 로직 자체에는 영향이 없지만(이 점은 안전함), run.log만 보고 사후 진단할 때 "LSTM이 신호를 못 냈다"와 "신호는 정상이었는데 예측 기록 저장만 실패했다"를 구분할 수 없어, 실제로는 DB/디스크 문제인데 모델 쪽을 의심하게 될 수 있다.

## 구체적 제안

1. `lstm_model.py`의 `LSTMStrategy.signal_with_confidence`가 이미 계산한 `prob_up`을 (예: `self.last_prob_up` 속성으로) 보존하도록 하고, `main_loop.py` 474~477행에서 `lstm_model.predict_proba(coin, df)`를 재호출하는 대신 `strat.last_prob_up`을 읽어 `storage.add_prediction`에 넘긴다. 공용 인터페이스인 반환값 `(signal, confidence)` 자체는 바꾸지 않고 부가 속성만 추가하면 다른 전략(`strategies.py`)과의 호환성도 유지된다.
2. `main_loop.py` 474~477행의 `storage.add_prediction` 호출을 468~471행의 신호 계산과 분리된 작은 try/except로 감싸거나, 498/502행 로그 문구에 "(신호계산 실패 / 예측기록 저장 실패)" 식으로 실패 단계를 구분하는 표시를 추가한다.

## 리스크/트레이드오프

- 제안 1: `signal_with_confidence`에 부가 속성을 추가하는 방식이라 인터페이스 변경은 아니지만, 혹시 다른 호출부(dashboard, retrain_now.py 등)가 `predict_proba`를 독립적으로 다른 `df`로 재호출해 다른 값을 기대하는 경우가 있다면 통합 전에 "정말 같은 df를 쓰는지"를 한 번 더 확인해야 한다.
- 제안 2: try 블록을 분리하면 코드가 약간 늘고, `_warned_repeated_exception` 키 체계(494행 근처)에 구분자를 하나 더 추가해야 해 사소한 유지보수 비용이 생긴다. 다만 두 제안 모두 매매 판단 로직이나 예외 격리 구조 자체는 건드리지 않으므로 리스크는 낮다.
