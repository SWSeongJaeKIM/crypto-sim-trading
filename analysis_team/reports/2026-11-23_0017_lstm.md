## 한줄 요약
모델 구조(SEQ_LEN, LSTMClassifier)와 과적합 방지 장치는 데이터 규모 대비 적절하게 설계돼 있고, 가장 구체적으로 손볼 만한 지점은 파인튜닝 학습률 전략이 "과거 패턴 망각 방지"에만 치우쳐 있어 "최근 패턴 반영"이라는 원래 목적은 사실상 거의 못 채우고 있다는 점이다.

## 발견한 점 (우선순위 순)

1. **파인튜닝의 LR 하향이 forgetting 방지와 recency 반영, 두 목표를 동시에 해결하지 못함** (`lstm_model.py:164-171, 211, 223`). 매 재학습마다 `history_days`(실제로는 90일, 아래 3번 참고) 전체 윈도우를 다시 `build_dataset`해서 `torch.randperm`(223줄)으로 완전 랜덤 셔플 학습한다. 신규 데이터(재학습 간격 ~2.4시간치, 전체 ~13만 샘플 중 수백 개)도 과거 데이터와 동일한 가중치로 섞인다. `finetune_lr = lr/3`(211줄)로 낮추는 것은 전체 업데이트 폭을 줄여 "과거 패턴이 급격히 덮어씌워지는 것"은 막지만, 거꾸로 신규 데이터가 가중치에 반영되는 속도도 똑같이 늦춘다. 즉 하나의 LR 손잡이로 반대 방향인 두 목표(안 잊기 vs 최근 더 반영하기)를 동시에 조절하려는 구조라, 실질적으로는 "안 잊기" 쪽에만 작동한다.

2. **코인 간 상관관계 피처 미사용** (`FEATURE_COLS`, `lstm_model.py:84`). `main_loop.py`가 `fetch_all_minute_history`로 전체 코인 캔들을 한 번에 가져와 두고도, 코인별 `train_model`/`predict_proba` 호출 시 자기 코인 데이터만 넘긴다. 이미 메모리에 있는 데이터인데 활용 안 함.

3. **작업 지시문의 전제(하루 1회 재학습, 30일 학습)가 실제 코드와 다름.** 실제로는 `main_loop.py`의 `RETRAIN_TIMES_LOCAL`(하루 10회, 약 2.4시간 간격)과 `HISTORY_DAYS_FOR_TRAIN = 90`이다. 90일치 데이터량(코인당 ~13만 샘플) 자체는 1분봉처럼 신호 대비 잡음이 큰 과제에서 작은 모델(32-hidden, 1-layer)을 학습시키기엔 충분하고, 10회/일 빈도도 과도하진 않다. 다만 매번 거의 동일한 90일 윈도우를 재사용하는 구조가 1번 문제의 원인이다.

4. **SEQ_LEN=60, LSTMClassifier(hidden=32, layers=1) 자체는 이미 적절함.** RSI14/MACD(26)/BB(20) 등 지표 계산 창보다 넉넉하고, 코드 자체 주석이 밝히는 "val_accuracy 54~62%"(50-59줄)라는 낮은 신호 대비 잡음 환경에서 모델을 크게 키우면 과적합만 커진다. `val_frac` 분리, train/val 겹침 제거(196줄), `VAL_ACC_ROLLBACK_THRESHOLD` 안전장치가 이미 갖춰져 있어 이 축은 손댈 필요 없음.

## 구체적 제안
- `lstm_model.py` 224-232줄의 미니배치 루프에서 `loss_fn`을 `nn.BCEWithLogitsLoss(reduction="none")`으로 바꾸고, 샘플 인덱스(시퀀스 끝 시점)가 최근일수록 큰 weight(예: 지수 감쇠)를 주는 벡터를 곱한 뒤 평균내는 weighted loss로 교체. 이러면 LR은 낮게 유지해 과거 패턴을 급격히 안 잊으면서도, 신규 데이터의 기울기 기여도는 별도로 높일 수 있다.
- `FEATURE_COLS`(84줄)에 기준 코인(예: BTC) 1분 수익률 컬럼을 추가. `main_loop.py`에서 이미 전체 코인 df를 들고 있으므로 `train_model`/`predict_proba`에 basket df를 추가 인자로 넘기고 `build_features`에서 타임스탬프 정렬 후 병합.

## 리스크/트레이드오프 (제안을 적용하면 생길 수 있는 부작용)
- Recency weighting을 넣으면 최근 짧은 구간의 급변동/이상치에 모델이 과하게 반응해 `val_accuracy_confident`가 오히려 불안정해질 수 있어, `VAL_ACC_ROLLBACK_THRESHOLD` 모니터링을 더 자주 확인할 필요가 있다.
- 상관코인 피처는 입력 차원 증가로 파라미터가 약간 늘고, 코인별 결측/지연 데이터 정렬 로직이 추가로 필요해 구현 복잡도가 커진다.
- 오더북 스프레드 피처는 `data_fetcher.py` 전체에 bid/ask/depth 관련 수집 코드가 없어, 코드 수정만으로는 추가할 수 없고 새 데이터 소스 연동이 선행돼야 한다.
- 실제 val_accuracy 추이, 손익과의 상관관계 등은 운영 데이터를 봐야 판단 가능 — 코드만으로는 결론 내릴 수 없다.
