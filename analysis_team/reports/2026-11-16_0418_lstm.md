## 한줄 요약
피처와 재학습 주기/데이터 기간 설계는 전반적으로 합리적이나, 파인튜닝이 "이어서 미세조정"이 아니라 매일 거의 전체 재학습과 동일하게 동작하고 val_accuracy를 전혀 활용하지 않는 점이 가장 눈에 띄는 개선 포인트입니다.

## 발견한 점 (2~4개, 우선순위 순)

1. **파인튜닝이 사실상 "매일 전체 재학습"과 구분되지 않음** (`lstm_model.py:134-141`): `resumed_from_existing`이 True여도 `lr`(1e-3)과 `epochs`(main_loop.py에서 고정 8)가 최초 학습과 동일합니다. 파인튜닝 시 가중치만 이어받고 학습강도는 그대로이므로, docstring(17-19행)이 의도한 "가볍게 최근 패턴 반영"이 아니라 매번 30일치 데이터 전체를 사실상 재학습하는 것과 거의 같습니다. 이건 "나쁨"이 아니라 설계 의도와 실제 동작이 불일치한다는 점이 문제입니다.

2. **val_accuracy를 계산만 하고 아무 데도 쓰지 않음** (`lstm_model.py:162-168`): 검증 정확도를 구해서 리턴값에 넣지만, early stopping이나 "최고 성능 epoch 가중치 선택"에는 전혀 사용되지 않고 무조건 마지막 epoch의 가중치를 저장합니다. 8 epoch 동안 val_acc가 중간에 더 좋았다가 과적합으로 떨어져도 그대로 저장되는 구조입니다.

3. **피처에 OHLC 중 open/high/low가 전혀 쓰이지 않음** (`lstm_model.py:41-65`): FEATURE_COLS(ret, vol_chg, rsi14, macd_hist, bb_pctb) 모두 close와 volume에서만 파생됩니다. 캔들의 몸통/꼬리 비율이나 고저 range 같은 "캔들 내부 구조" 정보, 그리고 BTC 등 대형코인의 동시 움직임(시장 베타) 정보가 빠져 있어, 1분 뒤 방향성 예측에 쓸 수 있는 정보를 일부 버리고 있습니다.

4. **SEQ_LEN/모델 구조 대 데이터량**: hidden=32, 1-layer LSTM은 30일×6코인 1분봉(코인당 수만 샘플) 대비 파라미터 수가 작아 과적합 위험은 낮습니다. 재학습 주기(1일 1회)+데이터기간(30일)도 CPU 학습 부담과 크립토 1분봉 특성을 고려하면 무리한 선택은 아닙니다. 이 부분은 실제 val_accuracy 추이를 봐야 최종 판단 가능하지만, 코드 구조만으로는 특별한 결함이 보이지 않습니다.

## 구체적 제안

- `lstm_model.py:136-141` 부근: `resumed_from_existing` 여부에 따라 학습강도를 분리합니다. 예: `ft_lr = lr * 0.3 if resumed_from_existing else lr`, `ft_epochs = max(3, epochs // 2) if resumed_from_existing else epochs`로 분기한 뒤 opt 생성과 학습 루프(150행)에 이 값을 사용. 이렇게 하면 최초 학습은 충분히, 매일 파인튜닝은 더 가볍게 "최근 패턴 미세조정"답게 동작합니다.
- `lstm_model.py:148-168`: 학습 루프 안에서 epoch마다 val_acc를 측정하고 `best_val_acc`/`best_state_dict`를 추적해, 168행 저장 시 마지막 epoch 대신 최고 검증 성능 시점의 state_dict를 저장하도록 변경.
- `lstm_model.py:45-65`: `feat["hl_range"] = (df["high"] - df["low"]) / close`처럼 캔들 range 피처를 FEATURE_COLS에 추가. 타코인 상관관계(예: BTC ret)는 `build_features`에 선택적 `market_ret: pd.Series | None` 파라미터를 추가하고, `main_loop.py`의 `retrain_lstm`/추론 호출부에서 BTC df의 ret를 같은 타임스탬프로 정렬해 넘기는 방식으로 확장 가능.

## 리스크/트레이드오프

- 파인튜닝 lr/epoch을 낮추면 시장 레짐이 급변했을 때(예: 급등락 장) 새 패턴 반영이 느려질 수 있어, `HISTORY_DAYS_FOR_TRAIN`(30일)과의 균형을 같이 재점검할 필요가 있습니다.
- best-epoch 저장 방식은 val set이 시간적으로 가장 최근 15% 구간이라, "가장 최근 패턴에 맞는 모델"이 아니라 "검증구간에 최적인 모델"을 고를 위험이 있어 과거쪽에 살짝 치우칠 수 있습니다.
- BTC 상관 피처 추가는 데이터 수집/정렬 로직(`main_loop.py`, `data_fetcher.py`)까지 건드려야 해서 변경 범위가 커지고, 코인 간 타임스탬프 미스매치 시 버그 유입 가능성이 있습니다.
