## 한줄 요약
스키마와 인덱스는 전반적으로 쿼리 패턴에 맞게 잘 설계되어 있으나, 동시 접근(WAL 미설정)과 전략명 없는 `trades` 조회, `portfolios` 키 인코딩 방식에서 장기적으로 개선 여지가 있다.

## 발견한 점 (우선순위 순)

1. **동시 쓰기/읽기 충돌 가능성** — `storage.py` 107~115줄 `connect()`는 `sqlite3.connect()` 호출 후 WAL 모드나 `busy_timeout`을 설정하지 않는다. `main_loop.py`는 매 사이클(1분)마다 쓰기 트랜잭션을 열고, `dashboard.py`는 15초마다(`setInterval(load, 15000)`, 376줄) `/api/data`에서 읽기 트랜잭션을 연다. SQLite 기본 저널 모드(rollback journal)에서는 쓰기 중 읽기가 차단되거나 그 반대가 발생할 수 있고, Python sqlite3 기본 타임아웃(5초) 내에 끝나지 않으면 `database is locked` 예외가 날 수 있다. 지금은 트랜잭션이 짧아 운 좋게 안 터질 가능성이 높지만, 데이터가 쌓여 트랜잭션이 길어지면 터질 소지가 있는 구조적 리스크다.

2. **`recent_trades`의 전체 스캔(WHERE 없는 조회)** — `storage.py` 168~171줄, `strategy`가 없을 때 `SELECT * FROM trades ORDER BY timestamp DESC LIMIT ?`를 실행한다. 기존 인덱스 `idx_trades_strategy(strategy, timestamp DESC)`(58줄)는 `strategy` 조건이 없는 이 쿼리에는 쓰이지 않아 전체 테이블 스캔+정렬이 일어난다. 이 함수가 `dashboard.py` 428줄에서 15초마다 호출되므로, `trades`가 append-only로 계속 쌓이면(실제 트레이딩 데이터라 코드만으로는 증가 속도를 알 수 없음) 점점 느려질 구조다.

3. **`portfolios` 키의 `"<strategy>__reset"/"<strategy>__cumulative"` 인코딩** — `storage.py` 자체 스키마는 `strategy TEXT PRIMARY KEY` 하나뿐이고, 모드 구분은 문자열에 묻어 저장한다. 소비 측(`dashboard.py` 411줄, 430줄)에서 `name.rpartition("__")`로 역파싱하는 동일 로직이 두 군데 중복돼 있고, 전략명 자체에 `"__"`가 포함되면 오파싱될 위험이 있다. 데이터 모델 차원에서 `mode` 컬럼이 없는 것이 유지보수성을 떨어뜨린다.

4. **`predictions`/`model_trainings`의 보관주기 부재** — append-only로 영구 누적되지만 인덱스(`idx_predictions_coin`, `idx_predictions_unresolved`)는 쿼리 패턴에 맞게 잘 설계돼 있어 조회 성능 자체는 당장 문제없다. 다만 실제로 몇 달~몇 년 뒤 DB 파일 크기가 얼마나 커질지는 실제 운영 데이터(누적 행 수)를 봐야 판단 가능하다.

## 구체적 제안
- `storage.py` 108번째 줄 `conn = sqlite3.connect(...)` 다음에 `conn.execute("PRAGMA journal_mode=WAL")`와 `conn.execute("PRAGMA busy_timeout=5000")`를 추가해 리더/라이터 충돌을 실질적으로 없앤다.
- `storage.py` SCHEMA 58번째 줄 근처에 `CREATE INDEX IF NOT EXISTS idx_trades_timestamp ON trades(timestamp DESC);`를 추가해 전략 미지정 `recent_trades` 조회를 인덱스 스캔으로 바꾼다.
- `dashboard.py`에 중복된 `rpartition("__")` 파싱을 `storage.py`에 `parse_portfolio_name(name)` 헬퍼로 추출해 한 곳에서만 관리한다. (PK를 `(strategy, mode)`로 분리하는 것은 더 근본적이지만 마이그레이션 비용이 크므로 지금은 헬퍼 추출이 안전한 절충안.)

## 리스크/트레이드오프
- WAL 전환 시 `-wal`/`-shm` 파일이 추가로 생겨, DB 파일만 단순 복사하는 백업 방식이면 최근 쓰기가 유실될 수 있다(체크포인트 필요).
- 신규 인덱스는 `add_trades`의 매 INSERT마다 유지 비용이 소폭 늘지만 미미한 수준이다.
- `portfolios` PK를 바꾸는 근본적 리팩터링은 기존 데이터 마이그레이션(이미 있는 `migrate_dual_portfolio.py`류 1회성 스크립트)이 또 필요해 운영 중단/오류 리스크가 있다.
- predictions/model_trainings 보관주기는 "시간순 전부 보존"이라는 설계 의도(21~23줄 주석)와 상충하므로, 삭제보다 아카이브 테이블 분리가 더 적합하며 이는 실제 데이터 크기를 본 뒤 판단할 사항이다.
