## 한줄 요약
전체적인 예외처리 구조(사이클 단위 try/except, 포트폴리오 reset 로직)는 견고하지만, 네트워크 장애 시 사이클 지연이 복합적으로 커질 수 있는 지점과 `print()`/`logging` 혼용으로 인한 진단 공백이 있다.

## 발견한 점 (2~4개, 우선순위 순)

1. **(높음) 장애 시 사이클 지연이 누적될 수 있는 구조** — `data_fetcher.py` 46~56행의 `_http_get_json`은 코인 1개당 최대 3회 재시도(`timeout=10s` + backoff 1+2+3초)를 하고, `fetch_all_latest_candles`(113~121행)는 6코인을 **순차** 호출한다. 네트워크가 전반적으로 불안정해지면 코인당 최악 약 33~36초가 걸릴 수 있고 6코인이면 한 사이클이 수분까지 늘어날 수 있다. 그런데 `main_loop.py` 337~340행은 `run_one_cycle` 실행이 끝난 "후"에 추가로 고정 60초를 더 기다리는 구조라, 작업 시간이 길어져도 그 뒤에 또 60초가 붙는다(실제 주기 = 작업시간 + 60초). 일시적 장애가 반복되면 사이클 주기가 설계값인 60초에서 점점 벌어질 수 있다.

2. **(중간) `print()`와 `logging` 혼용으로 run.log에 기록되지 않는 경고** — `data_fetcher.py`의 120, 139, 153행(코인별 수집 실패 경고)은 `print()`를 쓰는데, `main_loop.py` 53~57행의 `logging.FileHandler("run.log")`는 `logging` 모듈로 남긴 것만 파일에 기록한다. 즉 캔들/히스토리/현재가 수집 실패 경고는 콘솔에만 뜨고 `run.log`에는 남지 않는다. 서비스로 상주 실행 시(파일 docstring에 명시된 운영 방식) 콘솔을 계속 보고 있지 않으면 어떤 코인이 왜 실패했는지 사후 진단이 불가능하다.

3. **(중간) 초기 모델 존재 체크가 `any()`라 부분 누락을 못 잡음** — `main_loop.py` 307행 `has_any_model = any((...).exists() for c in COINS)`는 6개 코인 중 1개만 모델 파일이 있어도 `True`가 되어 최초 학습을 건너뛴다. 예를 들어 BTC 모델 파일만 삭제/손상된 상태로 재시작하면, 그 코인에 대해서만 모델이 없는 상태로 매 사이클 `predict_proba` 호출이 들어가게 되고(해당 처리는 `lstm_model.py` 쪽 책임이라 이 파일 범위 밖), 만약 그쪽에서 예외가 나면 `run_one_cycle` 전체가 320~323행 try/except에 걸려 "그 사이클 전체"가 스킵된다 — 한 코인 문제가 전체 사이클에 영향을 줄 수 있는 구조.

4. **(낮음) 히스토리 페이지네이션 중 실패 시 이미 모은 데이터 버림** — `fetch_minute_history`(83~104행)는 반복문 안에서 `_http_get_json`이 예외를 던지면 그대로 전파되고, 이미 쌓아둔 `all_rows`는 폐기된다. 호출부인 `fetch_all_minute_history`(138~141행)는 `FetchError`를 잡아 디스크 캐시 전체로 대체하므로, 101번 페이지 호출 중 100번째에서 실패해도 그 코인은 통째로 과거 캐시로 돌아간다(치명적이진 않지만 비효율).

## 구체적 제안
- `main_loop.py` 337행 전후: `run_one_cycle` 시작 시각을 기록해 `elapsed = time.time() - start`로 측정하고, `sleep_remaining = max(0, CYCLE_INTERVAL_SEC - elapsed)`만큼만 대기하도록 바꾸면 고정 60초 주기에 더 가깝게 맞출 수 있다(단, 아래 트레이드오프 참고).
- `data_fetcher.py` 120, 139, 153행: `print(...)` → `import logging`하여 `logging.getLogger("data_fetcher").warning(...)`로 교체. `main_loop.py`와 동일한 루트 로거 설정을 쓰면 `run.log`에도 남는다.
- `main_loop.py` 307행: `any(...)` → `all(...)`로 바꿔 코인 중 하나라도 모델이 없으면 전체 재학습을 돌리게 하거나, 최소한 누락된 코인 목록을 로그로 남기고 해당 코인만 개별 학습하는 분기를 추가.
- `data_fetcher.py` 91~104행: for 루프 본문을 try/except로 감싸 중간 실패 시 `all_rows`에 모인 데이터까지는 리턴하도록(부분 데이터 + 경고 로그) 수정하면 캐시 전체 폴백보다 최신성이 보존된다.

## 리스크/트레이드오프 (제안을 적용하면 생길 수 있는 부작용)
- 제안 1(경과시간 보정)을 적용하면 장애가 길어질 때 사이클이 밀리지 않고 거의 바로 재시도하게 되어, 오히려 Upbit API에 더 빈번히 재요청하며 rate limit에 더 쉽게 걸릴 수 있다. 최소 대기시간(예: 5~10초)의 하한을 두는 것이 안전하다.
- `any()` → `all()`로 바꾸면 코인 1개 모델만 없어도 6개 전체를 재학습하게 되어, 모델 파일이 우연히 하나 지워진 경우에도 불필요하게 전체 학습 시간(수 분)이 소요될 수 있다. "코인별 개별 체크 후 누락분만 학습"이 더 정밀하지만 구현 범위가 커진다.
- print→logging 전환은 리스크가 거의 없으나, 로그 레벨을 WARNING으로 맞춰야 INFO 레벨 로그와 혼재되어도 필터링이 가능하다는 점을 유의해야 한다.

(실제 운영 중 거래/손익/학습 정확도 데이터는 이 분석에서 보지 않았으며, 위 내용은 코드 로직만을 근거로 판단한 것이다.)
