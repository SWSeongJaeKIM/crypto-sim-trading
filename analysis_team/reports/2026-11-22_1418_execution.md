## 한줄 요약
Upbit API 호출 패턴·사이클 60초 타이밍·예외 격리는 이미 촘촘하게 보강되어 있고, 새로 확인한 핵심 이슈는 data_fetcher.py의 "강제 전체 재수집(force_full)" 마커가 부분 성공만으로도 "완료"로 기록되는 1건이며, 부가로 main_loop.py의 LSTM predict_proba 중복 호출(직전 회차에 지적되었으나 아직 코드에 미반영)이 남아있다.

## 발견한 점 (우선순위 순)

**1) data_fetcher.py 494~556행: force_full 부분 성공이 "오늘 완료"로 영구 기록됨**
`fetch_minute_history()`는 페이지 수집 중 실패해도 이미 목표의 80% 이상 모았으면 예외 없이 부분 데이터를 정상 반환한다(254~296행). `_fetch_one`(494~515행)은 이 부분 반환을 구분하지 못하고 `return coin, df, force_full`(515행)로 그대로 넘기며, 552~553행에서 `last_full_refresh[coin] = today_str`가 기록된다. force_full 시도 중엔 479행 조건(`if not force_full and ...`)에 의해 기존 캐시(cached_df)를 참조하지 않으므로 병합이 일어나지 않고, 부분결과가 그대로 캐시 CSV에 덮어써진다(507~508행). 결과적으로 그 코인은 당일 남은 최대 9번의 재학습 슬롯(RETRAIN_TIMES_LOCAL) 동안 "오늘 전체 재수집 이미 함"으로 취급되어 증분 수집만 하게 되고, 학습 데이터 창(HISTORY_DAYS_FOR_TRAIN=90일)이 실패 시점 수집량(예: 72일)으로 줄어든 채 유지된다. 오래된 쪽 끝만 비는 구조라 며칠~2주 정도면 증분 누적으로 자연 회복되지만, 그 기간 동안 "데이터가 줄어든 채 학습 중"이라는 사실이 fetch_minute_history 내부의 1회성 log.warning으로만 흘러가 사후 추적이 어렵다.

**2) main_loop.py 470~477행: LSTM predict_proba 중복 호출 (여전히 미반영)**
lstm_predictor 전략에서 코인당 매 사이클 `predict_proba`가 `signal_with_confidence`(470행) 내부와 예측기록 저장용(475행) 두 번 호출된다. 거래 로직에는 영향 없음(신호는 471행에서 이미 확정)이지만 특징생성+forward pass가 6코인×1분마다 중복 실행된다. 이 건은 직전 분석 회차(2026-11-22_1326_execution/synthesizer, Top3 #2)에서 이미 동일하게 지적되어 적용 대기 상태였는데, 현재 코드(git log 기준 최신 커밋 233e6d2)에는 아직 반영되지 않아 재확인 차원에서 다시 기록한다.

## 구체적 제안
1. data_fetcher.py: `fetch_minute_history`가 부분 반환인지 알 수 있는 신호(예: `(df, is_partial)` 튜플 또는 부분반환 시 콜백/플래그)를 추가하고, `_fetch_one`에서 `is_partial`이면 552~553행의 `last_full_refresh[coin] = today_str` 기록을 생략한다. 그러면 같은 날 다음 재학습 슬롯에서 전체 재수집을 다시 시도해 더 빨리 복구된다.
2. main_loop.py: `LSTMStrategy.signal_with_confidence`가 계산한 `prob_up`을 속성(예: `strat.last_prob_up`)에 보존하고 474~477행에서 재호출 대신 그 값을 사용한다.

## 리스크/트레이드오프
- 제안 1은 `fetch_minute_history`의 반환 시그니처를 바꾸므로 다른 호출부(단독 스크립트 등)가 있다면 함께 수정해야 하고, "부분 성공도 당일 1회로 소진"하던 기존의 재시도-폭주 방지 설계를 완화하는 것이므로, 같은 코인이 반복해서 부분 실패하면 당일 전체 재수집이 여러 번 재시도되어 API 호출이 늘 수 있다 — 코인당 당일 재시도 횟수 상한을 함께 두는 것이 안전하다.
- 제안 2는 인터페이스 변경이 작지만, dashboard.py나 retrain_now.py 등 다른 predict_proba 호출부가 같은 df로 재계산되길 기대하지 않는지 먼저 확인해야 한다(지난 보고서도 동일하게 지적).

**참고(운영데이터 필요 영역)**: 실제로 force_full 부분 실패가 얼마나 자주 발생했는지, 그로 인해 특정 코인의 학습 데이터 창이 실제로 축소된 적이 있는지는 코드만으로는 알 수 없고 run.log/trading.db의 실제 수집 이력을 봐야 판단 가능하다.
