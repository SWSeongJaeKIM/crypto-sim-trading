## 한줄 요약
전반적인 예외처리 구조는 괜찮으나(사이클 단위 try/except로 프로세스 자체는 죽지 않음), 최초 모델 학습 경로 하나가 이 보호막 밖에 있고, data_fetcher.py의 로깅이 run.log에 남지 않는 점, 사이클 타이밍이 처리시간을 보정하지 않는 점은 실제로 고쳐볼 만하다.

## 발견한 점 (우선순위 순)

1. **최초 LSTM 학습이 예외처리 밖에 있음 (main_loop.py 306~310줄)** — `main()`의 `while` 루프 진입 전, `has_any_model`이 False일 때 호출하는 `retrain_lstm(conn)`에는 try/except가 없다. while 루프 안의 `run_one_cycle`/`retrain_lstm` 호출은 각각 보호되어 있는데(320~331줄), 이 최초 학습 호출만 보호가 안 돼 있어 네트워크 일시 장애나 학습 중 예외가 나면 PC에 상주해야 할 프로세스 자체가 시작도 못 하고 죽는다. 사이클을 "죽이지 않는다"는 설계 의도와 어긋나는 유일한 지점.

2. **data_fetcher.py는 logging이 아니라 print() 사용 (120, 139, 153줄)** — main_loop.py는 `logging`으로 콘솔+run.log에 동시 기록하지만, data_fetcher.py의 모든 경고(`[WARN] ... 수집 실패`)는 `print()`라서 콘솔에만 뜨고 run.log 파일에는 전혀 남지 않는다. 서비스로 백그라운드 등록해 stdout이 버려지거나 로테이션되는 환경이면, 실제 API 실패 이력이 통째로 사라져 사후 진단이 불가능해진다.

3. **사이클 주기가 처리시간을 보정하지 않음 (main_loop.py 337~340줄)** — `for _ in range(CYCLE_INTERVAL_SEC): time.sleep(1)`은 "항상 60초를 더 잔다"는 뜻이라, 실제 사이클 간격은 `run_one_cycle 소요시간 + 60초`가 된다. 누적 지연(backlog)은 아니지만, API 재시도(최대 3회×1~3초)가 여러 코인에서 겹치면 간격이 느슨하게 늘어난다. 더 크게는 326~331줄의 재학습이 while 루프 안에서 동기적으로 실행되므로, 재학습 중(수 분)에는 매매 사이클이 전혀 돌지 않는다 — 하루 한 번이라 의도된 트레이드오프로 보이나 문서상 "60초 고정"과는 실제가 다르다.

4. **전략 단위 예외 격리가 없음 (203~253줄)** — `run_one_cycle` 전체가 바깥의 단일 try/except(320~323줄)로만 보호되므로, 5개 전략 중 하나(예: lstm_predictor가 특정 코인 모델 파일 문제로 예외)가 터지면 그 사이클의 나머지 전략들도 포트폴리오 저장/스냅샷 기록까지 통째로 스킵된다.

## 구체적 제안

- main_loop.py 308~310줄을 `try: retrain_lstm(conn) except Exception: log.exception(...)`로 감싸고, 실패 시 "모델 없이 lstm_predictor 비활성 상태로 시작"을 로그로 명시.
- data_fetcher.py에 `import logging; log = logging.getLogger("data_fetcher")`를 추가하고 120/139/153줄의 `print(f"[WARN] ...")`를 `log.warning(...)`로 교체(핸들러는 main_loop의 root logger 설정을 그대로 상속받으므로 run.log에도 남음).
- main_loop.py 319~340줄에서 `cycle_start = time.monotonic()`을 run_one_cycle 호출 전에 찍고, sleep 루프를 `remaining = max(5, CYCLE_INTERVAL_SEC - (time.monotonic() - cycle_start))`로 바꿔 실제 경과시간을 보정하고 로그에 "이번 사이클 소요 Xs"를 남긴다.
- 203~253줄의 `for strat_name in STRATEGY_NAMES:` 루프 본문을 try/except로 감싸 전략 1개 실패가 나머지 전략에 영향 주지 않게 한다.

## 리스크/트레이드오프 (제안을 적용하면 생길 수 있는 부작용)
- 최초 학습 실패를 삼키면 모델 없이 조용히 기능 저하 상태(lstm_predictor 무력화)로 계속 돌 수 있어, 로그를 안 보면 사람이 못 알아챌 위험 — 경고 로그 레벨을 ERROR로 명확히 구분해야 함.
- sleep 보정 시 처리시간이 60초를 넘기면(특히 재학습 직후) 거의 즉시 다음 사이클이 시작돼 API 호출 빈도가 순간적으로 올라갈 수 있음 — 최소 sleep(위 제안에서 5초)을 반드시 둬야 함.
- 전략별 try/except 세분화는 특정 전략이 계속 실패할 경우 매 사이클 동일 에러가 반복 로깅되어 로그량이 늘어날 수 있음 — 필요하면 동일 에러 반복 시 로그 빈도를 줄이는 처리 고려.
- 페이지네이션/레이트리밋 대응(data_fetcher.py 46~56, 83~110줄)은 재시도 백오프와 max_pages 안전장치가 있어 현재 구조로 충분해 보이며, 실제 운영 중 429 발생 빈도 같은 질문은 실제 운영 로그를 봐야 판단 가능.
