## 한줄 요약
전반적인 예외처리(재시도, 캐시 폴백, 하트비트)는 견고하게 되어 있으나, 사이클 전체를 감싸는 단일 try/except 때문에 특정 전략의 예외가 다른 전략의 거래까지 막을 수 있고, LSTM 재학습 시 90일치 데이터를 매번 전량 재수집하는 비효율이 있다.

## 발견한 점 (우선순위 순)

1. **전략 단위 예외 격리 부재** — `main_loop.py`의 `run_one_cycle`(240~321행) 안에서 `STRATEGY_NAMES`를 순회하는 for 루프(258행)는 내부 try/except가 없고, `main()`의 while 루프(420~424행)에서만 사이클 전체를 감싸고 있다. 만약 특정 전략 하나(예: `lstm_predictor`의 모델 파일 손상, 특정 조건식 전략의 `min_bars()`나 `signal_with_confidence()` 버그)가 매 사이클 반복적으로 예외를 던지면, 그 전략뿐 아니라 **같은 사이클의 나머지 모든 전략**이 거래를 스킵하게 된다. 재시도해도 동일 전략에서 또 터지므로 영구적으로 전체 매매가 막힐 위험이 있다.

2. **LSTM 재학습 시 90일 데이터 매 회 전량 재수집** — `data_fetcher.fetch_minute_history`(89~152행)는 캐시 CSV가 있어도 항상 API 처음부터 끝까지 재수집하고, 캐시는 "수집 실패 시 폴백"으로만 쓰인다(195~198행). `HISTORY_DAYS_FOR_TRAIN=90`, 재학습이 하루 10회(2시간24분 간격)이므로, 매번 90일 중 겹치는 약 87.6시간(99.9%)을 또 받아온다. 코인당 약 650페이지 × 6코인 × 10회/일 규모의 불필요한 API 호출이 발생하고, `retrain_lstm()`이 `main()`의 while 루프 안에서 동기 실행되므로(427~432행) 이 수집·학습이 끝날 때까지 `run_one_cycle`이 호출되지 않아 그 시간만큼 실시간 매매 사이클이 전부 멈춘다.

3. **data_fetcher.py의 로깅이 run.log에 남지 않음** — `main_loop.py`는 `logging.basicConfig`로 콘솔+`run.log` 파일 핸들러를 설정(57~62행)하지만, `data_fetcher.py`는 `logging`을 쓰지 않고 `print()`만 사용(133, 145, 162, 196, 210행 등). 따라서 "페이지네이션이 전진하지 않아 중단", "히스토리 수집 실패" 같은 진단에 중요한 경고가 콘솔에만 찍히고 파일 로그에는 남지 않는다. PC가 서비스로 백그라운드 실행 중이거나 콘솔 출력을 보지 않는 상태라면 사후에 원인 추적이 어려워진다.

4. (참고, 낮은 우선순위) **사이클 간격 drift** — `main()`의 while 루프는 `run_one_cycle` 실행 후 60초(438~441행) 쉬므로 실제 주기는 "60초+사이클 소요시간"이다. 매 사이클이 "최신" 캔들을 다시 받아오므로 지연이 누적되진 않지만, 사이클이 오래 걸릴 경우(네트워크 지연 등) 일부 1분봉을 건너뛸 수 있다. 치명적이진 않다.

## 구체적 제안

- **main_loop.py 258행**의 `for strat_name in STRATEGY_NAMES:` 블록 본문 전체를 `try: ... except Exception as e: log.exception(f"[{strat_name}] 전략 처리 중 에러 — 이 전략만 스킵하고 계속"); continue`로 감싸서, 한 전략의 버그가 다른 전략의 거래를 막지 못하게 격리.
- **data_fetcher.py `fetch_minute_history`**에 `since: pd.Timestamp | None = None` 파라미터를 추가하고, 캐시 CSV가 있으면 그 파일의 마지막 `open_time` 이후분만 `to`/`count`로 증분 수집해 기존 캐시에 append하는 방식으로 변경. `fetch_all_minute_history`(166~199행)에서 캐시 파일 존재 시 `since=cached_df["open_time"].max()`를 넘기도록 수정.
- **data_fetcher.py** 상단에 `import logging; log = logging.getLogger("data_fetcher")`를 추가하고, 모든 `print(...)` 호출(133, 145, 162, 196, 210행 등)을 `log.warning(...)`/`log.info(...)`로 교체. `main_loop.py`가 이미 root logger에 핸들러를 달아두므로 별도 설정 없이 run.log에 함께 남게 됨.

## 리스크/트레이드오프

- 전략별 try/except를 추가하면 버그가 조용히 반복될 때 알아차리기 늦어질 수 있으므로, 같은 전략이 연속 N회 실패하면 별도로 눈에 띄게 경고 로그 레벨을 올리는 보완이 필요하다.
- 증분 수집으로 바꾸면 캐시 파일이 손상되거나 오래된 경우(예: 장시간 미실행 후 재시작) "since" 시점과 실제 cutoff(90일 전) 사이에 공백이 생길 수 있어, 캐시 최신성 검증(마지막 시각이 너무 오래됐으면 전체 재수집으로 폴백) 로직을 함께 넣어야 한다.
- print→logging 교체는 동작 자체를 바꾸지 않지만, 로그 포맷이 바뀌므로 기존에 콘솔 출력만 파싱하는 보조 스크립트가 있다면 함께 확인이 필요하다.

(실제 운영 데이터 — 지금 특정 전략이 실제로 예외를 내고 있는지, 재학습 소요 시간이 실제로 몇 분인지 등 — 는 local/ 실행 로그를 봐야 확인 가능하며 이 분석에서는 코드 구조만으로 가능성을 지적한 것입니다.)
