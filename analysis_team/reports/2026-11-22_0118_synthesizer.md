## 이번 회차 Top 3 개선 제안

1. **model_trainings 테이블 prune 추가** (storage 제안) — predictions/snapshots는 이미 일일 정리 대상인데 model_trainings만 빠져 있음. main_loop.py의 기존 prune 블록에 `prune_model_trainings(conn, keep_days=365)` 호출만 추가하면 되는 수준이라 구현 난이도가 가장 낮고, DB 무한 증가를 막는 효과는 분명함. 매매 로직과 무관해 리스크도 거의 없음.

2. **data_fetcher.py 네트워크 예외 로그 쓰로틀링** (execution 제안) — main_loop.py에 이미 있는 `_warned_repeated_exception` 패턴을 네트워크 수집 계층(`_fetch_one` 류)에 그대로 복제해 (coin, 예외타입) 단위로 1시간 1회만 전체 스택트레이스를 찍도록 함. 기존 코드 패턴을 재사용하므로 구현이 쉽고, 장애 시 로그 폭주를 막아 운영 가시성을 바로 개선함.

3. **변동성(수익률 표준편차)·MDD 보조지표 추가** (risk 제안) — 기존에 받는 candles로 코인별 변동성을 계산해 add_snapshot에 보조 필드로 저장하고, 기존 snapshots 테이블로 사후 MDD를 계산해 대시보드에 표시. 매매 로직은 전혀 건드리지 않는 순수 분석 지표 추가라 리스크가 낮고, 현재 pnl_pct 단일 지표의 한계를 바로 보완함.

세 제안 모두 보고서 스스로 "저위험/매매 로직 변경 없음"으로 명시한 항목이라 우선순위로 선정했다. RSI 필터 수정, 거래량 가드, BTC 피처 추가, finetune_chain_length 자동 분기, 재학습 스레드 분리 등은 효과는 크지만 재학습·휩쏘·동시성 리스크가 수반되어 다음 순위로 미뤘다.

## 역할 간 의견 충돌

- **전략 리포트 내부 충돌**: RSI 필터 우회(급락 시에도 SELL 허용, 매도 신호를 더 자주 내자는 방향)와 거래량 가드 추가(신호 빈도를 줄이는 방향)가 방향상 반대다. 다만 전자는 "급락에서 손절 자체가 막히는" 치명적 결함을 겨냥하고 후자는 "체결가 왜곡"이라는 상대적으로 가벼운 문제를 겨냥하므로, 급락 방치로 인한 손실이 더 크다는 점에서 RSI 바이패스 쪽 근거가 더 탄탄하다. 두 제안은 레이어가 달라(필터 완화 vs 추가 필터) 실제로는 함께 적용 가능하지만, 먼저 손봐야 할 것은 RSI 쪽이다.

- **execution vs storage**: execution은 재학습(7~8분)을 별도 스레드로 분리해 매매 사이클이 멈추지 않게 하자고 제안하지만, storage는 현재 WAL+재시도+rollback 기반 동시성이 이미 견고해 "추가 변경 불필요"라고 평가한다. 다만 storage가 말하는 견고함은 DB 트랜잭션 동시성에 한정되고, execution이 우려하는 것은 모델 파일(.pt 등) 자체의 동시 읽기/쓰기 경쟁이라 겨냥하는 대상이 다르다. 실매매가 7~8분 멈추는 쪽의 비용이 더 명확하므로 execution의 문제의식이 더 설득력 있으나, 구현 시 모델 파일 락 같은 별도 안전장치가 필요하다는 storage의 우려도 반영해야 한다.

## 전체 총평

이번 회차 5개 리포트는 전반적으로 "기존 설계가 이미 상당히 견고하다"는 공통 전제 위에서 남은 공백을 짚는 성격이 강하며, 특히 risk 리포트가 "50% 집중 리스크"라는 통념이 실제 코드(약 15% 수준)와 다르다고 바로잡은 점이 눈에 띈다. 당장 손댈 수 있는 저위험·고가치 항목(DB prune, 로그 쓰로틀링, 보조 성과지표)과 로직 변경이 필요해 재학습·호환성 리스크를 동반하는 항목(RSI 필터, BTC 피처, 재학습 비동기화)을 명확히 분리해 단계적으로 접근하는 것이 합리적이다.
