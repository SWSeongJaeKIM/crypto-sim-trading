## 한줄 요약
스키마/인덱스 설계 자체는 쿼리 패턴에 맞게 합리적으로 짜여 있다. 다만 `main_loop.py`가 전체 루프를 하나의 커넥션·트랜잭션으로 묶어 쓰는 구조 때문에, "정상 종료 전까지는 디스크에 커밋되지 않는" 심각한 구조적 리스크가 있다.

## 발견한 점 (우선순위 순)

1. **(최우선) 쓰기가 프로세스 종료 전까지 커밋 안 됨.** `storage.py:106-115`의 `connect()`는 contextmanager이고, `conn.commit()`은 `with`-블록이 끝날 때만 호출된다. 그런데 `main_loop.py`의 `main()`은 `while not _stop:` 루프 전체(273~304줄)를 하나의 `with storage.connect() as conn:` 안에 넣어놓았다(이 커넥션은 프로세스가 살아있는 내내 유지됨). `run_one_cycle`/`retrain_lstm`이 호출하는 `set_portfolio`, `add_trades`, `add_snapshot`, `add_prediction`, `resolve_predictions`, `set_meta`, `add_model_training`이 전부 이 하나의 커밋 안 된 트랜잭션에 쌓인다. SQLite는 커넥션 간 격리가 있으므로, `dashboard.py:325`가 별도 커넥션으로 같은 DB를 읽어도 main_loop가 아직 커밋하지 않은 데이터는 보이지 않는다. 더 심각한 문제는 비정상 종료(크래시, OOM-kill, `kill -9`)가 나면 마지막 정상 종료(SIGINT/SIGTERM → 루프 탈출 → with-block 종료 시 커밋, `main_loop.py:63-70, 304`) 이후 쌓인 거래/스냅샷/예측 기록이 전부 날아간다는 점이다. 다른 스크립트들(`retrain_now.py:21`, `migrate_dual_portfolio.py:37`, `dashboard.py:325`)은 모두 짧은 단위로 `connect()`를 열고 닫는데, `main_loop.py`만 예외적으로 프로세스 전체 수명으로 커넥션을 유지한다.

2. **append-only 테이블에 보관주기(retention)가 없음.** `predictions`(storage.py:90-103)와 `snapshots`는 1분 주기로 코인×전략×모드 수만큼 계속 쌓이는데, `storage.py`에는 정리(prune/archive) 함수가 전혀 없다. 현재 행 수준에서 SQLite가 못 버틸 정도는 아니지만, 장기 무중단 운영 시 선형으로 계속 커지며 파일 크기·백업 비용이 늘어난다.

3. **`portfolios` PK의 문자열 인코딩 방식.** `"<전략>__reset"/"<전략>__cumulative"`(`main_loop.py:84-87`)는 동작은 하지만 mode 값이 DB 레벨에서 검증되지 않고(CHECK 제약 없음), 모든 소비자가 `rpartition("__")` 파싱+fallback 로직을 각자 복제해야 한다(`dashboard.py:334-336`). strategy/mode를 분리하지 않은 설계라 향후 mode 추가 시 파싱 로직 전체를 손봐야 한다.

4. (경미) `add_trades`(storage.py:136-141)가 for 루프로 한 건씩 INSERT — 현재 거래 빈도상 문제는 아니다.

## 구체적 제안
- `main_loop.py:222` (run_one_cycle 끝) 및 `retrain_lstm` 종료 지점에 `conn.commit()`을 명시적으로 추가하거나, 더 근본적으로 `main()`의 `with storage.connect()`를 while 루프 바깥이 아니라 **사이클마다 새로 여는 구조**로 바꾸는 것을 권장한다(다른 스크립트들과 일관성도 맞음).
- `storage.py`에 `prune_old_snapshots(conn, keep_days)` / `prune_old_predictions(conn, keep_days)`를 추가하고, 일일 재학습 트리거(`main_loop.py:288` 근처)에서 하루 1번 호출한다.
- `portfolios` 테이블을 `strategy TEXT, mode TEXT CHECK(mode IN ('reset','cumulative')), PRIMARY KEY(strategy, mode)`로 분리하고 `get_portfolio`/`set_portfolio` 시그니처를 `(strategy, mode)`로 바꿔 문자열 파싱 제거.

## 리스크/트레이드오프
- 사이클마다 커밋하면 쓰기 I/O가 늘어 느린 디스크 환경에서 지연이 소폭 늘 수 있으나, 1분 주기 시스템 특성상 무시 가능한 수준이며 데이터 안전성 이득이 훨씬 크다.
- prune 추가 시 `model_trainings`의 "전부 보존" 설계 의도(storage.py:21-23 docstring)와는 별개로, predictions/snapshots만 정리 대상으로 한정해야 한다.
- `portfolios` 스키마 분리는 기존 DB 마이그레이션(이미 `migrate_dual_portfolio.py` 전례 있음)과 `dashboard.py` 등 소비 코드 동시 수정이 필요해 일회성 비용이 든다.
- "실제로 지금 데이터가 손실되고 있는지/대시보드가 비어 보이는지"는 실제 운영 환경(재시작 빈도 등)을 봐야 확정 가능 — 이건 코드 구조상의 리스크로 보고하며, 실제 데이터 기반 검증은 이 분석 범위 밖이다.
