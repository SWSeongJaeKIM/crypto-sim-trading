## 한줄 요약
예외처리·로깅·Upbit 호출 패턴은 이미 수십 차례의 분석을 거쳐 매우 견고한 상태이고, 재학습 중 매매 사이클이 멈추는 구조적 문제는 여러 차례 검토 후 동시성 위험(모델 파일 비원자적 쓰기) 때문에 의도적으로 보류된 상태다. 이번 리뷰에서 실제로 코드를 직접 확인해 아직 반영되지 않은 작은 구멍 2곳과, 지금까지 지적되지 않은 중복 정의 1곳을 새로 확인했다.

## 발견한 점 (2~4개, 우선순위 순)

1. **(중간) `data_fetcher.py` 478~480행: `on_progress` 콜백 호출이 try/except 밖** — `fetch_all_minute_history()`의 `_fetch_one()`에서 코인 하나당 첫 `on_progress(coin, i, len(COINS))` 호출이 보호되지 않는다. 이 콜백은 결국 `main_loop.set_progress()` → `storage.connect()`로 이어지므로, 디스크 I/O 오류 등으로 여기서 예외가 나면 `ThreadPoolExecutor`로 동시 수집 중인 다른 5개 코인의 결과까지 `future.result()`에서 통째로 날아가고, 재학습 슬롯 전체가 실패한다. 이 파일이 다른 모든 곳에서 지키는 "코인 하나의 장애가 다른 코인을 막지 않는다"는 원칙이 이 한 곳에서 깨져 있다.

2. **(낮음) `main_loop.py` 381~384행: 캔들 전체 수집 실패 로그에 반복 쓰로틀 없음** — 모델 없음/코인별 에러/사이클 전체 에러 등에는 모두 1시간 쓰로틀이 있는데, `if not candles:` 분기의 `log.warning`만 예외다. Upbit 전체 장애가 몇 시간 지속되면 매분(최대 1440회/일) 같은 줄이 반복 출력된다.

3. **(낮음, 잠재적) `COINS` 리스트가 `data_fetcher.py`(36행)와 `portfolio.py`(46행) 두 곳에 각각 하드코딩** — 지금은 값이 일치하지만, 둘 중 하나만(예: `portfolio.py`에 코인 추가) 수정되면 `main_loop.py`(38행에서 `portfolio.COINS` import)가 기대하는 코인 집합과 `data_fetcher`가 실제로 수집하는 코인 집합이 어긋나, 새 코인이 "매 사이클 가격 데이터 없음"으로 조용히(1시간에 1회 경고만) 영구 누락될 수 있다.

## 구체적 제안

- 발견 1: `data_fetcher.py` 478~480행을 `try: ... except Exception as e: log.warning(...)`로 감싸 다른 콜백 호출(506행 근처 `_on_page`)과 동일한 보호 패턴을 적용.
- 발견 2: `main_loop.py` 382행의 `log.warning`을 기존 `_warned_repeated_exception` 딕셔너리에 `("_all_candles", "_all_candles", "fail")` 같은 키로 묶어 1시간당 1회로 통일.
- 발견 3: 한쪽(`data_fetcher.py`)의 `COINS`를 삭제하고 `portfolio.py`의 `COINS`를 단일 소스로 import하거나, 반대로 통일 — 최소한 두 파일 중 한쪽에 "다른 파일과 반드시 동기화" 주석을 명시.

## 리스크/트레이드오프 (제안을 적용하면 생길 수 있는 부작용)

- 발견 1 수정은 콜백 실패를 삼키는 것뿐이라 대시보드 진행률 표시만 그 순간 한 번 누락되고, 다음 페이지 콜백에서 바로 복구되므로 매매·데이터 수집 로직에는 영향 없음.
- 발견 2 수정은 Upbit 전체 장애가 장시간 지속될 때 "지금도 실패 중"이라는 신호가 로그에 덜 자주 보이지만, `heartbeat.txt`/`progress.stage="error"`가 이미 같은 정보를 대시보드·워치독에 전달하므로 손실은 적음.
- 발견 3은 import 구조 변경이라 순환 import 여부를 먼저 확인해야 하며, 실제로 코인 목록이 바뀐 이력이 있는지는 git log 확인이 필요하다.
- 재학습 중 손절 체크 정지 문제는 과거 여러 회차(2026-11-16~2026-11-22, `analysis_team/reports/applied_log.json` 기준 최소 7회)에서 백그라운드 스레드 분리가 반복 제안됐으나, 모델 파일(`{coin}_lstm.pt`)의 비원자적 `torch.save` 쓰기와 추론측 동시 읽기 사이 경쟁 상태 때문에 매번 보류됐다 — 근본 해결에는 모델 저장을 임시파일+rename 방식의 원자적 교체로 먼저 바꾸는 선행 작업이 필요하며, 그 영향이 실제로 손실로 이어졌는지는 운영 데이터(run.log, trading.db)를 봐야 판단 가능하다.
