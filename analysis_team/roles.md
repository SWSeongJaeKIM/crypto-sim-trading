# 6에이전트 역할별 지시사항

이 파일은 스케줄 작업이 매 실행마다 그대로 따르는 "작업지시서"다.
각 역할은 독립된 서브에이전트(Agent tool)로 병렬 실행하고, 결과를
`analysis_team/reports/<타임스탬프>_<role>.md`로 저장한다.

공통 규칙 (모든 역할):
- 비판을 위한 비판 금지. "이미 잘 돼 있음"도 정당한 결론이다 — 억지로
  문제를 만들어내지 않는다.
- 제안은 구체적으로: 어떤 파일 몇 번째 줄 근처, 무엇을 어떻게 바꾸면
  되는지. "더 좋게 만들어라" 같은 추상적 제안은 쓰지 않는다.
- 리포트는 한국어, 500단어 이내. 형식:
  ```
  ## 한줄 요약
  ## 발견한 점 (2~4개, 우선순위 순)
  ## 구체적 제안
  ## 리스크/트레이드오프 (제안을 적용하면 생길 수 있는 부작용)
  ```
- PC에서 실제로 돌고 있는 운영 데이터(거래내역, 손익, 학습 정확도 등)는
  이 분석팀이 볼 수 없다 — **코드 구조와 로직만으로** 판단한다. 데이터를
  봐야 알 수 있는 질문("지금 실제로 수익이 나고 있나?")에는 답하지 않고,
  "이건 실제 운영 데이터를 봐야 판단 가능"이라고 명시한다.

---

## 1. 전략 분석가 (strategy)

대상 파일: `local/strategies.py`

관점:
- 4개 조건식(ma_cross_rsi, bollinger_rsi, macd_momentum, trend_follow)의
  진입/청산 조건이 논리적으로 타당한가?
- 기본 파라미터값(기간, 임계값 등)이 1분봉 스캘핑에 적합한가, 아니면
  원래 더 긴 타임프레임(일봉 등)에서 쓰이는 값을 그대로 가져온 건 아닌가?
- 조건식들이 서로 너무 비슷해서(상관관계가 높아서) 사실상 같은 신호를
  내고 있지 않은가?
- 극단적 시장 상황(급등/급락, 거래량 바닥)에서 오작동할 소지가 있는가?

## 2. LSTM 분석가 (lstm)

대상 파일: `local/lstm_model.py`

관점:
- 피처 구성(`FEATURE_COLS`)이 1분 뒤 방향성을 예측하는 데 충분한가?
  빠진 피처(예: 호가 스프레드, 다른 코인과의 상관관계)가 있는가?
- `SEQ_LEN`(시퀀스 길이)과 모델 구조(`LSTMClassifier`)가 데이터 양/
  문제 복잡도에 맞는가? 과적합/과소적합 소지는?
- 파인튜닝 방식(기존 가중치 이어서 학습)이 "최근 패턴 반영"과 "과거
  패턴 망각"의 균형을 잘 잡고 있는가?
- 재학습 주기(하루 1회) + 학습 데이터 기간(30일)이 1분봉 예측이라는
  과제와 잘 맞는가?

## 3. 실행/버그 분석가 (execution)

대상 파일: `local/main_loop.py`, `local/data_fetcher.py`

관점:
- 예외처리가 충분한가? API 호출 실패, 데이터 누락, 모델 파일 없음 등
  엣지케이스가 사이클을 죽이지 않고 복구되는가?
- Upbit API 호출 패턴(페이지네이션, rate limit 대응)에 문제가 없는가?
- 사이클 타이밍(60초 고정)과 실제 작업 소요 시간 사이에 밀림/누적
  지연 가능성이 있는가?
- 로깅이 문제 진단에 충분한가?

## 4. 데이터/저장소 분석가 (storage)

대상 파일: `local/storage.py`

관점:
- 스키마 설계(테이블/인덱스)가 쿼리 패턴에 맞는가? 느려질 만한 쿼리가
  있는가(예: WHERE 없는 전체 스캔)?
- `predictions`, `model_trainings` 같은 계속 쌓이는(append-only) 테이블이
  시간이 지나면 용량/속도 문제를 일으킬 가능성은? 보관주기(retention)가
  필요한가?
- 데이터 정합성: 동시 쓰기(main_loop)와 읽기(dashboard)가 충돌할 소지는?
- `portfolios` 테이블의 `"<전략>__reset"/"<전략>__cumulative"` 네이밍
  방식이 장기적으로 유지보수하기 괜찮은 설계인가, 더 나은 스키마가 있는가?

## 5. 리스크 분석가 (risk)

대상 파일: `local/portfolio.py`, `local/main_loop.py`의 매매 실행 부분

관점:
- `TRADE_FRACTION`(매매 시 자금의 50%를 움직임)이 과도한 집중 리스크를
  만들지 않는가?
- 코인 6개 균등 배분 구조가 변동성이 다른 코인들(BTC vs DOGE 등) 사이에
  리스크를 공평하게 분산하고 있는가?
- 리셋(7일)/누적 포트폴리오 구조가 "단기 성과"와 "장기 성과"를 보여주는
  목적에 잘 맞는가, 보완할 지표가 있는가?
- 전략이 손실 중일 때 손실을 키우는 방향으로 계속 매매할 위험(물타기성
  매수 등)이 로직상 있는가?

## 6. 종합 조정자 (synthesizer)

입력: 위 1~5번이 작성한 이번 회차 리포트 5개 전체.

작업:
- 5개 리포트의 제안들을 모아서 중복/유사한 것을 하나로 합친다.
- "지금 가장 먼저 해볼 만한 개선 Top 3"를 선정 — 효과 대비 구현
  난이도가 낮은 것 우선.
- 서로 충돌하는 제안이 있다면(예: 한쪽은 "더 자주 매매", 다른 쪽은
  "매매 빈도 낮춰라") 그 긴장관계를 명시하고 어느 쪽이 더 근거가
  탄탄한지 판단.
- 출력 형식은 공통 규칙과 다르게:
  ```
  ## 이번 회차 Top 3 개선 제안
  ## 역할 간 의견 충돌 (있다면)
  ## 전체 총평 (한 문단)
  ```
